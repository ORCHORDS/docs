# tls-termination-architecture

**Issue:** Every service fronted by a reverse proxy, CDN, or load balancer forces the same architectural decision — where does TLS end? Terminate at the edge and forward plaintext (fast but the internal network is unencrypted), pass TLS through untouched (encrypted end-to-end but the proxy is blind), or terminate and re-encrypt to the origin (both, at the cost of two certificate fleets). This article covers how to choose between edge, passthrough, and re-encrypt topologies, how client identity and trust headers behave under termination, and the certificate, protocol, and operational consequences of each choice. It deliberately complements `nginx-reverse-proxy-config.md` (nginx mechanics) and `ssl-tls-certificate-management.md` (certificate lifecycle) by focusing on the topology decision itself.

## The Three Termination Topologies

1. **Edge termination.** The proxy (NGINX, HAProxy, ALB, ingress controller) terminates client TLS and forwards plaintext HTTP to backends. This is the simplest model: one certificate fleet, full L7 visibility (routing, WAF, header rewriting, compression) at the proxy, and cheap backend connections — but traffic inside the network is unauthenticated and readable, which is only acceptable when the backend network is a trusted, isolated segment.
2. **Passthrough.** The proxy forwards TCP (or proxy-protocol-tagged TCP) without decrypting, so the origin sees the client's original TLS session — required when the origin must present its own certificate to the client or consume client certificates directly. The cost: the proxy cannot read SNI beyond the ClientHello, cannot apply L7 rules or WAF, cannot cache, and per-backend routing is limited to SNI/ALPN-based dispatch.
3. **Re-encrypt.** Terminate at the edge, then establish a fresh TLS (or mutual TLS) connection to each origin. You keep edge features plus encryption and optionally client-cert authentication all the way to the backend; the price is a second certificate fleet on the origins (usually an internal CA) and roughly double the TLS handshakes per connection unless proxy-to-origin connections are pooled and kept alive.
4. **Choosing by threat model, not habit.** The decision is really "do I trust the network between proxy and origin?": edge termination assumes a segmented, controlled network (a VPC with locked security groups); re-encrypt or passthrough is the answer for zero-trust networks, multi-tenant clusters, or compliance regimes that mandate encryption in transit on every hop.
5. **Hybrids are the norm.** Real deployments mix modes per-route: public marketing traffic on edge termination with a CDN, payment/API routes re-encrypted to origins, and gRPC/WebSocket or client-cert routes passed through — ingress resources (Kubernetes, OpenShift route `termination:` types) and LB listeners support per-route selection precisely for this.

## Identity and Header Trust Under Termination

1. **X-Forwarded-* headers are the leak point.** With edge termination, the origin learns the client IP, protocol, and host only via `X-Forwarded-For`/`X-Forwarded-Proto`/`X-Forwarded-Host`; the origin must be configured to trust these exclusively from the proxy (NGINX `real_ip` module with `set_real_ip_from`, Express `trust proxy`) or any direct-to-origin request can spoof its identity headers.
2. **Client certificates do not survive naive termination.** Under edge or re-encrypt termination the origin never sees the client's TLS handshake, so client-cert authentication silently breaks when migrating from passthrough; the standard fix is mTLS at the proxy and forward identity in a header (`X-SSL-Client-Cert`, `X-SSL-Client-DN` from HAProxy/NGINX variables) that the origin validates like a signed assertion.
3. **Re-propagating identity under mTLS.** A robust pattern terminates inbound client mTLS at the proxy, authenticates the client, then opens its own authenticated mTLS session to the origin and forwards the verified client identity in a header — the origin authenticates the proxy (client cert) rather than the end user, and trusts the identity header because the connection is mutually authenticated.
4. **Backend authentication of the proxy is mandatory in re-encrypt.** Encryption alone proves nothing about who is calling: give each proxy a client certificate from your internal CA and verify it at the origin, otherwise any workload in the subnet that can reach the origin port counts as "the proxy".
5. **Protocol downgrade signals.** With edge termination the origin sees plain HTTP and cannot distinguish "proxy sent HTTP because the client used HTTP" from an attacker on the internal network; mitigate with a shared header injected by the proxy, strict network policy allowing only proxy→origin on the backend port, and HSTS at the edge so clients never speak plain HTTP in the first place.

## Certificate and Operational Consequences

1. **Two fleets under re-encrypt.** The edge needs public certificates (ACME/ACM — see `lets-encrypt-auto-renewal.md`) while origins need internal-CA certificates; automate both, because the edge fleet fails publicly while the internal fleet fails quietly — internal cert expiry is a classic "everything 503s and nothing looks expired" incident.
2. **SNI and hostname discipline.** Passthrough LBs dispatch on SNI, so every backend service behind one listener needs a unique, resolvable hostname; wildcard certs help at the edge, but remember wildcards do not match second-level subdomains (`a.b.example.com`), which bites multi-tenant routing schemes.
3. **Connection pooling changes the cost model.** Re-encrypt doubles handshakes only if every client connection maps to a fresh backend TLS connection; with keepalive and connection reuse at the proxy (HAProxy `http-reuse safe`, NGINX `keepalive` upstreams), backend handshakes amortize across many client sessions and the CPU overhead becomes marginal.
4. **Cipher and protocol parity.** The two TLS legs are independent sessions: the edge can offer TLS 1.3 + modern groups to clients while the origin leg runs whatever the backend stack supports — useful for isolating legacy backends, but define a floor (TLS 1.2 minimum, ideally 1.3 internally) and monitor both legs separately in metrics.
5. **Observability of the encrypted hop.** Under passthrough the proxy loses all HTTP visibility, so error budgets and per-route metrics must come from the origins themselves; under re-encrypt, log both the client-facing status and the backend TLS errors distinctly (certificate validation failures vs 5xx), or debugging origin cert problems feels like reading tea leaves.

## Pitfalls

1. **Redirect loops after enabling HTTPS at the edge.** The origin sees plain HTTP (the TLS ended upstream), issues a redirect to HTTPS, and the cycle repeats; the origin must honor `X-Forwarded-Proto` when generating redirects, and this is the single most common misconfiguration when introducing a TLS-terminating proxy in front of an existing app.
2. **Health checks bypass TLS entirely.** Load balancer health checks (see `load-balancer-health-checks.md`) usually probe the backend port directly, so a valid health status does not prove the re-encrypted path or origin certificate is good — check the TLS listener separately or health checks will pass while user traffic fails handshake.
3. **Proxy-to-origin cert validation left off.** Many re-encrypt setups configure the proxy with `verify none` for convenience during rollout and never tighten it; without verification, re-encrypt is encryption theater — any endpoint that can intercept the connection terminates it.
4. **Stapling and OCSP differ per leg.** OCSP stapling must be configured on whichever component terminates (edge), while origin certificates from a private CA typically have no external resolver at all; skipping stapling at the edge adds client latency and leaks query patterns to the CA.
5. **Protocol detection on shared ports.** Running TLS and plaintext listeners on the same port (HAProxy `ssl-hello-word`/detect-protocol, or PROXY protocol v2 TLV tagging) is convenient but produces hair-splitting bugs where PROXY-protocol bytes reach an origin that does not expect them; keep protocol expectations explicit per listener, and test both paths after any LB software upgrade.
