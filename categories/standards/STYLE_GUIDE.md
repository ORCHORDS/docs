# Documentation Style Guide

## Goals

Documentation should be accurate, concise, searchable, accessible, and usable during normal work and under pressure.

## Writing rules

- Lead with purpose and scope.
- Use short sections with descriptive headings.
- Prefer active voice and direct verbs.
- Define acronyms on first use.
- Separate requirements from examples and implementation claims.
- Use tables for comparisons, roles, thresholds, and evidence.
- Avoid inflated assurance such as "fully secure" or "100% compliant".
- State uncertainty explicitly.

## Requirement words

Use **MUST**, **SHOULD**, and **MAY** only for normative statements. Normative wording follows RFC 2119 and RFC 8174 conventions.

## Dates and versions

Use ISO dates in review metadata, identify versioned frameworks, mark drafts as drafts, and do not use "latest" in a controlled requirement unless the verification mechanism is defined.

## Links and accessibility

Prefer primary sources, use relative links inside the repository, avoid private resources, use descriptive link text, meaningful heading order, useful alt text, and simple tables.

See [Accessibility Policy](../accessibility/ACCESSIBILITY_POLICY.md).

## SOP format

SOPs should include purpose, trigger/scope, roles, inputs, procedure, escalation, evidence, completion criteria, exceptions, and related documents.

## Claims

Do not state a control exists merely because policy requires it. Use "required", "implemented", "planned", or "not applicable" accurately.
