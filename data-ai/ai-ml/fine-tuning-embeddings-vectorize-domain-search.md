# Fine-Tuning Embeddings for Domain-Specific Semantic Search with Vectorize
- **Date**: 2026-08-22
- **Author**: example.com
- **Status**: active

## Symptom / Use-case

Generic embedding models (BAAI/bge-base, all-MiniLM) return poor ranking for
domain-specific queries: a music platform searching for "bright acoustic strumming"
or a legal platform searching "force majeure construction contract" gets off-topic
results because the general model was not trained on that vocabulary.

You want to fine-tune a lightweight embedding model on your own query–passage pairs
and deploy it to Cloudflare Vectorize for production semantic search.

## Context

Cloudflare Vectorize supports custom embedding dimensions (up to 1 536 for
`cosine` metric) and allows you to upload embeddings generated by any model — not
only the Workers AI catalogue. The fine-tuning workflow lives outside Cloudflare
(training on GPU), but the inference and indexing workflow runs entirely on the
edge.

Recommended base models for fine-tuning (size vs. quality trade-off):

| Model | Dim | MTEB avg | Good for |
|---|---|---|---|
| `BAAI/bge-small-en-v1.5` | 384 | 62.1 | Low-latency mobile |
| `BAAI/bge-base-en-v1.5` | 768 | 63.5 | Balanced |
| `intfloat/e5-base-v2` | 768 | 61.5 | Query-expansion friendly |
| `nomic-ai/nomic-embed-text-v1` | 768 | 62.4 | Long documents |

Fine-tuning approach: **contrastive learning** with `sentence-transformers`
`MultipleNegativesRankingLoss` on (query, positive_passage) pairs mined from your
platform's click/purchase logs.

## Section 1 — Mining Training Pairs from Platform Logs

Good training data is the difference between a useful fine-tune and a wasted GPU
hour. Use implicit feedback (clicks, purchases, bookmarks) as weak supervision.

```python
# scripts/mine_pairs.py
import sqlite3, json, random

DB_PATH = "analytics.db"  # or export from D1 via wrangler d1 export

def mine_pairs(db_path: str, min_clicks: int = 2) -> list[dict]:
    """
    Returns list of {"query": ..., "positive": ...} dicts.
    Filters low-signal queries (< min_clicks).
    """
    conn = sqlite3.connect(db_path)
    rows = conn.execute(
        """
        SELECT s.query_text, p.passage_text
          FROM search_clicks sc
          JOIN searches s ON sc.search_id = s.id
          JOIN passages p ON sc.passage_id = p.id
         GROUP BY sc.search_id, sc.passage_id
        HAVING COUNT(*) >= ?
        """,
        (min_clicks,),
    ).fetchall()
    conn.close()

    pairs = [{"query": q, "positive": p} for q, p in rows]
    random.shuffle(pairs)
    return pairs


if __name__ == "__main__":
    pairs = mine_pairs(DB_PATH)
    split = int(len(pairs) * 0.9)
    with open("train_pairs.jsonl", "w") as f:
        for pair in pairs[:split]:
            f.write(json.dumps(pair) + "\n")
    with open("eval_pairs.jsonl", "w") as f:
        for pair in pairs[split:]:
            f.write(json.dumps(pair) + "\n")

    print(f"Train: {split}  Eval: {len(pairs) - split}")
```

## Section 2 — Fine-Tuning with sentence-transformers

```python
# scripts/finetune_embeddings.py
from sentence_transformers import (
    SentenceTransformer,
    InputExample,
    losses,
)
from sentence_transformers.evaluation import InformationRetrievalEvaluator
from torch.utils.data import DataLoader
import json

BASE_MODEL = "BAAI/bge-base-en-v1.5"
OUTPUT_DIR = "./fine_tuned_embeddings"
EPOCHS     = 3
BATCH_SIZE = 32


def load_pairs(path: str) -> list[InputExample]:
    examples = []
    with open(path) as f:
        for line in f:
            obj = json.loads(line)
            examples.append(InputExample(texts=[obj["query"], obj["positive"]]))
    return examples


model = SentenceTransformer(BASE_MODEL)

train_examples = load_pairs("train_pairs.jsonl")
train_dataloader = DataLoader(train_examples, shuffle=True, batch_size=BATCH_SIZE)

# MultipleNegativesRankingLoss treats other items in the batch as negatives
# — efficient for large batches; no need to mine hard negatives up front.
loss = losses.MultipleNegativesRankingLoss(model)

# Build an evaluator from the eval pairs
eval_queries    = {}
eval_corpus     = {}
eval_relevant   = {}

with open("eval_pairs.jsonl") as f:
    for i, line in enumerate(f):
        obj = json.loads(line)
        qid  = f"q{i}"
        pid  = f"p{i}"
        eval_queries[qid]  = obj["query"]
        eval_corpus[pid]   = obj["positive"]
        eval_relevant[qid] = {pid}

evaluator = InformationRetrievalEvaluator(
    queries=eval_queries,
    corpus=eval_corpus,
    relevant_docs=eval_relevant,
    name="domain-eval",
)

model.fit(
    train_objectives=[(train_dataloader, loss)],
    evaluator=evaluator,
    epochs=EPOCHS,
    warmup_steps=100,
    output_path=OUTPUT_DIR,
    show_progress_bar=True,
)

print(f"Model saved to {OUTPUT_DIR}")
```

## Section 3 — Exporting and Hosting the Model for Workers Inference

Workers AI does not yet allow uploading arbitrary ONNX models to the catalogue.
Two deployment options:

**Option A — Self-hosted inference Worker (recommended for small models)**

Export to ONNX and run via `@xenova/transformers` in a Worker with compatibility
flag `nodejs_compat`.

```bash
# Export the fine-tuned model to ONNX
python -c "
from sentence_transformers import SentenceTransformer
import torch, os

model = SentenceTransformer('./fine_tuned_embeddings')
dummy = ['example query']
embeddings = model.encode(dummy)
print('Embedding dim:', embeddings.shape[1])

# Export via ONNX (requires optimum)
from optimum.exporters.onnx import main_export
main_export('./fine_tuned_embeddings', output='./onnx_model', task='feature-extraction')
"
```

```typescript
// workers/embed/index.ts  — lightweight embedding Worker
import { pipeline } from "@xenova/transformers";
import type { Env } from "./env";

let extractor: ReturnType<typeof pipeline> extends Promise<infer T> ? T : never;

export default {
  async fetch(req: Request, _env: Env): Promise<Response> {
    extractor ??= await pipeline("feature-extraction", "./model");

    const { texts } = await req.json<{ texts: string[] }>();

    // Batch limit: 32 texts max per call to stay within CPU budget
    const output = await extractor(texts.slice(0, 32), { pooling: "mean", normalize: true });

    return Response.json({ embeddings: Array.from(output.data) });
  },
};
```

**Option B — Workers AI catalogue model + query expansion**

If you cannot host the fine-tuned model, prepend a domain-specific prefix to
queries to steer a general model:

```typescript
function expandQuery(raw: string, domain: "music" | "legal"): string {
  const prefixes = {
    music:  "Represent this music search query: ",
    legal:  "Represent this legal document retrieval query: ",
  };
  return `${prefixes[domain]}${raw}`;
}
```

This is a cheap approximation; real fine-tuning is significantly better for
specialised domains.

## Section 4 — Indexing and Searching with Vectorize

```typescript
// workers/search/vectorize-search.ts
export interface Env {
  VECTORIZE: VectorizeIndex;
  EMBED_WORKER: Fetcher;   // Service binding to the embedding Worker
}

async function getEmbedding(env: Env, text: string): Promise<number[]> {
  const res = await env.EMBED_WORKER.fetch("https://internal/embed", {
    method: "POST",
    headers: { "Content-Type": "application/json" },
    body: JSON.stringify({ texts: [text] }),
  });
  const { embeddings } = await res.json<{ embeddings: number[] }>();
  // embeddings is flat [dim] for a single text
  return embeddings;
}

// Upsert passages during ingestion
export async function indexPassage(
  env: Env,
  id: string,
  text: string,
  metadata: Record<string, string>,
): Promise<void> {
  const vector = await getEmbedding(env, text);
  await env.VECTORIZE.upsert([{ id, values: vector, metadata }]);
}

// Query at search time
export async function semanticSearch(
  env: Env,
  query: string,
  topK: number,
  isMobile: boolean,
): Promise<VectorizeMatch[]> {
  const queryVec = await getEmbedding(env, query);

  const results = await env.VECTORIZE.query(queryVec, {
    topK: isMobile ? Math.min(topK, 5) : topK,  // fewer results on mobile
    returnMetadata: "indexed",
    returnValues: false,  // omit raw vectors from response to save bandwidth
  });

  return results.matches;
}
```

Wrangler binding for Vectorize:

```toml
[[vectorize]]
binding        = "VECTORIZE"
index_name     = "domain-search-index"
```

Create the index with the correct dimension from your fine-tuned model:

```bash
npx wrangler vectorize create domain-search-index \
  --dimensions=768 \
  --metric=cosine
```

## Anti-patterns

- **Fine-tuning on too few pairs** — fewer than ~500 (query, passage) pairs usually
  hurts rather than helps; the model overfits. Collect at least 2 000 before
  committing to a fine-tuning run.
- **Skipping evaluation** — shipping a fine-tuned model without comparing NDCG@10
  against the base model on a held-out set means you might be deploying a worse
  model.
- **Different embedding for index vs. query** — if you fine-tuned for asymmetric
  retrieval (short query, long passage) always encode queries and passages with the
  same checkpoint but different instruction prefixes; using the base model for one
  and the fine-tuned for the other breaks similarity scores.
- **Neglecting normalisation** — `sentence-transformers` normalises by default; if
  you export to ONNX and call it raw you must divide each vector by its L2 norm
  before upserting to Vectorize (which uses cosine similarity assuming unit vectors).
- **Mobile: returning full passage text in search results** — Vectorize `returnMetadata`
  can include the full passage. On mobile return only `id` and `title`; fetch the
  full passage on demand.

---

## Gotchas

- Vectorize index dimensions are immutable after creation. If your fine-tuned model
  has a different output dimension than the index was created with, you must create
  a new index and re-index all documents.
- `wrangler vectorize upsert` has a 1 000-vector batch limit per call. For bulk
  ingestion, split the payload and retry with exponential back-off on 429s.
- `@xenova/transformers` in a Worker requires the ONNX model files to be bundled as
  static assets in the Worker. Use `wrangler.toml` `[assets]` stanza or upload to
  R2 and stream-load at cold start.
- Fine-tuning with `MultipleNegativesRankingLoss` is sensitive to batch size: small
  batches (< 16) produce weak negatives and under-train; large batches (> 128) can
  be unstable. 32–64 is the sweet spot for consumer GPU.
- D1 export via `wrangler d1 export` outputs a SQLite dump; you may need to adapt
  the `mine_pairs.py` script to the specific dump format.

## Verification

```python
# scripts/eval_fine_tuned.py
from sentence_transformers import SentenceTransformer
from sentence_transformers.evaluation import InformationRetrievalEvaluator
import json

base   = SentenceTransformer("BAAI/bge-base-en-v1.5")
tuned  = SentenceTransformer("./fine_tuned_embeddings")

# Reload eval pairs (same split as during training)
eval_queries, eval_corpus, eval_relevant = {}, {}, {}
with open("eval_pairs.jsonl") as f:
    for i, line in enumerate(f):
        obj = json.loads(line)
        eval_queries[f"q{i}"]   = obj["query"]
        eval_corpus[f"p{i}"]    = obj["positive"]
        eval_relevant[f"q{i}"] = {f"p{i}"}

evaluator = InformationRetrievalEvaluator(
    eval_queries, eval_corpus, eval_relevant, name="compare"
)

print("Base model NDCG@10:", evaluator(base,  output_path="./results-base"))
print("Fine-tuned NDCG@10:", evaluator(tuned, output_path="./results-tuned"))
```

Expected improvement: +3–10 NDCG@10 points on a well-curated domain dataset.
