# Node EventEmitter captureRejections error loop

**Issue:** An async EventEmitter listener rejects and `captureRejections` routes it to an async `error` listener that also rejects, producing an unhandled rejection or recursive-looking failure path instead of a contained error.

**Date:** 2026-08-18
**Author:** ORCHORDS
**Status:** documented

## Cause

With `captureRejections` enabled, Node attaches a rejection handler to a listener's returned Promise. A rejection is sent to `Symbol.for("nodejs.rejection")` when implemented, otherwise to the `error` event. Rejections generated by this mechanism are not captured again for `error` handlers, specifically to avoid infinite error loops. Node recommends not using async functions as `error` handlers.

## Controls

- Decide per emitter whether Promise-returning listeners are supported and enable `captureRejections` explicitly rather than through an unnoticed global default.
- Always install a synchronous `error` listener before events can be emitted.
- Make the synchronous handler enqueue bounded recovery or logging work; attach an explicit catch to that work.
- Use a custom rejection hook only when its ownership, arguments, and failure policy are tested.
- Include event name and stable operation identity in logs without recording secrets or full payloads.
- Keep fatal-process policy separate from application retry policy; do not continue after corrupted invariants.
- Prevent listener leaks and duplicate registration during reconnect or hot-reload paths.

## Safe pattern

```js
import { EventEmitter } from "node:events";

const bus = new EventEmitter({ captureRejections: true });

bus.on("error", (error) => {
  void reportError(error).catch((reportErrorFailure) => {
    process.stderr.write(`error reporting failed: ${reportErrorFailure.message}\n`);
  });
});
```

## Verification

Test a synchronous throw, an async rejection, a rejection from the reporting task, absence of an `error` listener, and repeated concurrent failures. Capture `unhandledRejection` and `uncaughtException` in an isolated child process and assert the chosen process-exit behavior.

## Gotchas

`captureRejections` does not turn EventEmitter into an awaited task queue: `emit()` still returns synchronously and does not wait for listener Promises. Enabling the global `events.captureRejections` changes the default only for subsequently created emitters and can alter unrelated code.
