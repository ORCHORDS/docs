# MCP Async Task Replay

## Scope

This article covers replay semantics for asynchronous MCP task results: idempotency keys, duplicate suppression, ordering, and dedupe windows. MCP (Model Context Protocol) supports asynchronous tasks in which a client submits a request that the server processes in the background and returns a task handle; the client later polls for status and retrieves the result when ready. Replay is the mechanism by which the client (or an intermediate broker) can safely retrieve the same result multiple times — for example, after a network failure that lost the original response — without causing the server to re-execute the task. The article covers the protocol-level guarantees MCP provides, the responsibilities of clients and servers, and the operational discipline for managing replay safely.

Out of scope: synchronous MCP request handling (covered in the MCP tool boundaries article and related), the design of the underlying message broker or task queue, and the broader task lifecycle (covered in the MCP tasks extension lifecycle article). This article focuses specifically on replay.

## Implementation workflow

Every asynchronous MCP task is identified by an opaque task identifier assigned by the server at submission time. The task identifier is unguessable (high-entropy, generated by the server's cryptographic random source), unique within the server's lifetime, and returned to the client in the initial task-creation response. The identifier is the foundation of replay: subsequent retrieval operations reference the same identifier and receive the same result.

Each task carries an idempotency key supplied by the client at submission time. The idempotency key is a string the client generates per logical operation and reuses across retries of the same submission. When the server receives a submission with an idempotency key it has seen before within the dedupe window, the server returns the original task identifier and the original task's status without re-executing the task. The dedupe window is configurable per server and per task kind; common defaults are 24 hours for client-driven retries and longer for tasks that involve expensive computation.

Replay is supported through two distinct retrieval operations: `tasks/get` for retrieving the current task state and any available result, and `tasks/result` for retrieving the result artifact specifically. Both operations are safe to retry; the server must return the same response for the same task identifier within the result-retention window. The result-retention window is the duration during which the server keeps the result available for retrieval; beyond that window, the server may evict the result and a subsequent retrieval will receive a `result-evicted` error.

For tasks that produce streamed results, replay is supported through a `tasks/stream` operation that returns the full sequence of events from the start. The operation may be paginated if the stream is long; each page carries a continuation token that the client uses to fetch the next page. The server guarantees that pages are returned in stream order; clients process pages in order and use the continuation token to fetch the next page. A client that retries `tasks/stream` after a partial retrieval must either resume from the last successfully processed page or restart from the beginning; the choice depends on the client's idempotency requirements.

Duplicate suppression at the server side requires persistent storage. The server stores, for each task, the task identifier, the idempotency key, the current status, the result (if any), and a timestamp. The storage must be durable across server restarts; losing the dedupe table would allow replays to re-execute tasks that the client believes have already been completed, violating the idempotency guarantee. The server's storage must be sized for the dedupe window and the rate of task submission; under-provisioned storage will manifest as silent dedupe failures.

Clients track their own retrieval position. The client stores the last successfully processed task identifier, the last successfully retrieved page token, and the result hash for each in-flight task. When the client retries a retrieval operation, it compares the server's response to its last known state; mismatches are surfaced for operator review. The client-side state allows the client to detect silent corruption in the server's replay behavior.

## Controls

Dedupe windows are configurable and enforced. The server must document its dedupe window per task kind and reject submissions that include idempotency keys outside the supported scope. Clients must respect the dedupe window: an idempotency key that has expired may legitimately result in a new task execution, and the client must be prepared for that possibility.

Replay protection applies to side effects, not only to results. A task that has external side effects (for example, a task that sends an email or modifies a database) must implement its own idempotency on the side-effect path; the MCP-level dedupe is necessary but not sufficient. A server that detects the same idempotency key twice within the window must not re-execute the side-effect path; if it cannot guarantee non-re-execution, it must surface that limitation explicitly in its documentation.

Replay log retention is bounded. The server retains the dedupe table and the result artifacts for the configured windows and then evicts. The eviction is logged with the task identifier (not the result content) so that operators can correlate evictions with downstream activity. Eviction before a client's last retrieval is a documented risk that the client must be prepared for; the server surfaces `result-evicted` as a distinct error so the client can distinguish it from transient failures.

Replay is observable. The server emits `task-deduplicated`, `task-result-retrieved`, `task-result-evicted`, and `task-stream-resumed` events. The events feed the same telemetry pipeline as trace spans. Operators must monitor the dedupe-hit rate: a sudden change indicates either client misbehavior (excessive retries) or server misconfiguration (insufficient dedupe window).

## Validation evidence

Conformance tests must cover: idempotent submission returning the same task identifier for the same idempotency key, `tasks/get` replay returning the same result, `tasks/result` replay returning the same result, `tasks/stream` replay returning the full sequence from the start, page continuation tokens advancing in order, eviction behavior after the retention window, dedupe-table durability across simulated server restart, and side-effect idempotency on the server's side. Inject a duplicate submission and verify no second execution occurs.

Operational evidence includes: dedupe hit rate, distribution of task durations, count of retrieval retries per task, count of `result-evicted` errors, count of stream-resume operations, and the storage footprint of the dedupe table. Reviewers should be able to trace any task from submission through result retrieval and any replay attempts in between.

## Failure handling

When the dedupe table is unavailable, the server must reject all submissions that include idempotency keys with a `dedupe-unavailable` error. The server must not silently accept submissions without enforcing idempotency; doing so would allow clients to trigger duplicate executions of side-effecting tasks. The rejection is logged and operators are notified.

When the result artifact has been evicted but the task identifier is still valid, the server returns `result-evicted` rather than a generic error. The client treats `result-evicted` as a non-retryable condition; the task must be re-submitted under a new idempotency key if the operation must be performed again. The client surfaces the eviction for operator review.

When the client's continuation token is invalid (for example, because the server has restarted and lost pagination state), the client must restart the stream from the beginning. The server's stream-restart behavior must be deterministic; given the same task and the same `tasks/stream` operation, the server must produce the same sequence of events. If the server cannot guarantee that, the protocol guarantees are broken and the implementation must be patched.

When replay collides with a task that has been cancelled (for example, the client retries a `tasks/result` operation for a task the user cancelled), the server returns the cancelled task's status and refuses to return the result. The cancellation is authoritative and must not be overridden by a replay.
