# Agent Tool Result Trust Levels

## Scope

This article covers the classification of tool results by trust level so that downstream agents apply appropriate handling and data-flow controls. A tool result is the data returned to the agent by a tool call: an HTTP response body, a database query result, a file read, a search engine output, or a structured response from a peer agent. The trust level of the result is a function of the tool's identity, the channel through which the result was retrieved, the freshness of the data, the integrity protections in place, and the sensitivity of the data the tool is permitted to expose. Different trust levels require different downstream handling: a high-trust result may be used in durable decisions; a low-trust result must be validated, sanitized, or treated as untrusted input.

Out of scope: the broader authorization model for invoking tools (covered by the tool authorization least-privilege and tool permission scopes articles), the schema validation of tool results (covered by the structured output schema enforcement article), and the negotiation of tool capabilities (covered by the capability validation and tool registry schema evolution articles).

## Implementation workflow

Define a trust-level taxonomy. The recommended taxonomy has four levels: `trusted-authoritative`, `trusted-verified`, `untrusted-external`, and `untrusted-unverified`. `trusted-authoritative` is for results from first-party tools under the deploying organization's direct control, with authenticated transport and known schema. `trusted-verified` is for results from third-party tools whose identity is verified through a workload attestation, whose schema is versioned, and whose responses are signed or otherwise tamper-evident. `untrusted-external` is for results from tools whose responses come from external content sources (web pages, user-supplied documents, search results) where the content itself may be adversarial even if the tool's transport is authenticated. `untrusted-unverified` is for results from tools whose identity or schema cannot be verified.

Tag every tool result with a trust level at the moment of receipt. The tag is generated by the tool dispatcher based on the tool's declared trust posture and the verification checks performed at receipt. The tag travels with the result through the agent's processing pipeline and is visible in the audit trail. The tag is part of the structured output envelope; downstream consumers see the tag and apply their own policy based on it.

Trust propagation rules are explicit. Each downstream use of a tool result carries forward the minimum trust level of all the inputs that contributed to it. If a high-trust decision depends on a low-trust input, the decision itself inherits the lower trust level. This is the same monotonicity discipline used in information-flow security, sometimes called "no read up, no write down" in the Bell-LaPadula sense, applied to agent data flows.

Validate before use. A `trusted-verified` result may still contain adversarial content if the underlying tool is compromised or if the data the tool aggregates is itself untrusted. The agent validates the result against the tool's declared schema, the expected size and shape, the freshness window, and any cryptographic signatures the tool provides. A result that fails validation is downgraded to `untrusted-unverified` regardless of the tool's declared trust posture.

Sanitize before promoting. An `untrusted-external` result may contain content that could influence the agent in undesirable ways — for example, instructions embedded in a web page that attempt to manipulate the agent's behavior. The agent sanitizes the result by stripping or escaping embedded instructions, isolating the content from the prompt's instruction layer, and limiting the operations the result can influence. The prompt injection OWASP guidance documents this class of risk.

Restrict influence of low-trust data. A result at the lowest trust level must not directly drive high-trust actions. Specifically, the agent must not use `untrusted-unverified` content to make durable decisions, to invoke irreversible tools, or to authenticate the user. The agent may use the content as a hint for further tool calls (which themselves produce verified results) but the hint itself does not enter the durable record.

## Controls

The trust-level taxonomy is enforced by the runtime, not by convention. The agent code reads and writes trust levels through a runtime API that does not allow arbitrary code to elevate a result's trust. Elevation requires an explicit validation step whose output is itself signed and audit-logged.

Tool declarations include the tool's intrinsic trust posture. The MCP tool annotation hints and the OpenID AuthZEN policy decisions articles describe related mechanisms; the tool manifest declares whether the tool is `trusted-authoritative`, `trusted-verified`, `untrusted-external`, or `untrusted-unverified`, and the runtime uses this declaration as a starting point for the per-result trust tag. The runtime may downgrade based on validation results but never upgrades without explicit operator approval.

Detect and respond to trust anomalies. A tool that consistently produces results that are downgraded on validation is itself suspect. The runtime records the anomaly, may temporarily quarantine the tool, and notifies the operator. The quarantine is reversible once the tool's posture has been re-verified.

Trust-level flow is auditable. Every use of a tool result in a downstream decision is recorded with the result's trust level, the policy that determined the allowed use, and the validator that confirmed the result. The audit trail allows a post-hoc reviewer to reconstruct why a decision depended on a given tool result and what trust assumptions held at the time.

## Validation evidence

Conformance tests must cover: correct tagging of canonical tool responses at each trust level, monotonic downgrade through mixed-trust operations, refusal to use unverified content for durable decisions, sanitization of embedded instructions in `untrusted-external` results, detection of trust-level anomalies on a tool that misbehaves, and audit trail completeness for trust-flow reconstruction. Inject a tool response with embedded instructions and verify the agent sanitizes before use.

Operational evidence includes: distribution of tool results across trust levels, count of validation-driven downgrades, count of trust-flow policy violations detected, count of quarantined tools, and reviewer audit findings on trust-flow reconstruction. Reviewers should be able to trace any decision's trust posture back through the contributing tool results.

## Failure handling

When the runtime cannot determine a tool's declared trust posture (for example, when the tool manifest is missing or malformed), the runtime treats all results from that tool as `untrusted-unverified` until the manifest is corrected. The agent continues to operate but with the most conservative handling. The manifest gap is itself an alertable anomaly.

When validation of a `trusted-verified` result fails, the agent does not retry the tool call in the hope of obtaining a passing result on the next attempt. Retrying an untrusted tool is not a recovery; it is a denial-of-service risk. The agent downgrades the result and surfaces the validation failure for operator review.

When the agent's trust policy itself is inconsistent or out of date, the runtime applies a documented fail-safe policy. The default fail-safe is to treat all results as `untrusted-unverified`; this is conservative and ensures no decision is made under a misconfigured policy. The operator is notified and must update the policy before normal trust handling resumes.

When a tool result's trust tag is corrupted in transit (for example, when the tag itself is tampered with), the runtime treats the result as `untrusted-unverified` and surfaces a `trust-tag-tampered` event. The event includes the result hash so the operator can correlate with the producing tool.
