# Agent A2A Task ID Unguessability

In A2A, a task identifier is an authorization surface. If IDs are sequential integers or derivable from usernames or timestamps, any client that learns one valid ID can enumerate its way into other principals' task histories, artifacts, and subscription streams. Unguessability is therefore a property to engineer: identifiers generated with cryptographic randomness, scoped authorization that never relies on obscurity alone, and lifecycle rules that prevent reuse. This article covers generation, reference handling, and the leak paths that quietly defeat a strong ID scheme.

## Scope

Applies to A2A servers that mint task and context identifiers and to clients that store, reference, and transmit them. Covers identifier generation, uniqueness and reuse policy, reference leakage in logs and artifacts, and enumeration resistance. Does not cover the push-notification webhook security around task updates, nor authentication between client and server, both of which are prerequisites assumed present; an unguessable ID never substitutes for authentication.

## Workflow or implementation guidance

1. Generate identifiers from a cryptographic random source, not from counters, hashes of public inputs, or UUID variants with predictable bits. Prefer formats with at least 122 bits of randomness, such as version-4 UUIDs generated by a vetted library, or opaque base64url strings from a secure random generator. If your platform still emits version-1 UUIDs by default, replace the generator: the MAC-address and timestamp components make those IDs guessable in the sense that matters here.
2. Treat the identifier as an opaque token end to end. Clients and intermediaries must not parse meaning out of it, sort by it, or infer ordering from it; ordering belongs to server-issued timestamps and cursors, not to the ID itself.
3. Enforce uniqueness with a server-side collision check on insert, not by assumption. Even with ample randomness, a duplicate-ID insert must fail loudly rather than silently attach data to an existing task.
4. Prohibit reuse absolutely. A completed or canceled task's identifier is never reassigned, and identifiers retired with a task stay retired. Reuse turns old logs, cached references, and third-party stored pointers into confused-deputy hazards.
5. Authorize every access by principal, with the ID serving only as a lookup key. The authorization decision must answer "may this authenticated client see this task," never "did this client present a syntactically valid ID." Where a task is intentionally shared across clients, model that as an explicit grant with its own audit record.
6. Control reference leakage. Task IDs appear in URLs (query strings get logged by proxies), in artifacts and message parts, in tracing baggage, and in error messages. Prefer headers or bodies over URLs for identifiers, keep IDs out of user-facing error text, and treat any task ID embedded inside artifact content as data the recipient may forward, since artifacts routinely travel onward.
7. Bound enumeration surface in list and query operations: pagination with server-issued cursors, per-principal result ceilings, and detection rules for sequential-scanning patterns against the task endpoint family.
8. Define a retention and deletion path: expired tasks are purged, and their identifiers deleted with them. Long-tail retention of retired IDs increases the value of any future leak.

## Controls

- Generation policy pinned in code review: approved generators only, minimum entropy documented, and a lint rule that flags new identifier-creation paths using insecure primitives.
- Authorization tests mandatory for every new endpoint that accepts a task or context ID, including streaming subscription and push-notification configuration endpoints.
- Log scrubbing standard: task IDs may appear in internal audit logs but must be excluded from third-party analytics, referrer headers, and shared trace exports.
- Rate limits and lockout on repeated not-found responses from one client, the standard signature of enumeration probing.
- Periodic entropy audits: statistical checks on generated ID samples to confirm the deployed generator matches the approved one.

## Validation evidence

- Guessability assessment: sample a large batch of production-generated IDs and demonstrate the entropy source and format meet the documented floor; for version-4 UUIDs, show the version and variant bits are correct and the remaining bits pass randomness tests.
- Enumeration test: with two client principals, verify principal A cannot read, subscribe to, or cancel principal B's task even when A knows B's exact identifier, and that a wrong-owner access returns the same shape as a nonexistent-ID access to avoid an oracle.
- Reuse test: create, complete, and purge a task; confirm the identifier is never reissued across a long generation run.
- Leakage review: grep traces, artifacts, and exported logs for task IDs after a scripted multi-hop interaction, documenting every location found and the justification for it.

## Failure modes and correction

- A gateway or client "improves" IDs by sorting or re-encoding them, leaking generation order. Correction: contract states IDs are opaque; conformance tests reject transformations.
- Debug endpoints accept an ID without principal checks because "the IDs are unguessable anyway." Correction: threat-model review explicitly rejects obscurity as an authorization control; static analysis flags ID-parameterized handlers lacking authorization middleware.
- Task IDs land in URLs and get captured by proxy logs with longer retention than the tasks themselves. Correction: move identifiers to headers or bodies; where URL carriage is unavoidable, document the exposure and shorten retention on those logs.
- Shard rebalancing regenerates IDs for migrated tasks, breaking stored references and creating reuse-adjacent hazards. Correction: migration must preserve identifiers verbatim; tests assert ID stability across a reshard.

## Limitations

Unguessability only raises the cost of unauthorized access; it never replaces authentication and per-principal authorization. Random IDs lengthen and complicate debugging, tempting developers to add structure back in. Detection of enumeration is probabilistic and noisy behind shared egress addresses. And once an ID has been legitimately shared into an artifact or third-party system, its confidentiality depends on that system, not on your generation policy.
