# A2A Context and Task Identifier Semantics

## Purpose

A2A distinguishes conversational context from an individual stateful unit of work. `contextId` groups related messages and tasks, while `taskId` identifies one specific Task lifecycle. Treating them as interchangeable can cause broken multi-turn behavior or cross-task authorization mistakes.

## Context identifiers

An agent may generate a `contextId` when a message does not include one. If it generates a new identifier, the response must include it. A server may also accept a client-provided context identifier; if it cannot accept that value, it must reject the request rather than silently substitute a different context.

Clients should treat server-generated context identifiers as opaque values. Multiple tasks and messages can share one `contextId` as part of the same conversational context.

## Task identifiers

A `taskId` identifies one Task and is generated by the server when a new task is created. A client-supplied task identifier must reference an existing task; clients do not create new tasks by inventing a `taskId`.

When both identifiers are supplied, the referenced task and context must agree. A2A requires mismatching `contextId` and `taskId` combinations to be rejected.

## Practical controls

1. Store context and task identifiers as separate fields with separate lifecycle rules.
2. Treat both identifiers as opaque references, not as authorization credentials.
3. Authorize every task lookup or mutation independently of possession of a task identifier.
4. Reject a task/context pair when the task does not belong to the supplied context.
5. Avoid predictable identifiers where guessing could increase enumeration risk.
6. Apply explicit context-expiration and cleanup rules without reassigning old identifiers to new conversations.
7. Preserve identifiers consistently across polling, streaming, push notifications, and multi-turn messages.
8. Log identifier relationships for debugging without using them as substitutes for authenticated identity.
