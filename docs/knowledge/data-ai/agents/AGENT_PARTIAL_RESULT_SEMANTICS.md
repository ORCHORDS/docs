# Partial-Result Semantics for Agent Workflows

## Scope

An agent may complete some branches while others time out, fail validation, lose authorization, or get cancelled. Returning a polished aggregate without representing omissions can cause users or downstream systems to treat incomplete work as complete. This article defines a contract for partial results across fan-out, retrieval, and multi-step workflows. It complements artifact assembly and error boundaries but focuses on completeness claims and safe consumption.

HTTP status semantics distinguish successful representations from errors but do not by themselves describe a multi-source agent result. A2A task and artifact structures provide protocol envelopes, while NIST AI RMF emphasizes validity, reliability, transparency, and documented limitations. Applications must therefore encode partiality explicitly rather than relying on prose generated by a model.

## Workflow

1. Before execution, enumerate expected work units or define a reproducible rule for discovering them. Assign stable unit identifiers and state whether each is required or optional.
2. For each unit, track `pending`, `running`, `succeeded`, `failed`, `cancelled`, `expired`, or `not_attempted`. Keep the last states distinct; they imply different recovery choices.
3. Validate each successful unit independently and bind its output to source, contract revision, and completion time.
4. Aggregate only after applying a declared completion policy: all required units, quorum, best effort, or threshold. The policy is selected by the application, not improvised by the model.
5. Emit a machine-readable completeness block containing expected count if known, status counts, omitted unit identifiers or protected references, cutoff reason, coverage dimensions, and whether side effects occurred.
6. Label every derived conclusion with the units it used. A summary based on three of five sources cannot inherit an “all sources checked” claim.
7. Permit downstream actions only if their required completeness predicate is satisfied. Display may accept best effort while a financial or administrative action requires all mandatory units.
8. Support continuation with a new attempt linked to the original snapshot; never mutate historical partial output into apparent original success.

## Controls, data, and evidence

Define completeness policies alongside workflow specifications. Use deterministic reducers that preserve missingness; do not replace missing numeric values with zero or absent booleans with false. Keep unit status and aggregation metadata outside free-form model text. For privacy or authorization, unit identifiers may be opaque, but their count and required status should remain verifiable.

Evidence should include the workflow revision, discovery snapshot or rule, unit ledger, validation outcomes, aggregation policy, reducer revision, completeness predicate, final status, and continuation links. Metrics include partial-result rate, required-unit failure rate, age at cutoff, continuation success, and downstream rejection due to insufficient coverage. Review samples for misleading natural-language claims even when metadata is correct.

## Validation tests

Fail one required unit and verify an all-required aggregate cannot be marked complete. Fail an optional unit and verify the result states the omission without unnecessarily blocking an approved best-effort consumer. Cancel the parent while units are finishing; late outputs must be fenced or attached only under the continuation rules.

Test unknown total cardinality, duplicate unit completions, discovery that changes during execution, and units that succeed with invalid payloads. Verify a reducer does not divide by the expected count when only completed values are present unless that behavior is explicitly intended. Ask a downstream side-effect to consume a partial aggregate and confirm its completeness predicate blocks execution. Render the result in all supported interfaces and ensure the partial label and counts remain visible, including accessibility output.

## Failure handling

If the expected-unit ledger is lost, the system cannot establish completeness. Return an indeterminate partial result and prohibit consumers requiring full coverage. If aggregation fails after units succeed, preserve validated unit artifacts and rerun the reducer idempotently. A reducer error must not recast valid units as failed.

When a source becomes unauthorized during execution, mark its unit failed or cancelled according to the actual event and remove inaccessible payloads from the assembled view. Do not silently substitute cached data unless the workflow permits it and labels its age. If a user requests continuation, reauthorize every pending unit and revalidate assumptions that may have changed.

## Limitations

A complete set of units can still be wrong, biased, stale, or based on an incomplete discovery rule. Quorum policies may hide correlated failures. Precise omission details can reveal sensitive inventory, requiring opaque references. Partiality metadata may be lost when exported into formats without equivalent fields, so gateways must downgrade claims conservatively. The contract cannot stop an external consumer from ignoring completeness unless enforcement protects consequential actions.
