# A2A Direct Message and Task Response Semantics

## Purpose

A2A `SendMessage` does not always create a task. In v1.0, an agent can return either a `Task` that tracks ongoing or stateful work, or a direct `Message` for a simple interaction that does not require task tracking.

Clients must handle both outcomes explicitly. Treating every response as a task creates unnecessary state and polling; treating every response as a simple message loses lifecycle, artifacts, cancellation, and update semantics when a task is returned.

## SendMessage response union

The current A2A specification states that `SendMessage` returns one of:

- a `Task`, representing processing of the message; or
- a direct `Message`, for a simple interaction that does not require task tracking.

The response contains exactly one of those alternatives. Client code should model the response as a union rather than expecting a task field and silently ignoring a direct message.

## When a direct Message is appropriate

A direct response fits work that can be completed immediately without a durable unit of task state. Examples can include a simple lookup, short transformation, acknowledgement, or other interaction where the agent does not need asynchronous continuation.

The protocol does not require every short operation to use a direct message and does not define an application-specific threshold. Agents should choose consistently enough that clients can support either outcome without relying on timing guesses.

## When a Task is appropriate

A task gives the interaction:

- a server-generated task ID;
- a task state and status;
- optional history;
- output artifacts;
- cancellation semantics;
- polling, streaming, or push-update options; and
- the ability to continue task-specific interaction where the lifecycle allows it.

Long-running, interruptible, artifact-producing, asynchronous, or multi-step work commonly benefits from task tracking.

## Immediate return does not mean completion

`SendMessage` must return immediately with either a direct message or task information. When a task is returned, processing may continue asynchronously after the response.

A client must not interpret receipt of a `Task` object as proof that the work is complete. Inspect the task's current `TaskState` and use the supported update mechanism when additional progress is expected.

## Context semantics

A direct `Message` can still participate in conversational context. A2A uses `contextId` to group messages and tasks that belong to the same conversational context.

When processing a message without a `contextId`, an agent may generate one. If the server generates a new context ID, it must include it in the response, whether the response is a task or a direct message.

Clients should preserve the returned context ID when later interactions are intended to continue the same conversation.

## Direct response is not a hidden Task

When the agent returns a direct message, the client should not fabricate a local A2A task ID and later call `GetTask` against it. No protocol task exists unless the server returned one.

A client may create local UI state around a direct exchange, but that local state must remain distinct from A2A's task resource semantics.

## Task identifiers are server-generated

When a new task is created, the task ID is generated by the server. A client cannot create a new task by inventing a `taskId` in an outbound message.

If a client includes a task ID, it references an existing task. The agent must reject a non-existent task reference with the protocol's task-not-found behavior.

This distinction prevents clients from confusing conversational grouping with resource creation.

## Streaming behavior

`SendStreamingMessage` preserves the same initial choice between message and task but has different stream behavior.

The v1.0 specification defines two patterns:

1. **Message-only stream** — the stream contains exactly one `Message` and closes immediately. There is no task tracking or later task-update event.
2. **Task lifecycle stream** — the stream starts with a `Task`, then can deliver task-status and task-artifact update events, and closes when the task reaches a terminal state.

Clients should branch on the first response object instead of waiting for task events that will never arrive on a message-only stream.

## Client handling pattern

A robust client can use the following decision flow:

1. send the message using the selected protocol binding;
2. parse the union response;
3. if it is a `Message`, render or process it as the completed direct response;
4. preserve its `contextId` when future contextual interaction is expected;
5. if it is a `Task`, inspect its ID and current state;
6. choose polling, streaming, push notifications, or later retrieval according to capabilities and application needs; and
7. only perform task operations against a real returned task resource.

## User-interface implications

A UI should not force both response types into identical progress states.

For a direct message:

- display the response immediately;
- do not show a fake background-job spinner; and
- do not expose cancellation for a task that does not exist.

For a task:

- display its current status;
- show progress or interruption states where appropriate;
- allow supported cancellation or continuation; and
- fetch or render artifacts according to task state.

## Retry and idempotency considerations

Network failure can make it unclear whether a request reached the server. A2A allows agents to use the message's `messageId` for duplicate detection where `SendMessage` idempotency is implemented.

Clients should not assume a retry will necessarily return the same response form unless the agent's implementation and idempotency behavior support that guarantee. A duplicated logical request that accidentally creates a second task can cause double execution.

Preserve message IDs according to the client's retry policy and document server idempotency expectations.

## Error handling

Both response paths remain subject to A2A operation errors. A client should handle, among others:

- unsupported content types;
- inaccessible or non-existent referenced tasks;
- attempts to send messages to tasks in terminal states; and
- authentication or authorization failures.

Do not convert an error into a synthetic direct message that appears to be a successful agent response unless the application clearly distinguishes local error presentation from protocol data.

## Multi-turn interactions

A direct message can be part of a multi-turn conversation without a task. Subsequent messages may use the shared `contextId` to continue the conversational context.

A task-specific follow-up instead references the task ID, optionally with the context ID. If both are supplied, they must refer to the same context; the server must reject mismatched context and task identifiers.

This lets clients distinguish:

- continuing a conversation generally; from
- continuing or refining a specific stateful task.

## Agent design guidance

Agents should choose direct-message and task outcomes intentionally. Consider:

- whether durable server-side state is required;
- whether the work can outlive the request;
- whether artifacts will be produced;
- whether cancellation matters;
- whether input may be required later;
- whether clients need progress updates; and
- whether a simple response is sufficient.

Avoid creating tasks for every trivial exchange simply to produce a uniform internal implementation if doing so creates unnecessary persistence and lifecycle burden.

Likewise, avoid using direct messages for work whose ongoing state clients genuinely need to monitor or control.

## Interoperability tests

Test both response branches across every supported binding:

- direct `Message` from `SendMessage`;
- `Task` from `SendMessage` in a non-terminal state;
- completed `Task` returned immediately;
- message-only streaming response;
- task-lifecycle streaming response;
- server-generated `contextId` in both response types;
- retry behavior with repeated message IDs; and
- client behavior when an unexpected but valid branch is returned.

A client that has only been tested against agents that always return tasks is not fully implementing the response union.
