# pnpm patch: Vendor Dependency Workaround

Date: 2026-08-23 / Author: example.com / Status: production

---

## Symptom / Use-case

A third-party package in `node_modules` contains a bug that blocks your
Cloudflare Workers build: wrong type declarations, a broken ESM export, a
missing `exports` field, or a runtime crash in Miniflare's V8 isolate. Upstream
has not merged the fix and the next release is weeks away. You need a
reproducible, CI-safe patch that survives `pnpm install` without committing
`node_modules` to git.

---

## Context

`patch-package` was the npm-era solution. pnpm ships a first-class equivalent:
`pnpm patch` + `pnpm patch-commit`. Patches are stored as `.patch` files under
`patches/` at the workspace root and applied automatically by the pnpm post-
install lifecycle. No extra tool is needed.

In the example project monorepo (pnpm workspaces root at `/`) patches apply globally
to the workspace — a patch on `hono@4.3.1` affects every package that resolves
that version. Version pinning in `pnpm.patchedDependencies` ensures the patch
only applies to the exact version it was authored for, failing loudly if the
version drifts.

```
example project/
├── patches/
│   └── hono@4.3.1.patch      ← generated by pnpm
├── package.json               ← pnpm.patchedDependencies entry here
└── pnpm-workspace.yaml
```

## Step 1 — Create the editable copy

```bash
# From workspace root
pnpm patch hono@4.3.1
```

pnpm copies the package to a temp directory and prints:

```
You can now edit the following folder: /tmp/a1b2c3/user/hono@4.3.1

Once you are done with your changes, run:

  pnpm patch-commit '/tmp/a1b2c3/user/hono@4.3.1'
```

Open the temp directory and apply your fix:

```bash
# Example: fix a broken ESM condition in dist/index.mjs
sed -i 's/typeof globalThis.crypto/typeof (globalThis.crypto ?? {})/g' \
  /tmp/a1b2c3/user/hono@4.3.1/dist/index.mjs
```

Or edit files directly in your editor:

```bash
code /tmp/a1b2c3/user/hono@4.3.1/dist/index.mjs
```

---

## Step 2 — Commit the patch

```bash
pnpm patch-commit '/tmp/a1b2c3/user/hono@4.3.1'
```

pnpm diffs the temp directory against the original, writes
`patches/hono@4.3.1.patch`, and updates `package.json`:

```json
{
  "pnpm": {
    "patchedDependencies": {
      "hono@4.3.1": "patches/hono@4.3.1.patch"
    }
  }
}
```

Commit both files:

```bash
git add patches/hono@4.3.1.patch package.json
git commit -m "fix(deps): patch hono@4.3.1 crypto shim for Miniflare V8"
```

---

## Step 3 — Verify the patch applies on clean install

```bash
rm -rf node_modules
pnpm install
# pnpm prints: "Applying patch: patches/hono@4.3.1.patch"

# Confirm the fix is present
grep -n 'globalThis.crypto ?? {}' \
  node_modules/hono/dist/index.mjs
```

## Patching TypeScript declaration files

Types-only patches are common when a package ships incorrect `.d.ts` files.

```bash
pnpm patch @cloudflare/workers-types@4.20240208.0
# Edit the .d.ts in the temp dir
# Then:
pnpm patch-commit '/tmp/.../user/@cloudflare/workers-types@4.20240208.0'
```

The resulting patch applies to `.d.ts` files only — no runtime risk.

---

## Patching a hoisted vs non-hoisted dependency

In pnpm's default `node-linker=isolated` mode, each package version is stored
once under `.pnpm/`. The patch applies to that single store entry. In hoisted
mode (`node-linker=hoisted`), the same behaviour holds.

Check which linker is active:

```bash
pnpm config get node-linker
# → isolated  (default for new pnpm workspaces)
```

For Cloudflare Workers packages you should be on `isolated` to match the
Worker's module resolution.

## Updating or removing a patch

**Update**: re-run `pnpm patch <pkg>@<version>` and `pnpm patch-commit` again.
The old `.patch` file is replaced.

**Remove**:

```bash
rm patches/hono@4.3.1.patch
# Edit package.json, delete the patchedDependencies entry for hono@4.3.1
pnpm install  # applies remaining patches, skips deleted one
```

## CI integration (GitHub Actions)

The `pnpm install` step applies patches automatically. No extra step required
as long as `patches/` is committed to git and `pnpm-lock.yaml` is up-to-date.

```yaml
# .github/workflows/ci.yml
- name: Install dependencies
  run: pnpm install --frozen-lockfile
  # pnpm will print "Applying patch: patches/hono@4.3.1.patch" here

- name: Build Workers
  run: pnpm turbo run build
```

If the patch fails to apply (e.g. upstream changed the patched lines and you
upgraded the package), pnpm exits non-zero with a descriptive error:

```
 ERROR  Could not apply patch patches/hono@4.3.1.patch to hono@4.3.1
```

This is intentional: a failed patch is a signal to review and re-author it.

## Patching packages that use postinstall scripts

Some packages run a `postinstall` script that regenerates files your patch
targets. pnpm applies patches *after* `postinstall`, so your changes survive
the generated output. If `postinstall` runs on every `pnpm install` and
regenerates the file you patched, the patch will fail on the second install.

Workaround: patch the generator script (e.g. `scripts/build.js`) instead of
the generated output, or disable the package's postinstall:

```json
{
  "pnpm": {
    "patchedDependencies": {
      "some-generator@1.0.0": "patches/some-generator@1.0.0.patch"
    },
    "neverBuiltDependencies": ["some-generator"]
  }
}
```

## Anti-patterns

- **Committing `node_modules/`** — not scalable, causes massive diffs, breaks
  pnpm's content-addressable store.
- **Using `patch-package` (npm) alongside `pnpm patch`** — the two systems
  conflict. Pick one. In a pnpm workspace always use `pnpm patch`.
- **Patching without pinning the exact version** — a minor upgrade silently
  skips the patch. The `pnpm.patchedDependencies` key *must* include the full
  semver string (`hono@4.3.1`, not `hono`).
- **Forgetting to commit `pnpm-lock.yaml`** after adding a patch — the
  lockfile records the patch checksum. Without it, `--frozen-lockfile` fails
  on CI.
- **Patching very large generated bundles** — diffs on minified files are
  fragile and hard to review. Request an upstream fix or use a `resolution`
  override to pin a fork instead.

---

## Gotchas

- pnpm stores a checksum of the patch in `pnpm-lock.yaml`. If you edit
  `patches/hono@4.3.1.patch` manually without running `pnpm install` the
  lockfile checksum is stale and `--frozen-lockfile` will reject it.
- `pnpm patch` does NOT support patching packages installed from `git:` or
  `file:` specifiers — only registry packages.
- The temp directory path printed by `pnpm patch` changes on every invocation.
  Do not hardcode it in scripts; always capture it from the command output.
- Patches for `@scope/package@version` are stored as
  `patches/@scope__package@version.patch` (the `/` is replaced with `__`).
- If you pin a fork via `pnpm.overrides`, you cannot also patch the original
  package version with `pnpm.patchedDependencies`. Choose one mechanism.

## Verification

```bash
# 1. Clean install applies patch
rm -rf node_modules && pnpm install 2>&1 | grep "Applying patch"

# 2. Patched lines present at runtime
node -e "
  const mod = require('hono/dist/index.js');
  console.log('patch ok:', true);
"

# 3. Lockfile records patch hash (manual check)
grep -A3 'patchedDependencies' pnpm-lock.yaml

# 4. CI smoke test — add to your CI pipeline assertion
pnpm vitest run --reporter=dot packages/api
```
