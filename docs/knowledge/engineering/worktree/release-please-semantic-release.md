# release-please-semantic-release

**Issue:** A team releases a library weekly. The release process is: developer remembers to bump version, updates CHANGELOG.md by hand, runs `npm version`, runs `npm publish`, creates a GitHub release. The team forgets the changelog; the version is wrong; the publish fails.
**Date:** 2026-08-10
**Repo:** example-org/example-repo
**Author:** ORCHORDS
**Status:** published

## Symptom

Manual releases are error-prone. The team wants versioning and changelogs automated from commit history, but the choice between "fully automated" and "human-approved" determines which tool fits.

## Root cause

Three release automation tools dominate the npm ecosystem in 2026:

- **semantic-release** — fully automated. Push commits; it versions, tags, publishes.
- **release-please** (Google) — PR-gated. Opens a release PR; merging publishes.
- **Changesets** — explicit changelog entries. Per-PR file declares the change.

All three rely on Conventional Commits to derive version bumps. The difference is the human gate.

## The Conventional Commits foundation

All three tools read the commit history to determine the next version. The Angular commit convention:

| Commit type | SemVer impact | Example |
|---|---|---|
| `fix:` | PATCH (0.0.x) | Backward-compatible bug fix |
| `feat:` | MINOR (0.x.0) | New, backward-compatible feature |
| `feat!:` or `BREAKING CHANGE:` in footer | MAJOR (x.0.0) | Incompatible API change |
| `docs:`, `chore:`, `style:`, `refactor:` | None | No release |

The team commits with accurate types; the tool figures out the version.

## semantic-release — fully automated

semantic-release is the most widely adopted (23,000+ stars, 130,000+ dependents). The premise: if your commits follow the convention, the machine determines whether the next release is patch, minor, or major. No human decision required.

It runs through a plugin pipeline: verify conditions, analyze commits, generate notes, create a git tag, prepare, publish, notify. Each step can be handled by a different plugin.

```yaml
# .github/workflows/release.yml
name: Release
on:
  push:
    branches: [main]
jobs:
  release:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
        with:
          fetch-depth: 0
      - uses: googleapis/release-please-action@v4
        with:
          release-type: node
          package-name: my-package
      # OR for semantic-release:
      # - uses: cycjimmy/semantic-release-action@v4
      #   env:
      #     GITHUB_TOKEN: ${{ secrets.GITHUB_TOKEN }}
      #     NPM_TOKEN: ${{ secrets.NPM_TOKEN }}
```

**Best for:** fully autonomous pipelines, single-package repos, teams that trust the commit convention.

**Worst for:** teams that want to review what ships; the human gate is the entire point of release-please.

## release-please — PR-gated (Google's choice)

release-please is the open-source tool Google built for their own projects. It maintains a "Release PR" — a living PR that contains the version bump, the changelog, and any language-specific file changes (package.json, pyproject.toml, pom.xml, etc.). Merging the PR triggers the publish.

```yaml
# .github/workflows/release-please.yml
name: release-please
on:
  push:
    branches: [main]
jobs:
  release-please:
    runs-on: ubuntu-latest
    steps:
      - uses: googleapis/release-please-action@v4
        with:
          release-type: node
          package-name: my-package
```

On every push to main, release-please scans commits since the last release. If it finds releasable changes (`feat:`, `fix:`), it opens or updates a release PR. The PR contains:

- Version bump in `package.json`
- Generated `CHANGELOG.md`
- Any ecosystem-specific file changes (Python `pyproject.toml`, Java `pom.xml`, Go `go.mod`, etc.)

When you merge the PR, release-please creates the git tag, drafts the GitHub Release, and publishes to the registry (npm, PyPI, etc.).

If no releasable commits have landed, release-please does nothing. No PR, no release.

**Best for:** reviewed, batched releases; teams that want a human gate; multi-language repos (it supports 20+ ecosystems: Node, Python, Java, Go, Rust, Ruby, PHP, Helm, Terraform).

**Worst for:** teams that want zero-touch automation; the PR is overhead.

## Changesets — explicit changelog entries

Changesets takes a different approach. Instead of deriving version info from commits, it asks developers to explicitly declare what changed and how it should be released:

```bash
npx changeset
# ? Which packages would you like to include? my-package
# ? What kind of change is this? minor
# ? Summary of the change: Add new API endpoint for user preferences
```

A `.changeset/some-id.md` file is committed alongside the change. The release PR is generated by aggregating all `.changeset/*.md` files.

**Best for:** monorepos with multiple independently-versioned packages; teams that want explicit human-written changelog entries.

**Worst for:** single-package repos where the commit history is sufficient.

## The decision matrix

| Tool | Release trigger | Human gate | Monorepo | Multi-language | Cost |
|---|---|---|---|---|---|
| semantic-release | Auto on push to main | None by default | Limited | Yes (plugins) | Free |
| release-please | Merge the release PR | Yes (PR review) | Excellent (20+ ecosystems, manifest config) | Excellent | Free |
| Changesets | Merge the changeset PR | Yes (PR review) | Excellent (per-package versioning) | Limited (JS/TS) | Free |

## The squash-merge prerequisite

For any of these tools to work cleanly, the team must use **squash merges** (linear history) for PRs. With merge commits, the commit history on `main` contains merge artifacts that confuse the version-derivation logic. With squash, each PR becomes a single commit on `main`, and the commit message is the PR title and body.

Configure in the GitHub repository settings: "Allow squash merging" → "Default to squash merge."

## The first-release initialization

release-please will not trigger if there is nothing to release. For the first release:

```bash
git commit --allow-empty -m "chore: release 0.0.1
Release-As: 0.0.1"
```

This sets the initial version. Subsequent releases are incremented from there.

For semantic-release, the first release is triggered by the first commit with `feat:` or `fix:`. There is no `0.0.1` initialization.

## The verification pattern

After a release:

1. The git tag is created (e.g., `v1.4.2`)
2. `CHANGELOG.md` is updated
3. The GitHub Release is drafted with the changelog as body
4. The package is published to the registry
5. CI on the tag passes (a separate job tests the published version)

The team should never need to run `npm version`, edit `CHANGELOG.md`, or run `npm publish` by hand after the initial setup. If they do, the automation is misconfigured.

## Verification

The tell that release automation is working:

- Merging a `feat:` PR triggers a new minor version (or, for release-please, opens a release PR)
- `CHANGELOG.md` is generated, not hand-edited
- The team can answer "what shipped in v1.4.2?" by looking at the GitHub Release
- A `BREAKING CHANGE:` commit triggers a major version bump automatically
- Squash merges are the default for the repo

The tell it isn't:

- The team runs `npm version` by hand
- `CHANGELOG.md` is updated in the same PR as the feature
- A `BREAKING CHANGE:` ships as a minor version
- Two engineers bump the version at the same time and conflict

## Gotchas

- **Squash merges are required.** Without them, the commit history on main contains merge artifacts that break version derivation.
- **The first release needs an initialization commit.** `Release-As: 0.0.1` for release-please; first releasable commit for semantic-release.
- **Commit messages must be accurate.** A `feat:` that should have been a `fix:` triggers a minor version instead of a patch.
- **`BREAKING CHANGE:` must be in the footer or the type must be `feat!:`.** A commit with `feat:` and a `BREAKING CHANGE:` body line is ambiguous to some parsers.
- **release-please does nothing if no releasable commits have landed.** Don't panic when no PR appears — it means there's nothing to release.
- **Plugin configuration matters for semantic-release.** The `@semantic-release/npm`, `@semantic-release/github`, `@semantic-release/changelog` plugins are nearly always required.
