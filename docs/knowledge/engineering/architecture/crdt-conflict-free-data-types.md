# crdt-conflict-free-data-types

**Issue:** When multiple replicas of the same data can accept writes independently — collaborative editors, offline-first mobile apps, multi-region configurations, chat presence — someone must decide what happens when replicas disagree. Traditional answers (locks, consensus per edit, last-writer-wins) either serialize users behind network round trips or silently destroy concurrent edits. Conflict-free Replicated Data Types (CRDTs, Shapiro et al. 2011) solve this mathematically: data structures whose merge operation is commutative, associative, and idempotent, so any replica that receives any set of updates, in any order, possibly with duplicates, converges to the same state without coordination. By 2025-2026 CRDTs are the default engine inside collaborative editing stacks (Yjs, Automerge, newer entrants like cola) and local-first sync engines, and the FOSDEM 2026 local-first track is dedicated to this ecosystem. But CRDTs are not free: metadata growth, non-intuitive merge semantics, garbage collection of tombstones, and real production retractions (Cinapse publicly moved away from Automerge in 2025) mean architects must choose the right CRDT family — or conclude that a simpler sync engine suffices.

## The Two Families

1. **State-based (CvRDT).** Replicas periodically broadcast their full state; merge is a join over a semilattice — take the union/pointwise-max and the result only grows. Simple, tolerant of message loss and duplication, but payloads grow with state unless delta-CRDT techniques (shipping only recent changes) are used. Anti-entropy gossip systems (anti-entropy-gossip-replication) are state-based CRDT thinking applied to whole datasets.
2. **Operation-based (CmRDT).** Replicas broadcast individual operations; merge is applying every operation exactly-once in causal order. Payloads are tiny, but the transport must provide reliable causal broadcast — the kind of guarantee that adds its own complexity. Text-editing CRDTs (Yjs's YATA, Automerge's RGA lineage, cola) are operation-based with clever position identifiers so concurrent inserts interleave deterministically.
3. **Convergence theorem.** Both families rest on the same proof: if merge is commutative, associative, and idempotent (or operations are commutative given causal delivery), then all replicas that have received the same set of updates hold equal state — regardless of arrival order or duplication. This is why CRDTs pair naturally with at-least-once delivery (see at-least-once-delivery): no exactly-once machinery needed.

## The Standard Toolbox

1. **Counters.** G-Counter (grow-only: per-replica counters, merged by max/sum) and PN-Counter (two G-Counters, increments minus decrements) are the hello-world of CRDTs — DynamoDB-style distributed counters and real-time vote/like counters are typically PN-Counters under the hood.
2. **Registers and sets.** LWW-Register (last-writer-wins with a timestamp or hybrid clock — see hybrid-logical-clocks) loses concurrent writes by design; MV-Register keeps concurrent values as siblings for the application to resolve (Dynamo-style). Sets graduate from G-Set (add-only) through 2P-Set (adds plus a remove tombstone set) to OR-Set (observed-remove: elements tagged with unique add-tags, remove only kills observed tags), which is the usable one for real applications.
3. **Sequences and maps.** Sequence/list CRDTs (RGA, YATA, LSEQ) are the hard-won core of collaborative text: each inserted character carries an immutable position identifier so concurrent inserts at the same point converge to the same order everywhere. Map CRDTs compose per-key registers/sets. JSON CRDTs (Automerge) nest maps, lists, and scalars into one document — convenient, but the reason metadata can balloon.
4. **Version vectors as the bookkeeping.** Operation-based CRDTs track which replica has seen which operations with per-replica counters — version vectors, not vector clocks (see vector-clocks-vs-version-vectors). This metadata is what enables tombstone GC: once every replica has seen a delete, the tombstone can be dropped.

## Costs and Failure Modes

1. **Metadata growth and tombstone GC.** Every character in a text CRDT can carry a multi-byte unique ID; deleted elements linger as tombstones until all replicas have acknowledged the delete. Offline-forever replicas block GC forever, so production systems either cap vector clocks, compress identifiers (Yjs's integer IDs plus client clocks), or run periodic snapshotting — same discipline as event-sourcing-snapshots.
2. **Semantics that surprise users.** Concurrently edited text interleaves both users' characters; concurrent deletes both succeed; a counter cannot go below its merged baseline. CRDTs guarantee convergence, not that the converged state is what any user expected. Product owners must review merge behavior on paper for their nastiest concurrent case before committing.
3. **Not a database replacement.** CRDTs give eventual consistency for the *data they model*; they do not give transactions, secondary indexes, or ad-hoc queries across documents. The 2025 Cinapse/PowerSync post-mortem genre exists precisely because teams tried to make a JSON CRDT document do a database's job and hit performance and query-modeling walls — they moved the sync problem to a sync engine over a conventional database.
4. **Security surface.** Malicious or buggy clients can inflate documents (billions of no-op inserts) since merges must accept anything well-formed. Server-side relay/validation layers and document-size limits are standard hardening for open-collaboration systems.

## Where CRDTs Fit (and Where Not)

1. **Strong fit: collaborative editing and presence.** Multi-cursor documents, shared whiteboards, multiplayer game state, cursor/selection sharing. Yjs/Automerge-class libraries dominate here, and 2025 surveys (Velt's CRDT library guide) treat them as the default; the Eg-walker research line shows the performance frontier still moving — running the CRDT only for concurrent-edit merging.
2. **Strong fit: offline-first and local-first apps.** Devices that edit local replicas and sync opportunistically cannot demand a coordination round per keystroke. CRDTs plus a sync/relay server is the canonical local-first architecture showcased across the FOSDEM 2026 local-first track.
3. **Moderate fit: multi-region hot configuration.** Feature flags, routing tables, rate-limit buckets that must be writable in every region without cross-region locks: LWW or PN-Counter CRDTs with anti-entropy dissemination fit well (the Riak/Cassandra config lineage).
4. **Weak fit: strongly-consistent business state.** Balances, inventory at flash-sale precision, unique username allocation — anything needing read-modify-write linearizability. Use a consensus-backed store; if you must mix (CRDT presence beside transactional state), draw the boundary explicitly and let the transactional side own invariants.
5. **Decision heuristic.** If users concurrently mutate the same entities and can tolerate last-write-losing merging rules, or if connectivity is intermittent by design, evaluate a CRDT library first. If the real requirement is "cache replicas of a server database," a read-path sync engine is cheaper and simpler — the lesson the 2025 migration stories teach.
