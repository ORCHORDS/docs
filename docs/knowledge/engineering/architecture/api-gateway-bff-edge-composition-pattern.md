# Api Gateway Bff Edge Composition Pattern

## Scope

This article addresses the engineering design decision that arises when an organization wants to expose many internal services through a single, optimised surface per client channel. It covers the Backend for Frontend (BFF) pattern, the conventional API gateway pattern, and the emerging composition pattern in which a worker or edge function aggregates calls on behalf of mobile, web, partner, or device clients. The intent is to define when to use each, how the responsibilities differ, and what the runtime topology looks like when an edge tier is involved. The discussion is project-neutral and applies to any stack that can host an HTTP intermediary: Java, Go, Node.js, Cloudflare Workers, or a managed gateway product. It does not prescribe a specific gateway vendor or framework.

## Workflow or implementation guidance

The composition pattern layers three roles. The first layer is the protocol gateway, which terminates TLS, performs authentication, applies coarse rate limits, and forwards the request to a stable internal address space. The second layer is the BFF, a service that is shaped to one client channel: it speaks the language and cadence that a mobile app, a web SPA, or a partner system expects. The third layer is the edge composition tier, which fans out to internal services and stitches responses, sometimes caching parts of them, often performing per-channel shape transforms. In Cloudflare Workers the BFF and the edge composition tier frequently collapse into one Worker that calls downstream services through service bindings, returning a tailored response.

The first step is to enumerate the channels the system serves and the request shapes each channel actually needs. Mobile clients often want a single, denormalized payload; web clients can tolerate multiple round trips but care about cacheability; partner systems want stable, documented contracts. Each channel tends to favour a different BFF because trying to serve them all from one endpoint produces either over-fetching for mobile or under-fetching for web. The second step is to identify cross-cutting concerns that belong in the gateway rather than in the BFF: rate limits, authentication, schema validation, audit logging, request tracing, and TLS termination are gateway concerns. The third step is to decide whether the BFF should call upstream services directly or compose through the gateway; in practice the BFF almost always calls the internal services directly because it shares trust boundaries with them.

A typical implementation separates concerns at the handler level. The edge or BFF Worker receives a request, validates an access token, opens per-request context (correlation ID, user claims, channel identifier), and then performs parallel subrequests to the upstream services using `Promise.all` or `ctx.waitUntil` in Workers. The responses are combined in memory and returned in a channel-specific shape. Where latency matters, the BFF can choose to short-circuit by returning a cached fragment for part of the response, leaving the rest freshly fetched. Error handling must be deliberate: a failure of one subrequest should not always cascade; some endpoints should degrade to a partial response with a structured "stale" or "unavailable" section so that the client UI can still render something useful.

When a system already has a strong API gateway, the BFF is often a small Worker deployed alongside it. The gateway handles authentication and edge policy; the BFF handles shape transformation and aggregation. When a system runs directly at the edge without a traditional gateway, the BFF takes on gateway duties itself, including token introspection, which can be acceptable for low-risk APIs but should not be the default posture.

## Controls

Controls for the composition pattern are split between the gateway and the BFF. Gateway controls include TLS termination, IP allow-listing, schema-based rate limiting, and centralized audit logging. BFF controls include per-channel response shaping, per-channel caching policies, per-channel error handling, and downstream timeout configuration. Edge composition tiers should expose correlation IDs in headers and propagate them into every downstream call so that traces can be reconstructed even after fan-out. Authentication must be checked at the boundary, never trusted from upstream; a Worker that reads a header set by an upstream is no longer authenticating, it is forwarding.

Configuration changes to the BFF must be versioned and reviewed because they affect what clients see. Any change in response shape is effectively a contract change and must follow the same discipline as any public API: versioning, deprecation windows, and changelog entries. Rate limits applied at the BFF should be at least as strict as at the gateway, and ideally tighter, because the BFF has more context about the client channel and the cost of the downstream calls it is about to make.

## Validation evidence

Validation is the easiest part of this pattern to under-invest in, and the easiest part to get wrong. The composition tier must have synthetic checks that verify each channel's contract, not just that the BFF returns 200. A scheduled test should call the BFF with a representative client payload, validate the response shape against the channel schema, and assert that each fragment is either present, deliberately absent, or marked stale. Latency budgets must be measured per channel because mobile and web will have different acceptable tail latencies; the test should fail if p95 exceeds the budget for a sustained period. Cache hit rate and partial-cache hit rate should be tracked separately because the latter is what actually protects downstream services during traffic spikes.

Trace sampling must cover enough of the cross-service calls to make root-causing tractable. A composition tier that fans out to five services and shows only its own span in a trace is operationally blind. Distributed tracing with OpenTelemetry or a comparable system should propagate trace context through every subrequest, and the BFF span should be marked with attributes describing the channel, the version of the BFF, and the cache state of each fragment.

## Failure modes and correction

The most common failure is over-fetching: a single BFF endpoint returns every field any client might want because different clients ask for different shapes. The cure is to split the BFF endpoints so that each endpoint corresponds to a deliberate client use case. A second failure is over-posting: the BFF accepts writes from many channels and forwards them upstream, blurring ownership of validation. The cure is to keep the BFF strictly read-side for aggregation and to put any write path behind a normal API with full server-side validation. A third failure is unbounded fan-out: the composition tier issues too many subrequests in parallel and exhausts connections or downstream capacity. The cure is to budget the fan-out, parallelise only what is safe to parallelise, and apply bulkhead isolation between the BFF and each upstream.

A fourth failure is silent partial failure: the BFF returns a 200 with empty fragments because one upstream timed out and the handler swallowed the error. The cure is to fail loudly in observability and either return a partial response with explicit "unavailable" markers or fail the whole request with a structured error code. A fifth failure is the gateway doing the BFF's job: the gateway starts returning channel-specific shapes and slowly becomes a giant per-channel switchboard. The cure is to keep the gateway protocol-only and move all shaping downstream.

## Limitations

The composition pattern adds operational surface area: another deployable, another cache to monitor, another place where schemas live. It pays off when the channel count is high or when the cost of cross-service round trips is meaningful; it does not pay off when a single client makes a small number of well-shaped calls. It also assumes that the internal services behind the BFF are stable enough to compose; if every upstream is itself rapidly changing, the BFF becomes a coupling point and accumulates breaking-change debt. Finally, an edge composition tier cannot compensate for an upstream that is fundamentally slow; it can hide one slow call behind another fast call for a short window, but latency budgets will eventually catch up.
