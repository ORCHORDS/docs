# Saga Pattern Choreography vs Orchestration

## Scope

This article covers the choice between the two saga coordination styles for multi-service business transactions: choreography, where services react to each other's events with no central coordinator, and orchestration, where a dedicated orchestrator issues commands and tracks progress. Scope covers the decision criteria, failure handling differences between the styles, testability and observability consequences, and migration between styles. It presumes the saga concept and compensating transactions generally; it does not re-cover compensation pair design, which has its own article, and it excludes distributed two-phase commit as an alternative.

## Workflow or implementation guidance

Make the choice per business transaction, not per system. Choreography suits transactions with few steps (three or fewer participants), no branching logic, and stable semantics — the failure of adding a participant is adding a subscription, and the flow reads as a set of local reactions. Orchestration suits anything with branching, timeouts, human-in-the-loop steps, retry policy that differs per step, or more than a handful of participants — wherever the phrase "what happens next depends on" appears more than twice, a central definition of what happens next is cheaper than distributing it across event handlers.

Choreography's discipline is event design. Each participant publishes business facts (`OrderPlaced`, `PaymentCaptured`) and subscribes to others' facts; no participant emits commands aimed at another participant, because command-style events quietly re-create orchestration with none of its explicitness. Local transactional state tracks what this participant has already done, with idempotent handlers keyed on event id since at-least-once delivery guarantees duplicates. A minimal shape:

```ts
on('OrderPlaced', async (e) => {
  if (await alreadyProcessed(e.id)) return;      // idempotency under at-least-once
  await reserveStock(e.orderId);
  await publish('StockReserved', { orderId: e.orderId, eventId: newId() });
});
```

Orchestration's discipline is state machine definition. The orchestrator declares steps, decisions, timeouts, and compensations in one reviewable artifact, persists its progress per saga instance, and commands participants through request-reply or command messages. Participants stay dumb and reusable — they expose operations, not opinions about the flow — which is the property that lets the flow evolve without touching every service.

Whichever style, define failure handling per step before shipping: retry with backoff for transient faults, compensation for business rejections, and an escalation state (dead-letter with alert) for both styles' version of "cannot proceed." In choreography, failure handling must also be choreographed — each participant decides locally whether to emit a failure fact — and that decision surface is exactly where implicit flows become unmanageable. Track saga progress explicitly in both styles: correlation ids propagated through every message, plus per-instance state records, because reconstructing "where is this order stuck" from scattered logs is the failure mode that pushes teams to orchestration.

## Controls

In choreography, control drift with a flow registry: every event type, its publisher, and its subscribers catalogued with owners, plus a periodically generated dependency graph of who reacts to whom — an edge that appears in the graph but not the registry is an undocumented dependency. Bound fan-out by policy: a participant subscribing to more than a few event types is usually accreting flow logic and should be reviewed. In orchestration, control the definition artifact: saga definitions are versioned, reviewed like schemas, and carry explicit declarations of each step's compensability and timeout. Concurrency caps per saga type prevent orchestrator stampedes when a downstream degrades. For both styles, require end-to-end tracing ids in every message and a saga-instance lookup API — being able to answer "what state is this instance in, and what is it waiting for" is an operational control, not a convenience. Alert on saga age: a saga running past its declared timeout ceiling is stuck, and stuck sagas hold business-level commitments (reserved stock, held payments) that cost money while invisible.

## Validation evidence

For choreography, the decisive evidence is an end-to-end flow test per transaction type: drive the initiating event through a real broker with real subscribers and assert the terminal state and the complete set of published events, in order per aggregate. Because no component knows the whole flow, only a test can assert the whole flow still exists after a refactor. Fault-injection at each participant: make one subscriber fail, then reject, then stall, and assert the choreographed outcome (compensating events or failure facts) matches the documented failure design — undocumented gaps appear here first. For orchestration, state machine coverage: for each definition, tests drive every declared transition including timeout paths, compensation paths, and the escalation state, asserting persisted state at each step. Resume evidence: kill the orchestrator mid-instance, restart, and assert continuation from persisted state without re-executing completed steps. Comparative evidence when choosing or migrating: instrument both candidate implementations with the same metrics — saga completion rate, median and p99 duration, compensation rate, stuck-saga count — and run a shadow period where the new style executes alongside the old on sampled traffic, comparing outcomes instance by instance. Observability evidence: for a sampled production window, verify every saga instance is answerable by lookup, since unanswerable instances are where support escalations originate.

## Failure modes and correction

Choreography's signature failure is the mystery flow: enough participants and events that nobody can enumerate the possible paths, debugging becomes log archaeology across services, and changes break distant subscribers nobody contacted. Correct with the flow registry, the dependency graph, and by migrating transactions that exceed a complexity threshold to orchestration rather than adding a third reaction layer. The second is cyclic reaction: A reacts to B, B reacts to A's reaction, and an unmodeled loop runs until rate limits stop it. Correct with per-instance processed-event markers that break cycles and a flow-level review of new subscriptions for feedback edges. Orchestration's signature failure is the god orchestrator: business logic migrates into the coordinator until every participating service is a CRUD shell and the orchestrator is a monolith with extra network hops. Correct by keeping the orchestrator to sequencing, timeouts, and compensation dispatch, with decisions residing in participants. The second is orchestrator state loss: progress held in memory dies with the process, and sagas restart from zero or hang. Correct with transactional persistence per step. Both styles share the dual-write failure: emitting messages outside a transactional outbox so crashes lose them. Correct with outbox writes for every publish. A third shared failure is idempotency gaps under at-least-once redelivery — handlers that assume exactly-once and double-execute on retry. Correct with event-id keyed idempotency in every handler, verified by deliberate duplicate-injection tests.

## Limitations

Neither style provides isolation: intermediate states are externally visible, and customers can observe partial transactions regardless of coordination style. Choreography scales poorly with participant count and branching — its natural ceiling is reached quickly, and the migration to orchestration is a rewrite of every participant's reaction logic, so the pattern choice should anticipate growth honestly rather than optimistically. Orchestration concentrates flow logic in one component that becomes a change bottleneck and a coupling point every service negotiates with, and its persisted state store is new critical infrastructure. Both styles demand idempotency and compensation discipline in every participant forever, and a single non-compliant service degrades the whole transaction's guarantees. Testing is inherently integration-shaped: unit tests cannot exercise multi-service flows, so the valuable tests are slow and brittle against real brokers. Human-driven steps (approvals) stretch durations arbitrarily in both styles, requiring timeout semantics neither style supplies by default. Finally, the choice is often as much organizational as technical — transaction boundaries that cross team ownership argue for orchestration's explicit contracts, while co-located teams can sustain choreography's implicit understandings longer — and reorganizations can invalidate a technically sound choice.
