# ISO/IEC/IEEE 15288:2015 System Life Cycle Processes Governance

## Purpose

ISO/IEC/IEEE 15288:2015 establishes a comprehensive set of processes for system life cycle activities. Governance ensures that an organization adopts the processes appropriate to its system context, that systems and software processes are integrated, and that process assessment is applied to drive improvement.

## Current context and source status

ISO/IEC/IEEE 15288 was published in 2015 as a joint standard, replacing the 2008 edition. The standard is closely aligned with ISO/IEC/IEEE 12207 (software life cycle processes) and uses the same four process groups. Verify the current edition before treating any clause identifier as a current requirement.

## Governance workflow and controls

### 1. Apply the four process groups

Apply the four process groups:

- agreement processes;
- organization project-enabling processes;
- technical management processes;
- technical processes.

Use the same process structure as ISO/IEC/IEEE 12207 but with system-specific emphasis.

### 2. Apply system-specific processes

Apply system-specific processes including:

- system requirements definition;
- architecture definition;
- system analysis;
- system integration;
- system verification;
- system validation;
- system transition;
- system operation;
- system maintenance;
- system disposal.

### 3. Integrate with software processes

Integrate the system processes with software processes (ISO/IEC/IEEE 12207). Identify handoffs and shared artifacts.

### 4. Apply system-of-interest and system-of-systems

Apply the standard to system-of-interest and, where applicable, to system-of-systems contexts. Document the system context.

### 5. Tailor processes

Tailor processes per project. Document the tailoring rationale. Reuse tailoring patterns where possible.

### 6. Apply process assessment

Apply ISO/IEC 33001 process assessment to evaluate process capability. Use the results for improvement.

### 7. Train staff

Train staff on the chosen processes. Tailor training by role.

## Validation and evidence

- Process adoption documentation.
- Tailoring rationale per project.
- Process assessment reports.
- Integration with software processes.

## Failure correction

Common defects include processes that don't reflect system scope, missing integration with software processes, and assessment without improvement. Corrective actions include a scope review, an integration plan, and an assessment-improvement linkage.

## Limitations

- The standard is comprehensive; full adoption is resource-intensive.
- System-of-systems contexts add complexity.
- Tailoring is necessary for agile projects.
- Process assessment is separate from project work.
