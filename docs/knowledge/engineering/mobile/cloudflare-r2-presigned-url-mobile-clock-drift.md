# Cloudflare R2 Presigned URL Expiry Failures Due to Mobile Clock Drift

- **Date**: 2026-08-22
- **Author**: example.com
- **Status**: active

## Symptom / Use-case

example project users upload profile photos and post attachments via R2 presigned URLs generated by
a Cloudflare Worker. Desktop uploads succeed reliably. A subset of mobile users — consistently
Android devices, occasionally older iPhones — receive HTTP 403 "Request has expired" errors
when attempting to PUT to the presigned URL, even within 30 seconds of the Worker generating
it. The 403 occurs most often after the app has been backgrounded and foregrounded, or
immediately after a network switch from Wi-Fi to cellular. Retrying with a fresh presigned URL
always succeeds.

## Context

R2 presigned URLs use AWS Signature Version 4 (SigV4), inherited from the S3-compatible API.
The signature includes a timestamp (`X-Amz-Date`) and a validity window (`X-Amz-Expires`).
R2 validates the signature against the request arrival time using a **±15-minute clock skew
tolerance** — this sounds generous, but mobile devices accumulate clock drift in specific
scenarios:

1. **Android doze mode and clock synchronisation**: When an Android device enters Doze mode,
   NTP synchronisation is suspended. Devices in Doze for 6+ hours can drift 30–60 seconds.
   After the user wakes the device and opens example project, the device clock may be ahead of true
   UTC by 30–90 seconds. This is within R2's tolerance window, but…

2. **The Worker generates the presigned URL using `Date.now()` from the Worker's runtime
   clock**, which is accurate (Workers run on Cloudflare infrastructure synced to GPS/NTP).
   The presigned URL's `X-Amz-Date` is set to the Worker's current UTC time. When the mobile
   client receives this URL, it uses the URL as-is — the timestamp is baked in. R2 then
   validates the request arrival time against the `X-Amz-Date` + `X-Amz-Expires` window.

3. **The critical issue is not clock drift on the signing side, but on the network transit
   side**: If the presigned URL is generated with `X-Amz-Expires=300` (5 minutes), and the
   mobile device takes 4 minutes to upload (poor cellular connection), the URL may expire
   mid-upload if the connection stalls. R2 does not support resumable uploads via presigned
   URLs — there is no `uploadId` equivalent. A stalled upload that resumes after expiry fails
   the entire PUT.

4. **iOS background upload task timing**: When a React Native app sends the upload to an
   `NSURLSession` background task, iOS may delay the upload until the app is in the foreground
   or the device is on Wi-Fi. If the app is backgrounded immediately after triggering the
   upload, the actual PUT request may arrive at R2 minutes later — past the presigned URL
   expiry.

5. **Android clock manipulation by users**: A non-trivial fraction of example project's adult-anonymous
   audience uses modified Android builds (custom ROMs, rooted devices). Some have NTP disabled
   or set their clocks manually. If a user's clock is 20+ minutes ahead, the presigned URL's
   `X-Amz-Date` (set to accurate Worker time) will appear to R2 as a future-dated request
   that has not yet become valid, AND when the user uploads, R2 may see the request as
   arriving before the valid-from time.

## Section 1 — Generating Mobile-Safe Presigned URLs in Workers

The R2 presigned URL must be generated via the `aws4fetch` library or equivalent, since
Cloudflare's `env.R2_BUCKET` binding does not natively expose a presign method.

```typescript
// workers/upload/presign.ts
import { AwsClient } from 'aws4fetch';

const R2_ENDPOINT = `https://${ACCOUNT_ID}.r2.cloudflarestorage.com`;

export async function generatePresignedUploadUrl(
  env: Env,
  key: string,
  request: Request
): Promise<{ url: string; expiresAt: number }> {
  const isMobileClient = isMobile(request);

  // Mobile-safe expiry: shorter for Android/iOS to avoid background-task stale URLs
  // but long enough to allow for poor upload speeds on cellular
  const EXPIRY_SECONDS = isMobileClient ? 900 : 3600; // 15 min mobile, 1 hr desktop

  const client = new AwsClient({
    accessKeyId: env.R2_ACCESS_KEY_ID,
    secretAccessKey: env.R2_SECRET_ACCESS_KEY,
    region: 'auto',
    service: 's3',
  });

  const url = new URL(`${R2_ENDPOINT}/${env.R2_BUCKET_NAME}/${encodeURIComponent(key)}`);

  // Generate the presigned URL
  const signed = await client.sign(
    new Request(url.toString(), { method: 'PUT' }),
    {
      aws: {
        signQuery: true, // presigned URL (not header-signed)
        datetime: undefined, // use current time from Worker runtime (accurate)
        expiresIn: EXPIRY_SECONDS,
      },
    }
  );

  const expiresAt = Date.now() + EXPIRY_SECONDS * 1000;

  return {
    url: signed.url,
    expiresAt, // Return expiry time to the client so it can check before uploading
  };
}

function isMobile(request: Request): boolean {
  const deviceType = request.headers.get('cf-device-type');
  if (deviceType) return deviceType !== 'desktop';
  const ua = request.headers.get('user-agent') ?? '';
  return /okhttp|CFNetwork|Expo|ReactNative/i.test(ua);
}
```

```typescript
// workers/upload/route.ts — the presign endpoint
export async function handlePresignRequest(
  request: Request,
  env: Env
): Promise<Response> {
  const { key, contentType, fileSize } = await request.json() as {
    key: string;
    contentType: string;
    fileSize: number;
  };

  // Validate file size upfront — mobile uploads > 50 MB via presigned URL are unreliable
  const MAX_MOBILE_UPLOAD_BYTES = 50 * 1024 * 1024; // 50 MB
  if (isMobile(request) && fileSize > MAX_MOBILE_UPLOAD_BYTES) {
    return new Response(
      JSON.stringify({ error: 'File too large for mobile upload. Max 50 MB.' }),
      { status: 413, headers: { 'Content-Type': 'application/json' } }
    );
  }

  const { url, expiresAt } = await generatePresignedUploadUrl(env, key, request);

  return new Response(
    JSON.stringify({ uploadUrl: url, expiresAt, key }),
    { headers: { 'Content-Type': 'application/json' } }
  );
}
```

## Section 2 — React Native Upload with Expiry Guard

```typescript
// src/api/upload.ts — React Native upload with clock-drift and expiry awareness
import { Platform } from 'react-native';
import * as FileSystem from 'expo-file-system';

interface PresignedUpload {
  uploadUrl: string;
  expiresAt: number; // Unix timestamp ms — from the Worker's accurate clock
  key: string;
}

const EXPIRY_SAFETY_MARGIN_MS = 60_000; // Refresh URL if less than 60s remain

export async function uploadFileToR2(
  fileUri: string,
  contentType: string,
  fileSize: number,
  token: string
): Promise<string> {
  let presigned = await fetchPresignedUrl(fileUri, contentType, fileSize, token);

  // Check if presigned URL might expire before the upload completes
  // Estimate upload time based on file size and conservative 500 kbps mobile bandwidth
  const CONSERVATIVE_MOBILE_BANDWIDTH_BPS = 500_000 / 8; // 500 kbps in bytes/s
  const estimatedUploadSeconds = fileSize / CONSERVATIVE_MOBILE_BANDWIDTH_BPS;
  const estimatedCompletionMs = Date.now() + estimatedUploadSeconds * 1000;

  if (estimatedCompletionMs > presigned.expiresAt - EXPIRY_SAFETY_MARGIN_MS) {
    console.warn(
      `Upload may expire during transfer. File: ${fileSize} bytes, ` +
      `est. ${estimatedUploadSeconds.toFixed(0)}s, URL expires in ` +
      `${((presigned.expiresAt - Date.now()) / 1000).toFixed(0)}s. Requesting fresh URL.`
    );
    // Request a fresh URL — let the server know we need extended expiry
    presigned = await fetchPresignedUrl(fileUri, contentType, fileSize, token, true);
  }

  if (Platform.OS === 'android' || Platform.OS === 'ios') {
    // Use Expo FileSystem for the actual PUT — handles large files, progress events,
    // and does NOT go through the JSI bridge (avoids memory pressure from large buffers)
    const result = await FileSystem.uploadAsync(presigned.uploadUrl, fileUri, {
      httpMethod: 'PUT',
      headers: {
        'Content-Type': contentType,
        // DO NOT include 'Content-Length' manually — FileSystem sets it from the file
      },
      uploadType: FileSystem.FileSystemUploadType.BINARY_CONTENT,
    });

    if (result.status !== 200) {
      if (result.status === 403) {
        const body = result.body;
        if (body.includes('Request has expired')) {
          throw new Error('UPLOAD_URL_EXPIRED');
        }
        throw new Error(`UPLOAD_FORBIDDEN: ${body}`);
      }
      throw new Error(`UPLOAD_FAILED: HTTP ${result.status}`);
    }
  }

  return presigned.key;
}

async function fetchPresignedUrl(
  fileUri: string,
  contentType: string,
  fileSize: number,
  token: string,
  extendedExpiry = false
): Promise<PresignedUpload> {
  const response = await fetch('https://api.example.com/upload/presign', {
    method: 'POST',
    headers: {
      'Authorization': `Bearer ${token}`,
      'Content-Type': 'application/json',
    },
    body: JSON.stringify({
      key: `uploads/${Date.now()}-${Math.random().toString(36).slice(2)}`,
      contentType,
      fileSize,
      extendedExpiry, // Hint to server: give us a longer expiry window
    }),
  });
  if (!response.ok) throw new Error(`Presign failed: ${response.status}`);
  return response.json();
}
```

## Section 3 — Handling Mid-Upload Expiry and Retry

```typescript
// src/api/upload.ts — retry wrapper for expired presigned URLs
export async function uploadWithRetry(
  fileUri: string,
  contentType: string,
  fileSize: number,
  token: string,
  maxAttempts = 3
): Promise<string> {
  for (let attempt = 1; attempt <= maxAttempts; attempt++) {
    try {
      return await uploadFileToR2(fileUri, contentType, fileSize, token);
    } catch (err) {
      const message = err instanceof Error ? err.message : String(err);

      if (message === 'UPLOAD_URL_EXPIRED' && attempt < maxAttempts) {
        console.log(`Upload URL expired on attempt ${attempt}. Refreshing and retrying...`);
        // Wait briefly — the device may be in a network handoff causing the slowness
        await new Promise(resolve => setTimeout(resolve, 1000 * attempt));
        continue;
      }

      throw err; // Non-retryable error or max attempts reached
    }
  }
  throw new Error('Upload failed after maximum retries');
}
```

## Section 4 — iOS Background Upload Handling

iOS background uploads are managed by `NSURLSession` background tasks, which can delay the
actual network PUT until conditions are met (Wi-Fi, device plugged in, etc.). This creates
a timing gap between presigned URL generation and the actual upload:

```typescript
// For Capacitor / Expo on iOS, avoid background upload tasks for time-sensitive presigned URLs.
// Instead, use foreground upload only and prompt the user to keep the app open.

// capacitor.config.ts
import { CapacitorConfig } from '@capacitor/cli';

const config: CapacitorConfig = {
  appId: 'app.example project.example project',
  appName: 'example project',
  // DO NOT enable backgrounding for upload tasks — presigned URL will expire
  // Use shorter foreground uploads with progress feedback instead
  ios: {
    allowsLinkPreview: false,
    // Background fetch and background transfer are intentionally disabled
    // to prevent presigned URL expiry during deferred uploads
  },
};

export default config;
```

## Anti-patterns

- **Setting `X-Amz-Expires` to a very short value (< 60 s) for "security"**: On mobile with
  slow connections or network handoffs, 60 s is not enough time to complete the PUT. Use
  300–900 s (5–15 min) for mobile and rely on the key structure to limit abuse.
- **Not returning `expiresAt` to the client**: Without a server-provided expiry timestamp,
  the client cannot check whether the presigned URL is still valid before attempting the upload.
  Always return `expiresAt` as a Unix timestamp in milliseconds from the Worker.
- **Using device `Date.now()` to check expiry on the client**: Mobile device clocks drift.
  For expiry checks, trust the server-provided `expiresAt` (from the Worker's accurate clock)
  and add your own safety margin — do not compare server time against device time.
- **Sending R2 uploads through a Worker proxy instead of direct presigned URL**: Proxying
  through a Worker adds the Worker's 6 MB response body limit and 30 s CPU limit to the upload
  path. Use presigned direct-to-R2 URLs for all file uploads.
- **Using `fetch` (not `FileSystem.uploadAsync`) for large file uploads on RN**: Standard `fetch`
  reads the file into a JS-side buffer before sending, causing memory pressure on large files
  and potential bridge timeout on files > 10 MB.

## Gotchas

- **R2 presigned URLs are path-scoped, not bucket-scoped.** A URL for `uploads/foo.jpg`
  cannot be used to upload to `uploads/bar.jpg`. Generate one URL per file, per upload.
- **R2 SigV4 signature is sensitive to the Content-Type header.** If the client sends a
  different `Content-Type` than what was used to sign the URL, R2 returns 403 "Signature
  does not match". For mobile, always include `contentType` in the presign request and match
  it in the PUT.
- **Cloudflare R2's ±15-minute clock skew tolerance is NOT the same as the expiry window.**
  These are independent: a 300 s presigned URL that was generated 14 minutes ago (within
  the skew window) is still valid if the request arrives within 5 minutes of generation.
  But if the device clock is 16 minutes ahead, the request signature may fail even if the
  presigned URL has not technically expired.
- **`expo-file-system` `uploadAsync` does not support upload progress on iOS < 16.** Use
  a custom `NSURLSession` plugin or accept the lack of progress reporting on older iOS.
- **R2 presigned URLs do not support multipart upload.** For files > 200 MB, use the R2
  S3-compatible multipart API with separate presigned URLs per part — not the standard
  presigned PUT workflow.
