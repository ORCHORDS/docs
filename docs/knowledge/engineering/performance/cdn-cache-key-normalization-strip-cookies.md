# Cdn Cache Key Normalization Strip Cookies

## Scope
This article addresses the engineering decisions around CDN cache key construction when the default behaviour would key on the entire request, including cookies, query strings, and authorization headers. The scope covers how Cloudflare and similar CDNs compute the cache key, how stripping cookies and query parameters broadens the key so more requests share a cached response, the correctness implications of doing so, and the failure modes that arise when cookies actually do carry content-affecting information. The article is restricted to read paths and the HTTP semantics of cacheability; it does not cover write paths, origin authentication, or the legal implications of mixing user data in shared caches.

## Workflow or implementation guidance
Begin by establishing a clear policy on which request inputs affect the response. For a public marketing page, the response is identical regardless of the user; for a personalised page, the response depends on the user's identity, cart, or location. The CDN cache key should include only the inputs that affect the response: any other input is noise that fragments the cache into N variants where one would do. Map each request input (cookies, query strings, headers) to a binary "affects-response" flag, and use that map to drive the cache key normalization.

Implement cookie stripping at the edge as a `Cache Rules` action in Cloudflare, or as a Workers `fetch` handler that rewrites the request before it reaches the cache. The pattern is to clone the inbound request, drop the `Cookie` header on the clone, and use the clone as the cache lookup key. The original request is still forwarded to the origin (or to a Worker that handles personalisation separately), but the cache itself never sees the cookie value, so the same response is served to all users who share the same path, query parameters, and accept headers.

Strip query parameters selectively. The default behaviour in most CDNs is to key on the full query string; this fragments the cache into one entry per unique query. For pages where the query string is presentational (`utm_source`, `utm_campaign`), the response is identical regardless of the value, so the query string should be stripped from the cache key. For pages where the query string is functional (`?id=123`, `?lang=fr`), the query string must be preserved. Implement an allowlist or denylist of query parameters; Cloudflare's `Cache Rules` supports a "Query String" inclusion list that retains only the listed parameters in the key.

Strip authorization headers by default. The `Authorization` header is a strong signal that the response is private; if a cache ever keys on it and serves the cached response to a different user, the response will leak data. Most CDNs refuse to cache responses with `Authorization` by default; verify this in the platform's documentation and add a Worker pre-check that returns a 401 or a private response if `Authorization` is present on what should be a public path.

Normalize the cache key on the `Vary` header. If the origin returns `Vary: Accept-Encoding`, the cache key should include the request's `Accept-Encoding` value so gzip and brotli variants are stored separately; if the origin returns `Vary: *`, the response is uncacheable. Verify that the origin's `Vary` headers are intentional: a stray `Vary: User-Agent` will fragment the cache into one entry per user-agent string, which on a mobile site can mean thousands of variants per URL.

Where personalization is required, separate the cacheable shell from the uncacheable user data. The shell (HTML structure, CSS, JS, hero image) is served from cache; the user data (name, cart count, location-specific pricing) is fetched in a second request from a personalisation API. The two responses are combined client-side, and the user's session cookie never touches the cache. This pattern requires that the shell contain placeholders for the user data and that the personalisation API return quickly enough not to delay LCP.

Finally, monitor cache hit rate per route. A hit rate below 50% on a route that should be cacheable indicates the key is too broad (cookies are leaking into the key) or the key is too narrow (the response depends on inputs that have not been normalised). Adjust the key construction rules until the hit rate matches expectations.

## Controls
Define three categories of control. The first is **variant enumeration**: list all the request inputs that the cache key includes, and confirm each one is necessary. Cloudflare's `Cache Rules` UI exposes the computed key per request via the `CF-Cache-Key` debug header. The second is a **response consistency check**: for a small set of canonical requests with stripped cookies, verify that the response is byte-identical to the response when cookies are present. If the response differs, the origin is using a cookie value somewhere, and stripping will cause incorrect responses to be served from cache. The third is a **leak detector**: a small fraction of requests are issued with a synthetic cookie containing a known marker, and the response is checked for the marker; if the marker is present in a cached response served to a different user, the cookie is leaking into the cache key.

A useful guardrail metric is the **cache hit ratio per route**, broken down by query string length and cookie presence. A long tail of low-hit-rate entries indicates fragmentation; a flat hit-rate distribution across cookie-present and cookie-absent requests indicates the stripping is working as designed.

## Validation evidence
The validation evidence is a controlled A/B test on the cache configuration: route a fraction of traffic through the new key normalization rules and compare cache hit rate, origin request volume, and TTFB. The expected outcome is a substantial increase in hit rate (often 2–10× for routes with high cookie cardinality), a corresponding drop in origin traffic, and a measurable reduction in TTFB on cache hits. Run the test for at least one full business cycle to capture day-of-week and campaign-driven traffic patterns. Document the per-route hit rate before and after, the byte size of the average cached response, and the number of unique cache keys per route.

## Failure modes and correction
**Cookies leak into the cache key**: the strip rule is configured but a different code path is bypassing it. Correction: audit every cache lookup, ensure each one goes through the same normalized key, and add a debug header to surface the computed key on responses. **Origin response varies on a stripped input**: the origin is reading a cookie that should not affect the response. Correction: identify the cookie-using code path and remove it, or move the cookie-dependent rendering to a separate uncached endpoint. **Cache fragmentation from query parameters**: the query string contains functional parameters that legitimately vary the response, but unrelated tracking parameters are bloating the key. Correction: configure an explicit allowlist of functional parameters in the cache key rules; tracking parameters are dropped. **Stale personalisation served from cache**: the shell is cached and includes user-specific data that should be personalisation. Correction: move the user data out of the shell and into a separate API call; the shell must contain only data that is identical for all users. **Vary: User-Agent fragments cache on mobile**: the origin returns `Vary: User-Agent` and the CDN keys on it. Correction: remove `Vary: User-Agent` from the origin response if the response is genuinely device-agnostic, or split the response into separate routes per device class and key the cache on the route, not the user-agent string.

## Limitations
The article assumes a CDN whose cache key is configurable at the edge (Cloudflare, Fastly, Akamai). Some CDNs do not expose the key construction, and the only way to broaden hits is via origin configuration. The article assumes the response is genuinely identical for users with different cookies; in practice, A/B tests often use cookies for variant assignment, and stripping them removes the variant signal from the cache key. The article does not cover signed URLs, which are an alternative to cookie-based personalization for cacheable content. The article is restricted to HTTP caches; it does not address browser cache, service worker cache, or in-process caches.
