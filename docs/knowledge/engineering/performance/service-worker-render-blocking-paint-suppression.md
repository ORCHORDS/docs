# Service Worker Render Blocking Paint Suppression

## Scope
This article addresses the paint-blocking and render-suppression behaviour that a service worker can cause on first navigation, the mechanism behind it, and the engineering patterns that keep a service worker from delaying first paint instead of accelerating it. The scope covers the W3C Service Workers specification's request interception model, the navigation preload mechanism, the `install`/`activate` lifecycle, the HTML parser's dependency on the navigation response, and the failure modes that turn a performance optimisation into a first-paint regression. The article is restricted to the first navigation of a page controlled by a service worker; it does not cover offline strategy design, cache versioning hygiene, or push notifications. It is concerned with the question: under what conditions does a service worker sit between the browser's navigation request and the HTML response, how long can that interception take before it delays paint, and how is the delay removed.

## Workflow or implementation guidance
Begin by understanding where the delay comes from. On a navigation to a controlled page, the browser dispatches the request to the service worker before it can receive any HTML. The service worker's `fetch` handler runs, and if it responds from a cache the response is available immediately; if it calls `fetch()` against the network, the response is available when the network answers; and if the handler does anything else first—parsing a manifest, opening multiple caches, awaiting a storage read—the navigation waits for all of it. The HTML response gates everything downstream: the parser cannot start, no subresource can be discovered, and first paint is suppressed until the service worker responds. A handler that adds 300 ms of its own work before responding adds 300 ms to every paint on that navigation.

Keep the navigation path short and static. The `fetch` handler should decide the navigation response with the minimum number of `await`s: a single `caches.match` for a precached shell, or a single `fetch` with a cached fallback wired through `event.respondWith` in parallel rather than in series. Do not open caches inside the handler; hold the `Cache` objects in module scope from the install step. Do not read configuration from IndexedDB on the navigation path. Every `await` that is not strictly required to produce the response bytes is latency added to first paint.

Use `event.respondWith` once, immediately, with a promise that races the network against the cache where a race is the right strategy, and never with a promise chain that resolves only after several sequential storage operations. The `respondWith` call itself is what unblocks the navigation; the sooner it is called, the sooner the browser can begin the response. Calling it late—after logging, analytics, or an `await`—delays the navigation by exactly that amount.

Enable navigation preload. Navigation preload issues the network request for the navigation in parallel with the service worker's startup, so the worker's script download and initialisation do not serialise ahead of the HTML fetch. The worker receives the preloaded response via `event.preloadResponse` and can use it directly as the network answer. The feature requires advertising `NavigationPreload` in the `activate` handler and handling `event.preloadResponse` in `fetch`; with both in place, the worker's own startup cost is largely hidden from the navigation.

Minimise the worker's script size and initialisation cost. The worker's `evaluate` and top-level execution happen before any `fetch` handler can run. A large bundle, or a top-level `await` on a slow operation, delays the first intercepted navigation. Split the worker into a small entry script that installs the fetch handler immediately and lazily imports strategy code inside the handler (or off the critical path), so that top-level work is O(1) with respect to the application's size.

Warm the worker deliberately. The first navigation after registration pays the worker's startup; subsequent navigations on a live worker do not. A Worker that keeps itself alive (periodic background sync, a keep-alive fetch on a timer) trades memory and battery for startup latency. The better pattern is to accept the startup cost on the first navigation and use navigation preload to hide it, rather than to fight the browser's worker lifecycle.

Measure the interception cost directly. The Performance API exposes the service worker's contribution in the navigation timing entries: compare `PerformanceResourceTiming` for controlled and uncontrolled navigations of the same template, and use `performance.getEntriesByType('navigation')`'s activation and fetch timing to attribute the gap. In the lab, test with the service worker unregistered, registered-and-idle, and cold-starting, and compare first paint across the three states; the delta between the last two is the interception cost.

For render suppression specifically, understand that the browser suppresses paint while the navigation response is pending: the user sees the previous page (or a blank frame) until the service worker responds. Any long `await` inside the handler manifests as a blank frame, which users perceive as a slower page even when total load time is unchanged. The fix is always the same: produce response bytes earlier, and move everything that does not contribute bytes off the critical path.

## Controls
Define three categories of control. The first is a **navigation-path budget**: a code-review rule (enforced by lint or by review convention) that the navigation branch of the `fetch` handler performs at most one storage read and no IndexedDB access. The second is a **preload-enablement check**: a synthetic test confirms `NavigationPreload` is enabled and `event.preloadResponse` is consumed, so a regression in either surfaces as a failed check. The third is a **controlled-vs-uncontrolled paint split**: RUM data compares first-paint distributions for controlled and uncontrolled sessions of the same templates; a controlled-session regression indicates interception cost.

A useful guardrail metric is the **interception delta**: the difference in navigation-to-first-paint time between controlled and uncontrolled sessions. A positive delta above roughly 50 ms indicates the worker is on the critical path and the handler needs shortening.

## Validation evidence
The validation evidence is a three-state lab comparison: unregistered, warm worker, cold worker, all on the same page templates under throttled network and CPU profiles, reporting time to first byte, first contentful paint, and largest contentful paint for each state. The expected outcome is that a warm worker with navigation preload matches or beats the unregistered baseline, and that the cold-worker state's penalty is bounded by the preload response time rather than by the worker's startup. In production, confirm with the RUM controlled/uncontrolled split that the delta is near zero or negative. Document the worker's script size, the number of `await`s on the navigation branch, the preload enablement, and the measured deltas.

## Failure modes and correction
**Sequential awaits before responding**: the handler opens a cache, reads a manifest, then fetches, and each step adds latency to paint. Correction: hoist cache handles to module scope, collapse the branch to one storage read, and call `respondWith` with a racing promise. **Navigation preload not enabled**: the worker's startup serialises ahead of the HTML fetch. Correction: enable `NavigationPreload` in `activate` and consume `event.preloadResponse` in `fetch`, and handle the preload header on the server so the origin can send a lighter response. **Large worker bundle**: top-level evaluation of a big script delays the first interception. Correction: split the entry script, lazy-import strategy code inside the handler, and remove build-time polyfills from the worker's critical path. **Blank frame perceived as slowness**: the worker responds from the cache but only after a storage read, and the user sees a blank frame in between. Correction: precache the shell so the read is a single-key lookup, and consider serving the shell from a build-time snapshot that requires no runtime assembly. **Stale shell served after deploy**: the cached shell is old and the worker's activation logic defers cleanup, so users see the previous release's markup. Correction: version the caches, clean up old caches in `activate`, and use a network-first strategy for the navigation with the cache as a fallback rather than the reverse.

## Limitations
Behaviour differs across browser engines, and the service worker startup cost in particular varies with implementation; measure on the browsers that matter to the audience. The article does not cover the `Streams`-based response assembly pattern in depth, nor the interaction with bfcache, which has its own rules about restoring pages with active service workers. Navigation preload is not available in all engines at the time of writing; the pattern degrades to the unpreloaded path. The article assumes HTTPS-scope prerequisites for registration and does not cover the install-time caching strategy, which affects availability rather than navigation latency.
