# Decompression Cost Brotli Vs Zstd Comparison

## Scope
This article addresses the comparative decompression cost of Brotli (RFC 7932) and Zstandard (RFC 8478) as it applies to client-side web workloads, the trade-offs between compression ratio and CPU cost on the receiving browser, and the engineering patterns that pick the right algorithm for a given content type and user population. The scope covers the static dictionary mode in Brotli, the dictionary-training mode in Zstandard, the content-encoding negotiation over HTTP, and the measurable impact on Time to First Byte, First Contentful Paint, and INP. The article is restricted to client-side decompression on browser-class hardware; it does not cover server-side compression throughput, archival compression, or video/image codecs. It is concerned with the question: given a content type (HTML, CSS, JavaScript, JSON, font) and a user population (desktop, mid-tier mobile, low-end mobile), which algorithm delivers the best perceived performance, and what is the engineering cost of switching between them.

## Workflow or implementation guidance
Begin by establishing the baseline compression metrics for each content type. Brotli at level 11 (the maximum) compresses text 15–25% better than gzip at level 9, but the compression CPU cost is 5–10× higher; the decompression cost on the client is roughly comparable between Brotli level 1 and gzip. Zstandard at level 3 compresses text within a few percent of Brotli level 6 while decompressing 2–3× faster than Brotli; at level 19 (the maximum) the compression ratio is comparable to Brotli level 11 with similar CPU cost. The trade-off is: Brotli level 11 gives the smallest wire size; Zstandard level 3 gives the fastest client-side decompression.

For static assets (CSS, JavaScript, fonts) pre-compressed at build time, use the highest compression level available. The CPU cost is paid once at build time, and the client benefits from the smallest possible transfer. Brotli level 11 is the conventional choice; Zstandard level 19 is a viable alternative if the build pipeline can produce Zstandard dictionaries from the corpus.

For dynamic content (HTML, JSON API responses) compressed on-the-fly at request time, use a moderate compression level. The CPU cost is paid per request on the server, and the client only needs to decompress the bytes it receives. Brotli level 4–6 is the conventional choice for dynamic content; Zstandard level 3 is faster on both ends. The trade-off is the wire size: Brotli at level 4 produces larger payloads than Zstandard at level 3 in most cases, but the difference is small (typically 5–10%).

Negotiate the algorithm via the `Accept-Encoding` request header. The client advertises the algorithms it supports in priority order; the server picks the first one it can produce. Configure the CDN or origin to honour the client's preference, not the server's default. Modern browsers advertise `gzip, deflate, br`; servers that support Zstandard should advertise `zstd` ahead of `br` for clients that support it, since Zstandard decompresses faster on most hardware.

For Zstandard, consider dictionary training. A trained dictionary captures the repeated patterns in a corpus (e.g., a JavaScript bundle) and allows much higher compression at lower CPU cost than the default dictionary. Train the dictionary from a representative corpus and serve the dictionary to clients that support it; the dictionary is small (a few kilobytes) and amortises over many requests. The dictionary must be served with the response and the `content-encoding: zstd` header must reference the dictionary.

For Brotli, use the static dictionary mode for assets where the server has a pre-built dictionary (most static asset CDNs do not, but custom origins can). The static dictionary is built into the format and is available to all clients without a separate dictionary fetch.

Measure the end-to-end impact on user-facing metrics. The decompression CPU cost on low-end mobile devices can be measurable: a 200-KB Brotli-compressed JavaScript bundle takes 30–50 ms to decompress on a 4-year-old Android phone; the same bundle in Zstandard takes 15–25 ms. The difference shows up in INP and in the time to interactive. Use Real User Monitoring to measure the impact in production; do not rely on synthetic benchmarks from desktop hardware.

For content that is already compressed (JPEG, PNG, WebP, AVIF, MP4, WebM), do not apply Brotli or Zstandard on top. The compression algorithms cannot reduce the size of an already-compressed payload, and the CPU cost of attempting to compress and decompress is pure waste. Configure the CDN or origin to skip compression for `Content-Type` values that indicate already-compressed content.

## Controls
Define three categories of control. The first is an **algorithm coverage audit**: for representative content types, confirm that the CDN or origin serves the expected `Content-Encoding` based on the client's `Accept-Encoding`. The second is a **payload size regression alert**: track the wire size of representative assets per compression algorithm; an unexpected rise indicates the compression level has been changed or the asset has changed. The third is a **client-side CPU monitor**: where possible, measure the decompression time on representative client hardware (via RUM or via a controlled test on a low-end device) and alert when the decompression time exceeds the budget.

A useful guardrail metric is the **compression ratio per content type**: the wire size divided by the uncompressed size, tracked over time. A sudden drop in ratio indicates the content has changed (e.g., a new bundler output is less compressible) and may require re-tuning the compression level.

## Validation evidence
The validation evidence is a controlled comparison of wire size and client-side decompression time across Brotli levels, Zstandard levels, and gzip baselines. Measure on representative content types (HTML, CSS, JS, JSON, font) and on representative client hardware (desktop, mid-tier mobile, low-end mobile). The expected outcome is that Brotli level 11 produces the smallest wire size but the highest client-side decompression cost; Zstandard level 3 produces slightly larger payloads but 2–3× faster decompression; gzip level 9 produces the largest payloads but is universally supported. Document the per-content-type wire size, the per-client decompression time, and the user-facing INP impact.

## Failure modes and correction
**Client does not advertise the algorithm**: the client sends `Accept-Encoding: gzip, deflate` and the server serves gzip, even though the client supports Brotli. Correction: verify the client's `Accept-Encoding` header includes the algorithm; some proxies strip the header. **CDN serves wrong algorithm**: the CDN is configured to serve gzip regardless of `Accept-Encoding`. Correction: enable the per-algorithm content-encoding feature in the CDN configuration; verify with `curl -H "Accept-Encoding: br"`. **Decompression CPU spike on low-end devices**: a large Brotli-compressed payload overwhelms the client CPU and delays INP. Correction: switch to Zstandard at level 3, or split the payload into smaller chunks that decompress in parallel. **Compression CPU spike on the origin**: the origin is compressing dynamic content at level 11 and the CPU cost is unsustainable. Correction: lower the level to 4–6 for dynamic content; keep level 11 for static assets compressed at build time. **Already-compressed content is re-compressed**: a JPEG is wrapped in Brotli and the wire size is larger than the original. Correction: configure the CDN to skip compression for image MIME types.

## Limitations
The article assumes modern browsers (Chrome 109+, Firefox 121+, Safari 16+) that support Zstandard content-encoding. Older browsers fall back to Brotli or gzip; the algorithm choice may need to vary per user agent. The article assumes the server has CPU headroom for compression; if the origin is CPU-bound, even moderate compression levels are expensive. The article does not cover streaming compression, where the wire size cannot be known in advance and dynamic content must be compressed in chunks. The article does not cover the operational mechanics of dictionary distribution for Zstandard, which requires careful cache-control configuration.
