# Wasm Module Streaming Compile Perf

## Scope
This article addresses the streaming compilation of WebAssembly modules, the practice of compiling a module while its bytes are still downloading rather than after the download completes, and the engineering patterns that make the technique deliver its full latency benefit. The scope covers the WebAssembly specification's compilation model, the `WebAssembly.compileStreaming` and `WebAssembly.instantiateStreaming` APIs, the required content type and CORS constraints, the interaction with HTTP response streaming and compression, the size and tiering characteristics of V8-style engines (liftoff baseline plus turbofan top tier), and the measurement of compile time as a component of time-to-usable. The article is restricted to browser-side module loading; it does not cover WASI, server-side runtimes, or the authoring side of toolchain selection. It is concerned with the question: what determines how long a module takes from first byte to first call, and which decisions on the serving and instantiation path shorten it.

## Workflow or implementation guidance
Begin by understanding what streaming compilation changes. The naive path downloads the entire module, then parses and compiles it, so total time is download time plus compile time, serially. The streaming path hands each chunk to the compiler as it arrives, so compilation overlaps with downloading, and total time approaches max(download, compile) rather than the sum. On a fast connection with a large module, compile dominates and the overlap saves the download time; on a slow connection with a small module, download dominates and the overlap saves the compile time. Either way the saving is real, and the technique costs nothing but correct serving.

Use `instantiateStreaming` rather than `compileStreaming` followed by a manual `WebAssembly.instantiate`. `instantiateStreaming` compiles and instantiates in one step from the response, taking the module's imports as an argument, and avoids the intermediate module object entirely. The pattern is `const { instance } = await WebAssembly.instantiateStreaming(fetch(url), imports)`. Reserve `compileStreaming` for the case where the module is compiled once and instantiated many times with different imports.

Serve the module with the correct MIME type. The streaming APIs require `Content-Type: application/wasm`; a response with any other content type rejects the promise. This is a deliberate spec-level guard: streaming compilation needs to trust that the bytes are a module, and the content type is the contract. Verify the header in the serving configuration (origin, CDN, or object storage) before anything else, because a missing header is the single most common reason a streaming migration silently falls back or fails.

Serve the response with CORS if the module is cross-origin. `instantiateStreaming` consumes a `fetch` response, and a cross-origin response is only readable with proper CORS headers. A same-origin module needs nothing; a cross-origin module needs `Access-Control-Allow-Origin` on the response and `crossorigin` on the initiating fetch where applicable. Serving the module from the same origin as the page, or from a CDN configured for CORS, is the straightforward path.

Do not wrap the stream in a non-streaming intermediate. Reading the response body into an `ArrayBuffer` first and then calling `WebAssembly.instantiate(buffer)` reverts to the serial path and forfeits the overlap. The same applies to a service worker that buffers the response body before returning it; a worker that wants to cache the module should tee the stream, return one branch to the page, and cache the other asynchronously, so the page still receives streaming bytes.

Compress the module. WebAssembly binaries compress well with gzip and brotli because they contain repeated instruction patterns and name sections; brotli at a moderate level typically halves or better the wire size. Because compression is applied on the wire and decompression is interleaved with compilation on the client, the streaming overlap still holds: the client decompresses chunk-by-chunk as the compiler consumes chunks. Pre-compress static modules at build time for the best ratio, and ensure the CDN honours the client's `Accept-Encoding` preference.

Reduce the module's size at build time before worrying about compile speed. Dead-code elimination through tree shaking, disabling debug name sections in production builds, and targeting the smallest feature set that the runtime requires all shrink the module and therefore both the download and the compile. A smaller module is faster on every axis, and no serving technique compensates for a module that is several times larger than necessary.

Plan for tiered compilation. Production engines compile a module first with a fast baseline compiler that produces correct but unoptimised code, then re-optimise hot functions with a slower top-tier compiler in the background. The practical consequence is that the first calls into a freshly instantiated module are slower than steady-state calls, and a microbenchmark taken immediately after instantiation measures the baseline tier, not the optimised code. Warm up a representative workload before measuring, and treat the first-run penalty as a separate metric from steady-state throughput.

For repeated navigations, cache the compiled module. The browser's HTTP cache stores the bytes, but compilation still runs on each page load unless the module is cached in compiled form. A service worker can hold the `WebAssembly.Module` object in memory for the worker's lifetime, and `IndexedDB` structured cloning of a `Module` is supported in some engines as a compiled-code cache; where it is not, the fallback is to accept recompilation of a cached byte stream, which is still much faster than a cold download plus compile. Measure whether the module is on the critical path of a repeat visit before investing in compiled-code caching.

## Controls
Define three categories of control. The first is a **serving contract check**: a synthetic request to the module URL asserts the `Content-Type` is `application/wasm`, the response is CORS-readable when cross-origin, and the content encoding matches what the CDN is configured to emit. The second is a **streaming-path audit**: the instrumentation confirms that `instantiateStreaming` succeeded rather than falling back to a buffer path; a silent fallback is a regression with no error. The third is a **size budget**: the built module's wire size is compared against a budget in CI, and a growth beyond the budget fails the build, because module size drives both download and compile time.

A useful guardrail metric is the **first-call latency** for the module's entry function: the time from navigation start to the first completed call, split into download, compile, and instantiate phases via the Resource Timing entry for the fetch and an application-level mark around the instantiate call.

## Validation evidence
The validation evidence is a controlled comparison of the naive and streaming load paths for the production module on reference hardware under throttled network profiles, reporting total time from navigation to first call for each path. The expected outcome is that the streaming path's total time approximates the maximum of download and compile while the naive path's approximates their sum, with the difference most visible on the profile where the two phases are comparable in duration. Complement with a field measurement of first-call latency before and after the migration, split by network class. Document the module's wire size, the content type and encoding headers, the measured compile time on reference devices, the baseline-versus-optimised first-call gap, and the fallback rate where a non-streaming path was taken.

## Failure modes and correction
**Wrong content type**: the server returns `application/octet-stream` and the streaming API rejects the response. Correction: set `Content-Type: application/wasm` at the origin or CDN rule, and add the serving contract check so the regression cannot recur silently. **Cross-origin response unreadable**: the module is served from a CDN without CORS headers and the fetch body cannot be read. Correction: configure `Access-Control-Allow-Origin` on the module responses, or serve the module same-origin. **Service worker buffers the body**: the worker reads the full response before returning it, and compilation cannot overlap with download. Correction: return the original response and cache it via `ctx.waitUntil` with a tee, never by consuming the body on the critical path. **Silent fallback to buffer instantiation**: an error handler catches the streaming failure and falls back to `WebAssembly.instantiate(arrayBuffer)`. Correction: fix the underlying serving defect and instrument the fallback so its rate is visible; a fallback that fires for every user is a silent performance regression. **Module grows past the budget**: a dependency change bloats the module and first-call latency regresses on slow devices. Correction: enforce the size budget in CI, run dead-code elimination, and strip debug sections from production builds. **First-call measurement is misleading**: a benchmark taken immediately after instantiation measures the baseline compiler and reports a false regression. Correction: warm up the module with a representative workload before measuring steady-state throughput, and track first-run and steady-state as separate metrics.

## Limitations
Engine behaviour, including the exact tiering strategy and any compiled-code caching, is implementation-defined and varies across browsers and versions; the patterns here are portable but the magnitudes are not. The overlap benefit depends on the ratio of download time to compile time, so a module that is trivially small on a fast connection shows no measurable improvement. Streaming compilation does not reduce peak memory use: the engine still holds the module while compiling, and very large modules can hit memory limits on low-end devices regardless of the load path. The article does not cover dynamic linking of multiple modules, `WebAssembly.Module` sharing across workers via `postMessage`, or the interaction with `SharedArrayBuffer` and threads.
