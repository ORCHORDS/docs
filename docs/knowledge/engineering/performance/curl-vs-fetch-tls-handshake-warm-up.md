# Curl Vs Fetch TLS Handshake Warm Up

## Scope
This article addresses the engineering decisions around warming up TLS sessions for high-latency or high-RTT upstreams, comparing the cost and behaviour of `curl` invocations against in-process `fetch` (Workers `fetch`, Node.js `fetch`, browser `fetch`) and the trade-offs between connection reuse, 0-RTT data, and session resumption. The scope covers TLS 1.3 (RFC 8446), the related TLS 1.2 resumption mechanisms (session tickets, session IDs), and the practical implications for latency-sensitive request paths. The article is restricted to first-party TLS connections; it does not cover mutual TLS, client certificate authentication, or the operational mechanics of certificate management. It is concerned with how to ensure the first request to a remote origin does not pay the full handshake cost, and how the choice of client (curl vs fetch) affects the warm-up strategy.

## Workflow or implementation guidance
Begin by measuring the TLS handshake cost on the target network. The handshake for TLS 1.3 typically requires one round-trip (1-RTT) before the client can send application data; on a 100-ms-RTT network this is a 100-ms cost on the first request, amortised to zero on subsequent requests when the connection is reused. On a high-RTT network (mobile, satellite, intercontinental) the handshake cost dominates the request time. Use `curl -w "%{time_connect}\n" --insecure https://example.com/health` to measure the TCP+TLS handshake time in isolation; compare against `curl -w "%{time_starttransfer}\n"` for the full first-byte time. The delta is the TLS cost.

Decide whether to warm up connections in advance. For latency-sensitive paths (the first request after a cold start, the first request after a deploy, the first request for a user on a high-RTT network), the handshake cost is significant. For high-throughput paths (a Workers isolate serving many requests per second), the connection is reused and the handshake cost amortises to near zero. The decision to warm up is a function of the connection reuse rate: if each connection serves only one request, warm up; if each connection serves dozens, do not bother.

For `curl`-driven warm-up, issue a low-cost request (a HEAD or a `GET /health` that returns a small payload) shortly before the request that actually needs the connection. Store the connection in the kernel's TCP cache; the next request from the same process (or any process using the same source port, which is rare with ephemeral ports) reuses the connection. `curl`'s keepalive defaults are short; pass `--keepalive-time` to extend the idle timeout, or use a long-lived `curl` process that polls the health endpoint. For a Workers-style deployment, `curl` is not available; use a long-lived process that holds the socket open and re-uses it.

For in-process `fetch`, connections are pooled automatically by the runtime (Node.js `http.Agent`, Workers `fetch`'s connection cache, browser's connection pool). The pool size is typically 6 per origin in browsers and configurable in Node.js via `http.Agent`'s `maxSockets`. The pool evicts idle connections after a configurable timeout; tune the timeout based on the upstream's keepalive settings. For upstreams that close connections after 60 s of idleness, set the client-side pool timeout to 30 s so the client closes first and avoids a half-open connection.

For TLS 1.3 0-RTT data (RFC 8446 section 8), a client that has connected to a server before can send application data in the first flight of the handshake, saving the round-trip. 0-RTT is supported by Cloudflare's edge and most modern CDNs. The trade-off is replay vulnerability: a 0-RTT request can be replayed by an attacker who captures the packet, and the server must implement replay protection (single-use session tickets, server-side state) for any non-idempotent operation. Use 0-RTT only for idempotent reads; never for state-changing operations.

Configure session resumption explicitly. TLS 1.3 uses session tickets by default; the server sends a NewSessionTicket message after the handshake, and the client stores it for the next connection. Verify the ticket is stored (in Node.js, the `tls` module exposes the session ticket via `TLSSocket.getSession()`); if the ticket is dropped, every connection starts a fresh handshake. On the server side, configure a long ticket lifetime and rotate the ticket key periodically.

For Workers specifically, the `fetch` runtime reuses connections across requests automatically. Warm-up is rarely necessary because the runtime keeps a per-isolate pool; the first request to a given origin pays the handshake cost, subsequent requests reuse it. The case where warm-up matters is when the runtime schedules a new isolate for a high-RTT request and the isolate is short-lived; in that case the connection pool is destroyed before it can be reused, and the warm-up pattern is to keep the isolate warm by serving low-cost requests to it.

## Controls
Define three categories of control. The first is a **handshake-time SLO**: measure the p95 handshake time per upstream and alert when it exceeds the budget. The second is a **session-resumption rate**: track the fraction of TLS handshakes that complete in 0-RTT versus 1-RTT; a low resumption rate indicates tickets are not being stored or are expiring too quickly. The third is a **connection-pool utilisation**: monitor the in-use vs idle ratio in the connection pool; a high idle ratio indicates the pool is over-sized and wasting memory, a low ratio indicates the pool is too small and connections are not being reused.

A useful guardrail metric is the **first-request latency** per upstream: the time from `fetch` invocation to first byte for a cold connection. Compare against the steady-state latency (warm connection) and use the delta to size the warm-up strategy.

## Validation evidence
The validation evidence is a controlled comparison of first-request latency with and without connection warm-up, captured against the production upstream under the production network profile. The expected outcome is that warm connections return first byte 50–200 ms faster than cold connections on a high-RTT network, with no improvement on a low-RTT network where the handshake is already fast. Capture the connection reuse rate from the runtime's metrics; verify that the session resumption rate is above 80% for upstreams that have been contacted recently. Document the upstream's keepalive timeout, the client-side pool timeout, the handshake time p95, and the first-byte time p95.

## Failure modes and correction
**Connections never reused**: the client-side pool is destroyed between requests (e.g., a new Worker isolate per request). Correction: keep the isolate warm by routing traffic to it, or use a long-lived process that holds the pool open. **0-RTT replay attack**: an idempotent GET is replayed by an attacker, doubling load on the server. Correction: ensure the upstream implements replay protection (single-use tickets or server-side state), and avoid 0-RTT for non-idempotent operations. **Session ticket expired**: the client stored a ticket but it has expired, and every connection starts a fresh handshake. Correction: shorten the time between connections so the ticket is still valid, or extend the server-side ticket lifetime. **Half-open connection**: the client believes the connection is alive but the server has closed it; the next request fails. Correction: enable TCP keepalive on the client side, and set the idle timeout below the server's keepalive timeout. **Pool size too small**: the pool is exhausted under load and new requests open fresh connections. Correction: increase the pool size to the upstream's tolerance, or shed load with a circuit breaker.

## Limitations
The article assumes modern TLS 1.3 endpoints; older TLS 1.2 endpoints have different resumption mechanisms (session IDs and session tickets, with separate state on each side) and slower handshakes. The article does not cover QUIC, which has its own 0-RTT model and is increasingly common at the edge. The article assumes IPv4; IPv6 may have different routing characteristics that affect RTT. The article is focused on HTTPS; plain HTTP has no handshake cost and the analysis does not apply. The article does not cover mutual TLS, where the client also presents a certificate and the handshake is longer.
