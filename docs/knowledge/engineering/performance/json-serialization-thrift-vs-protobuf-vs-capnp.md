# Json Serialization Thrift Vs Protobuf Vs Capnp

## Scope
This article addresses the comparative cost of JSON against binary serialization formats—Apache Thrift, Protocol Buffers, and Cap'n Proto—for service-to-service payloads, the trade-offs between wire size, encode/decode CPU cost, and human readability, and the engineering decision of when to migrate an internal API off JSON. The scope covers the wire formats themselves, the language-binding code generation model, zero-copy deserialization, and the measured impact on request latency and CPU utilisation at the edge. The article is restricted to data serialization for RPC-style payloads; it does not cover REST API design, GraphQL, gRPC's HTTP/2 transport semantics, or message-queue encodings. It is concerned with the question: for a given payload shape and traffic profile, which format minimises total request cost, and what does a migration cost.

## Workflow or implementation guidance
Begin by measuring the actual cost of JSON in the hot path. JSON's dominance is a convenience argument, not a performance argument: encoding and decoding are text parsing, field names are repeated on the wire, numbers are decimal strings, and both sides re-parse the schema on every message. For a 50-KB JSON payload, `JSON.parse` on a low-end mobile device costs tens of milliseconds; on an edge worker, the CPU milliseconds are charged against the request. Profile the encode and decode cost separately: the encode cost is paid by the producer, the decode cost by every consumer, and the decode cost usually dominates because it is paid N times for a fan-out payload.

Understand what each binary format buys. Protocol Buffers use a tag-length-value wire format with compact varint encoding; the schema lives in a `.proto` file and both sides generate typed bindings. Thrift offers a family of wire protocols (compact, binary, JSON) plus an RPC layer, with a similar interface-definition-language workflow. Cap'n Proto takes a different position: the wire format is the in-memory format, so deserialization is a pointer fix-up rather than a parse, and reads are effectively zero-copy at the cost of a more restrictive memory layout. The practical ranking for decode cost on large payloads is Cap'n Proto fastest, Protobuf next, Thrift's compact protocol comparable to Protobuf, JSON slowest—typically by an order of magnitude on large payloads. Wire size follows a similar ordering, with binary formats 30–60% smaller than JSON for the same data, and a further reduction when field names dominate the JSON size.

Decide where the boundary of the migration is. The highest-value boundary is a high-fan-out internal edge: one producer, many consumers, large payloads, tight CPU budgets. The lowest-value boundary is a public, third-party-facing API where JSON's ubiquity outweighs the cost: consumers cannot be required to run code generation, and the debugging value of reading the payload in a proxy or a curl command is real. A common pattern is JSON at the public boundary and Protobuf or Cap'n Proto for internal service-to-service hops behind it.

Account for the operational cost before migrating. Binary formats require schema management: a schema registry, versioned evolution rules (Protobuf's field-number discipline, Cap'n Proto's union evolution), and a build step that generates bindings for every consuming language. Debugging requires tooling (`protoc --decode`, Cap'n Proto's tooling) rather than a text editor. A migration that halves decode time but adds a schema-registry dependency may be a net loss for a small team and a clear win for a large one.

Use the formats' evolution rules to avoid lock-step deploys. Protobuf's rule set—new fields get new numbers, unknown fields are preserved, field numbers are never reused—allows a producer to add a field before consumers know about it. Thrift and Cap'n Proto have equivalent rules. Encode the discipline in CI: a schema change that violates the rules (reusing a field number, changing a type) must fail the build. Without this, the binary format's speed advantage is paid for with outages.

For very large payloads, use the formats' streaming capabilities rather than loading the whole message. Protobuf's delimited stream format, Thrift's framed transport, and Cap'n Proto's segment model all allow incremental processing; a payload that does not fit in the worker's memory budget must be streamed regardless of format. Pair this with compression: Protobuf and Thrift payloads compress well with zstd, and Cap'n Proto's pointer-heavy format benefits from a built-in packing mode.

Where the producer is a browser, JSON remains the only practical choice: Protobuf and Cap'n Proto bindings exist for JavaScript but cost bundle size and code-generation complexity in the client. Treat the browser-to-edge hop as JSON and the edge-to-origin hop as binary, converting at the edge worker; the conversion cost is paid once per request rather than once per consumer.

## Controls
Define three categories of control. The first is a **schema-evolution gate**: CI validates every schema change against the compatibility rules and fails the build on a breaking change. The second is a **payload-size budget**: representative messages are size-checked per format; a growth beyond the budget triggers review. The third is a **decode-cost budget**: benchmark suites decode representative payloads on reference hardware and track the CPU cost per message; a regression indicates a schema change that made decoding more expensive.

A useful guardrail metric is the **encode-plus-decode cost per request**, measured on reference hardware and tracked over time. For a migration, the same metric measured under both formats is the evidence for the decision.

## Validation evidence
The validation evidence is a benchmark that encodes and decodes representative production payloads in each candidate format on reference hardware for every language in the service mesh, reporting per-message CPU time and wire bytes. Repeat with the production payload distribution (not a synthetic uniform payload), because real payloads have skewed field cardinality that changes the ratios. Complement with a staged rollout: route a fraction of internal traffic to the binary format, and compare CPU per request, request latency p50/p95/p99, and total bytes on the wire. Document the schema files, the generated bindings, the compatibility rules enforced in CI, and the measured cost delta.

## Failure modes and correction
**Schema drift breaks consumers**: a producer adds a field and a consumer with an old binding mishandles it. Correction: enforce the evolution rules in CI, deploy producers before consumers, and rely on unknown-field preservation rather than requiring lock-step. **Debugging becomes slow**: on-call engineers cannot read a binary payload in a proxy log. Correction: deploy a decode tool beside the logging pipeline, and log decoded summaries for high-cardinality errors. **Bundle size regression in the browser**: generated JavaScript bindings are larger than the JSON they replace. Correction: keep the browser boundary on JSON, and convert at the edge worker. **Decode cost regresses after a schema change**: a new nested structure or a repeated field with high cardinality makes decoding more expensive. Correction: flatten the schema, reduce nesting, and re-run the decode-cost benchmark. **Partial migration creates a double-parse**: the edge decodes JSON, re-encodes as Protobuf, and the origin decodes Protobuf, adding one full parse cycle to every request. Correction: move the boundary so each payload is parsed the minimum number of times, or pass the original bytes through where no transformation is needed.

## Limitations
The exact speed and size ratios vary by payload shape, language runtime, and library version; the orderings given here are typical but must be re-measured for the specific workload. The article does not cover gRPC's transport behaviour (streaming multiplexing, flow control), which interacts with the wire format choice. The article does not cover Flatbuffers, MessagePack, CBOR, or Avro, which occupy adjacent points in the design space. Browser-side numbers assume WebAssembly-free bindings; a WASM-based decoder changes the calculus. The article assumes internal services under one administrative control; cross-organisation APIs have compatibility requirements that change the decision.
