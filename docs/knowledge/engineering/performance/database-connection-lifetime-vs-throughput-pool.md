# Database Connection Lifetime Vs Throughput Pool

## Scope
This article addresses the engineering trade-offs between long-lived database connections and high-throughput connection pools, the configuration parameters that govern connection lifetime, and the failure modes that arise when the parameters are chosen incorrectly for the workload. The scope covers PgBouncer's pool modes (session, transaction, statement), HikariCP's `maxLifetime` and `idleTimeout`, PostgreSQL's `idle_in_transaction_session_timeout`, and the connection-establishment cost as a function of TLS handshake, authentication, and database warm-up. The article is restricted to client-side pool tuning and the protocol-level implications for downstream databases. It does not cover application-layer caching, query optimisation, or database schema design. It is concerned with how connection lifetime interacts with throughput, what the steady-state pool size should be, and what happens when steady state is exceeded.

## Workflow or implementation guidance
Begin by measuring the steady-state connection count under production load. A connection pool that is too small starves under burst; a pool that is too large wastes database resources. The right size is the p95 or p99 of concurrent in-flight queries at peak load, plus a small headroom for transaction overlap. HikariCP's documentation recommends a pool size based on the formula `(core_count * 2) + effective_spindle_count` for the database's perspective; the application perspective is the inverse: how many concurrent queries each instance issues, multiplied by the number of instances, must not exceed the database's connection capacity.

Configure `maxLifetime` to recycle connections before they accumulate state. A connection held for an hour may have stale prepared statement caches, an aborted TCP session masked by the kernel, or a server-side cursor that has grown unbounded. Configure `maxLifetime` on the order of 30 minutes, with `keepaliveTime` of a few minutes to keep idle connections alive through NAT timeouts. HikariCP's default jitter staggers the lifetime across the pool so connections do not all expire simultaneously; verify the jitter is enabled and matches the application's traffic pattern.

Configure `idleTimeout` separately from `maxLifetime`. `idleTimeout` closes connections that have been idle for the configured duration; `maxLifetime` closes them after a fixed lifetime regardless of activity. The two settings together govern the pool's resource profile: short `idleTimeout` frees database resources quickly but increases connection-establishment frequency; long `idleTimeout` keeps connections warm but holds database resources when the application is idle. The right setting depends on the application's traffic pattern—a bursty application benefits from short `idleTimeout` to release resources between bursts; a steady-traffic application benefits from long `idleTimeout` to avoid the establishment cost.

For transaction-pooling mode in PgBouncer, configure the application to avoid session-state features. Prepared statements must use `DEALLOCATE` on commit; advisory locks must be held within the transaction; `SET` statements must be re-issued on each new connection. With careful schema design, transaction pooling is a major capacity win because the database's connection capacity is no longer the bottleneck. The trade-off is that some application frameworks assume session-level state and must be configured for transaction pooling explicitly.

For session-pooling mode, where each application connection maps to a single database connection for the duration of the application connection, the connection-establishment cost is paid once and amortised across the lifetime. This mode is appropriate for legacy applications that depend on session state, but it caps the application's throughput at the database's connection capacity.

For statement-pooling mode, where each statement may use a different backend connection, prepared statements cannot be reused across statements and the application must issue the same query with the same SQL text on every call. This mode is rarely used in practice because the prepared-statement overhead is significant.

Configure the database's `idle_in_transaction_session_timeout` to release connections that the application has abandoned mid-transaction. A buggy application that opens a transaction and never commits will hold the connection indefinitely; the database's timeout reclaims it after the configured duration. Set the timeout to a value that is longer than the application's longest legitimate transaction but shorter than the application's typical idle period.

For TLS-protected connections, the TLS handshake is part of the establishment cost. A connection that uses client certificates or mutual TLS pays a longer handshake; configure the pool's keepalive so the handshake is amortised across many queries. For long-lived connections, the TLS session ticket can be reused on the next connection, reducing the handshake from 1-RTT to 0-RTT.

## Controls
Define three categories of control. The first is a **connection-acquisition SLO**: measure the p95 acquisition latency per pool and alert when it exceeds the budget. The second is a **pool utilisation metric**: track the average in-use count versus the maximum; high utilisation indicates the pool is too small, low utilisation indicates over-provisioning. The third is a **connection-age distribution**: track the ages of currently-open connections; an age distribution skewed toward the maximum lifetime indicates connections are being recycled frequently, an age distribution skewed toward zero indicates connections are being closed quickly.

A useful guardrail metric is the **connection-establishment rate**: the number of new connections opened per minute. A high rate indicates the pool is being churned; investigate the `idleTimeout` and the application's connection-release behaviour.

## Validation evidence
The validation evidence is a controlled pool exhaustion benchmark: ramp concurrent requests against the pool until it saturates, measure the saturation point, and verify the configured SLOs are met. Run the benchmark with realistic per-request latency distributions, including a small fraction of slow queries that hold connections for several seconds. Confirm the pool recovers quickly when load drops, that no leaked connections remain after the test, and that the database's `pg_stat_activity` (or equivalent) shows the expected number of connections from the application. Document the pool size, the saturation point, the acquisition latency distribution, the connection-establishment rate, and the connection-age distribution.

## Failure modes and correction
**Pool exhausts under burst load**: a sudden spike of requests fills the pool and subsequent requests time out. Correction: increase the pool size within the database's tolerance, or implement a queue with bounded wait time and shed load beyond the bound. **Connection leak**: an application forgets to release a connection; the pool shrinks over time until it is exhausted by leaks. Correction: enable `leakDetectionThreshold` (HikariCP) or the equivalent, and audit the code path for unclosed resources. **Session-pooling bottleneck**: the application's connection count equals the pool size, but the database's capacity is reached because the database cannot accept more connections. Correction: switch to transaction-pooling mode and audit the application for session-state dependencies. **Connection-establishment storm**: a deploy or restart closes all connections at once, and the next burst of requests opens N new connections simultaneously, overwhelming the database. Correction: stagger the establishment via the pool's jitter, or rate-limit the establishment on the application side. **Prepared statement cache fills**: a database pool with a per-connection prepared statement cache fills up over time, and new statements evict older ones. Correction: pin prepared statements at the application level rather than relying on the connection's cache.

## Limitations
The article focuses on PostgreSQL-compatible databases; MySQL has different connection-lifetime semantics and the parameters are not directly transferable. The article assumes a synchronous request-response model; asynchronous systems with backpressure have different failure modes. The recommended pool sizes are starting points, not universal rules; the actual right size depends on the specific workload and the database's connection capacity. The article does not cover connection encryption overhead in detail, or the operational mechanics of certificate rotation. The article does not address multi-region deployments where connection pools span data centres.
