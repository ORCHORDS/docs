# R2 Object First Byte Latency Warm Region

## Scope
This article addresses the first-byte latency of object reads from Cloudflare R2, the S3-compatible object storage that runs on Cloudflare's network, and the difference between a "warm" object—one whose metadata and data are resident in a colo close to the reader—and a "cold" object that must be fetched from the location where it was written. The scope covers R2's location model (a single, per-bucket location with a global anycast read path), the role of the Cache API and Cache Reserve in front of R2, presigned URL access patterns, and the engineering patterns that put bytes close to readers before they ask. The article is restricted to read latency; it does not cover write throughput, multipart upload tuning, lifecycle policies, or egress pricing. It is concerned with the question: what determines the time to first byte for an R2 object, how large is the warm-cold gap, and which caching layer closes it.

## Workflow or implementation guidance
Begin by understanding what dominates R2 first-byte latency. A read is routed to the nearest Cloudflare colo; if the object is not cached there, the read is served from the bucket's home region over Cloudflare's backbone. For a reader in the same region as the bucket, first byte is a few tens of milliseconds; for a reader on another continent, the backbone round-trip adds tens to over a hundred milliseconds. Unlike a service that replicates objects to every region, R2 does not keep persistent copies everywhere: the persistence model is one location per bucket, with caching providing the locality. The warm-cold gap is therefore a function of geography and cache state, not of object size.

Put the Cache API in front of R2 reads. The standard pattern is a Worker that binds to the R2 bucket, looks up the Cache API first, and only on a miss reads from R2 and writes the response to the cache. The cache is per-colo, so a popular object becomes warm in the colos where it is read, and subsequent reads are served from the colo's cache with first-byte latency in single-digit milliseconds. Set an explicit `Cache-Control` on the synthesised response so the cache honours the intended freshness; R2 object metadata is not automatically translated into cache directives.

For large or globally popular objects, add Cache Reserve. Cache Reserve extends the per-colo cache with a persistent, globally shared tier backed by R2 itself, so an object evicted from a colo's cache is still available from the reserve rather than from origin. This converts repeated cache misses into reserve hits and reduces the frequency with which the bucket's home region is consulted. Enable Cache Reserve on the zone and verify with the `cf-cache-status` header that responses report the reserve tier.

Warm caches deliberately for latency-critical assets. A Worker on a cron trigger (or the deploy pipeline) fetches the hot set of objects through the same cache path that user traffic uses, so the per-colo caches are populated before users ask. Warming is only worthwhile for a predictable hot set; for a long tail of cold objects, warming wastes more than it saves. Rank objects by recent read counts and warm the top decile in the colos that generate the traffic.

Choose the bucket's location deliberately. R2 lets you specify a location hint (for example North America, Europe, or Asia Pacific) at creation time. Place the bucket in the region that dominates the write traffic, because writes always pay the distance to the bucket; reads are mitigated by caching. If writes are geographically concentrated and reads are global, the location hint plus a cache layer is the right topology. Changing the location later requires a new bucket and a data migration, so decide it with the write distribution in mind.

Use presigned URLs correctly. A presigned URL points at the R2 endpoint and is served by the R2 request path, which is cacheable by Cloudflare's CDN but only if the cache configuration includes the query string (the signature is in the query). Presigned URLs with long expiry defeat the purpose of signing; short expiries mean the query string changes constantly and the cache key fragments. The alternative that avoids both problems is a Worker-mediated read: the Worker authenticates the user with its own credentials, reads from the bound R2 bucket, and serves the response through the Cache API under a stable key. This keeps the cache key stable and the authentication in application logic.

Measure the tail, not the median. First-byte latency for a warm object is uniformly fast; the p99 is dominated by cold reads in distant colos and by cache misses after eviction. Alert on the p99 per region, and treat a rising p99 with a flat median as a cache-efficiency problem rather than an R2 throughput problem.

For range requests and large objects, first byte is not the whole story: the read path streams the object, and throughput is bounded by the connection. But the first-byte metric is a clean signal for the cache-hit question, because a cache hit returns first byte from the colo and a miss pays the backbone round-trip before any byte is available.

## Controls
Define three categories of control. The first is a **cache-hit guardrail**: per-route cache hit ratio in Cloudflare analytics, with an alert when hit ratio drops, because a drop directly converts into first-byte latency. The second is a **cache-key audit**: the Worker logs the computed cache key for a sample of requests, and the audit verifies the key excludes volatile inputs (presigned query parameters, per-user cookies) and includes the necessary ones (the object path and any content-negotiation dimension). The third is a **warm-set freshness check**: the warming job records which objects it warmed and when; stale entries older than the cache TTL indicate the warming schedule is misaligned with the TTL.

A useful guardrail metric is the **first-byte p99 per region**. A rising p99 with a stable p50 is the signature of cache eviction or a cold popular object; a rising p50 indicates a broader routing or origin problem.

## Validation evidence
The validation evidence is a geographic first-byte benchmark: issue reads for the same object from multiple regions, first through a colo-warmed cache and then after a forced eviction, and record the time to first byte for each. The expected outcome is single-digit-millisecond first byte for a warm colo cache hit and tens to over a hundred milliseconds for a cold read from a distant bucket. In production, confirm with the `cf-cache-status` header distribution (HIT/DYNAMIC/REVALIDATED) and R2 request metrics that the hit ratio matches the design. Document the bucket location, the cache TTL, the warm-object p99 per region, the cold-object p99 per region, and the hit ratio before and after enabling Cache Reserve.

## Failure modes and correction
**Cache misses on presigned URLs**: the signature in the query string changes per request, so the cache key never repeats. Correction: serve reads through a Worker that authenticates and reads from the bound bucket, keeping the cache key stable, or configure the cache key to ignore the signature parameters and validate the signature before the cache lookup. **Hot object evicted from the colo cache**: the object falls out of the per-colo cache under pressure and every subsequent read pays the backbone round-trip. Correction: enable Cache Reserve so evicted objects are served from the persistent tier, or raise the object's cache priority. **Bucket in the wrong region**: writes dominate from one continent but the bucket was created elsewhere, so both writes and cold reads pay the distance. Correction: create a new bucket with the correct location hint and migrate; this is a planned operation, not a configuration change. **Warming job uses the wrong path**: the cron trigger fetches the object directly from R2 rather than through the Worker's cache path, so the colo cache is never populated. Correction: warm through the public URL the users hit, so the cache key and response headers match production traffic. **Per-user cache keys fragment the cache**: the Worker includes an identity header in the cache key, so every user gets a private copy and the hit ratio collapses. Correction: normalise the cache key to content dimensions only, and move personalisation out of the cached response.

## Limitations
Latency numbers depend on the reader's distance from Cloudflare colos and on backbone conditions; the magnitudes here are typical, not contractual. The article assumes the Workers platform; direct S3-API access from outside Cloudflare's network has a different latency profile. Cache Reserve availability and behaviour change as the product evolves; verify current semantics in the documentation. The article does not cover R2 event notifications, lifecycle rules, or jurisdiction restrictions on bucket location, all of which can constrain the topology but do not affect read latency directly.
