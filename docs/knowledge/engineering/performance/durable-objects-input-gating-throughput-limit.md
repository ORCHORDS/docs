# Durable Objects Input Gating Throughput Limit

## Scope
This article addresses Durable Objects' input gates and output gates as the mechanism that enables single-threaded, strongly consistent execution without explicit locking, and the throughput ceiling that the gating model imposes on a single object. The scope covers the JavaScript concurrency model inside a Durable Object, the `blockConcurrencyWhile` API, the input/output gating guarantees, the per-object request rate limits published by Cloudflare, and the engineering patterns that shard state across objects when a single object becomes the bottleneck. The article is restricted to Durable Objects on the Workers platform; it does not cover Workers KV, D1, or R2 consistency models. It is concerned with how much throughput a single object can sustain, what the limiting factor is, and how to design the object topology to scale beyond it.

## Workflow or implementation guidance
Begin by understanding the gating model. A Durable Object executes JavaScript on a single thread. While an `async` storage operation is in flight, the runtime would normally allow other events to be interleaved, which would break atomicity. Input gates close while a storage operation is outstanding: no new events are delivered to the object until the operation completes and the JavaScript stack unwinds. Output gates are the mirror image: a response is not sent until all storage writes it depends on have completed. Together, the two gates give the developer single-threaded semantics without explicit mutexes.

The throughput ceiling follows directly. A single object can process events only as fast as its storage operations complete, because each event holds the input gate while its storage is in flight. If the average handler performs two storage operations at 5 ms each, the object's ceiling is roughly 100 events per second. Sustained load above the ceiling queues inside the object, and the queue grows until the caller's deadline expires. The ceiling is not a published constant; it is a property of the workload, and the way to raise it is to reduce storage operations per event or to shard.

Reduce storage operations per event first. Batch reads and writes: Durable Objects' storage API supports `get` and `put` on multiple keys in a single call, and a transaction (`ctx.storage.transactionAsync`) groups operations so the gate is held once rather than per-operation. Cache hot values in the object's in-memory state; the object's lifetime is minutes-to-hours and the in-memory cache is valid as long as the object is alive. Re-derive values instead of reading them where the derivation is cheaper than the read.

Keep the object's stored state small and shallow. Storage operations whose keys are in a flat namespace are cheaper than deep hierarchical traversal. Avoid storing large values: a multi-megabyte value takes longer to read and write, and the gate is held for the duration. Split large values into per-key records and read only the keys needed for the event.

Design the object topology around contention. The classic sharding pattern is to key objects by an identifier with low cardinality but high isolation: per-room for a chat application, per-document for collaborative editing, per-user-session for presence. A "global" object keyed by a single constant becomes the bottleneck for the whole application; any key that is hot enough to need sharding should not be a single object.

When a single logical entity is genuinely too hot for one object, use fan-out with an aggregator. Split the entity into N shards, route writes to a shard by a hash of the entity id, and read the aggregate by querying all N shards in parallel and combining. The aggregator itself must not be a Durable Object (it would become the new bottleneck); use a plain Worker that fans out and combines. For counters, an alternative is a hierarchy: shard counters update in parallel, a periodic rollup object aggregates the shards, and readers query the rollup.

Use `blockConcurrencyWhile` only during initialisation. The API closes the input gate for the duration of an arbitrary async closure, which is exactly what is needed to load state once at object startup, and exactly the wrong tool for steady-state handling because it serialises everything behind one closure. Call it in the constructor to lazily hydrate state, and let normal event handling proceed afterwards.

Where strictly ordered processing is required, drive the object from alarms rather than from request traffic. An alarm delivers an event at a scheduled time and is guaranteed not to overlap with other events on the same object; a queue-like processing loop implemented with alarms gives deterministic ordering without holding the gate across events.

Finally, measure before sharding. The per-object limits are documented by Cloudflare (requests per second per object), but the practical ceiling is workload-dependent. Instrument the object's queue depth, the time events spend waiting, and the storage operation count per event. Shard only when the measurements show the single object is the bottleneck.

## Controls
Define three categories of control. The first is a **per-object rate guardrail**: track requests per second per object id and alert when a single object exceeds the design threshold. The second is a **storage-operations-per-event budget**: cap the number of storage calls per handler; a rise in the average indicates a regression that will lower the ceiling. The third is a **queue-depth monitor**: measure the time from event delivery to handler start inside the object; a growing value is the leading indicator that the object is saturated.

A useful guardrail metric is the **gate-held duration** per event: the total time the input gate is closed while storage is in flight. This metric, multiplied by the event rate, is the fraction of time the object is busy; sustained values above roughly 70% indicate the object will queue under burst.

## Validation evidence
The validation evidence is a load test against a representative Durable Object that ramps the event rate until the object saturates, measuring the saturation point, the queue depth, and the p99 event latency. The expected outcome is a knee in the latency curve at the object's ceiling, with latency flat below the knee and rising steeply above it. Repeat the test with the storage-batching optimisation and confirm the knee moves to a higher rate. Document the per-event storage operation count, the average storage latency, the saturation rate, and the p99 latency at the design load.

## Failure modes and correction
**Hot object saturates**: a single object key receives a disproportionate share of traffic and becomes the throughput limit for the whole application. Correction: shard the key space across multiple objects and aggregate reads in a plain Worker; or move the hot counter to a different primitive (Workers Analytics Engine or KV) whose throughput scales differently. **Gate held too long**: a handler awaits an external `fetch` while the input gate is closed, serialising all events behind the network call. Correction: move the external fetch outside the gate (perform it before the storage write or after the response via `ctx.waitUntil`), and never `await` a cross-network call between storage operations. **`blockConcurrencyWhile` used in the hot path**: every event is serialised behind a global closure. Correction: restrict `blockConcurrencyWhile` to constructor-time initialisation; use transactions for multi-step atomicity. **Storage values grow unbounded**: a value that started at a few kilobytes grows to megabytes, and every read/write holds the gate longer. Correction: normalise the state into per-key records, archive cold data to R2, and keep the live working set small. **Alarm storm**: many alarms scheduled at the same instant on the same object serialise and delay each other. Correction: jitter the alarm schedule, or move independent work to separate objects.

## Limitations
The specific request-rate and storage-throughput numbers are published by Cloudflare and change over time; this article deliberately avoids quoting them and points to the platform limits documentation instead. The gating model is specific to Durable Objects; the same design on a conventional database with row locks has different deadlock and starvation behaviour. The article assumes the WebSocket-hibernation API is not in use; hibernating sockets change the event delivery model and the throughput calculus. The article does not cover Durable Objects' integration with Queues, which delivers events in batches and changes the batching arithmetic.
