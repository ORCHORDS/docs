# Critical Render Path Preload Vs Http2 Push

## Scope
This article addresses the engineering decision between using `<link rel="preload">` and HTTP/2 server push to optimise the critical rendering path, the timing model behind each technique, and the failure modes that arise when the techniques are applied incorrectly. The scope covers the W3C Resource Hints specification, the IETF HTTP/2 specification (RFC 7540), and the deprecation of HTTP/2 server push in modern browsers. The article is restricted to first-party critical resources; it does not cover third-party preconnect, prefetch, or speculative loading of speculative future navigations. It is concerned with the question: given a resource that is required for first paint, should the server push it on the initial response, or should the document preload it via a hint, or should the developer rely on the preload scanner's default discovery?

## Workflow or implementation guidance
Begin by understanding what each technique actually does. `<link rel="preload">` instructs the browser to fetch a resource as a high priority, before the HTML parser would otherwise discover it; the resource still requires a `<link>` tag in the document body to be applied (for stylesheets, scripts, or fonts). HTTP/2 server push instructs the server to send a resource as part of the same HTTP/2 connection, before the client has requested it; the client may cancel the push if it determines the resource is not needed. The two techniques look superficially similar but operate at different layers: preload is a hint that the browser may ignore; push is a server action that the server may mis-time.

For first-party stylesheets, use `<link rel="preload">` placed in the document `<head>`, paired with the actual stylesheet `<link>` later in the body. The preload causes the stylesheet to be fetched with high priority; the actual stylesheet link applies it. The browser uses the stylesheet immediately, blocking first paint as expected, but the network round-trip is hidden behind the HTML parsing. This pattern works well because the stylesheet is genuinely required for first paint and the developer can declare the dependency explicitly.

For first-party scripts that block parsing, the same pattern applies: `<link rel="preload" as="script">` followed by a `<script>` tag. Where the script is inlined as a module, no preload is needed. Where the script is loaded via a bundler that injects its own `<script>` tags, the bundler should emit the preload; verify that the bundled output contains the preload and that the order is correct (preload before script tag).

For HTTP/2 push, the historical recommendation was to push stylesheets, fonts, and other critical resources on the initial document response. In practice, server push has been deprecated in Chrome and Firefox because of a fundamental race condition: the server pushes resources based on its prediction of what the browser needs, but the browser may have already started fetching them from the HTML parser's preload scanner. When the server's push and the browser's fetch overlap, the browser cancels one of them; the net effect is wasted bandwidth and connection capacity, and in the worst case a pushed resource arrives before the browser has parsed the HTML element that uses it, causing the browser to wait for a `<link>` tag that has not been parsed yet. Server push should not be used in modern applications; rely on preload, on the preload scanner, and on HTTP/3's reduced head-of-line blocking instead.

For HTTP/1.1 origins, the only critical-resource optimisation is to inline what you can and minimize round-trips. Preload still works on HTTP/1.1 but the connection is single-threaded, so a preloaded resource blocks the document fetch. Use preload sparingly on HTTP/1.1 and prefer inlining for small resources.

Use `crossorigin` correctly on preload for fonts. A font loaded with `crossorigin` attribute on the preload tag is fetched with CORS, matching the CORS request the browser will issue when applying the font; without `crossorigin`, the preload fetches without CORS and the actual font fetch (which is CORS) issues a second request, doubling the network cost. The pattern is `<link rel="preload" href="/font.woff2" as="font" type="font/woff2" crossorigin>`.

Avoid preloading resources that are not used on every page view. A preload is a strong hint that the resource is required; if the resource is only used on some page views, the preload wastes bandwidth on the views that don't use it. Use `media` and `imagesrcset` attributes to make preloads conditional on the viewport or the image source.

## Controls
Define three categories of control. The first is a **resource-waterfall audit**: for representative page templates, capture the network waterfall in WebPageTest or Chrome DevTools and identify resources that are fetched after first paint but before they are needed. The second is a **preload effectiveness check**: confirm via the Resource Timing API that preloaded resources were used within the same navigation and not re-fetched. The third is a **bundle audit**: verify that the build pipeline emits the preload tags in the correct order and that no preload tag references a resource that is not actually present in the document.

A useful guardrail metric is the **preload-to-use ratio**: the number of preloaded resources that are actually used in the page, divided by the total number of preloads. A ratio below 0.8 indicates the preloads are over-eager and wasting bandwidth.

## Validation evidence
The validation evidence is a controlled comparison of the network waterfall with and without preload, captured under a slow-3G throttling profile. The expected outcome is that preload pulls forward the resource fetch by 100–300 ms (one round-trip on a typical mobile network), and the document's first paint occurs once the preloaded resource is available. Verify that the preload is honoured by the browser (the resource is in the network panel's high-priority lane), that the resource is used (it appears in the Resource Timing API's `initiatorType`), and that no duplicate fetch occurs. Document the network timing for the preload and the matched resource, the order of the preload and the using element, and the `crossorigin` attribute presence where required.

## Failure modes and correction
**Preload not honoured**: the browser fetches the resource twice—once on preload and once on the actual `<link>` tag. Correction: ensure the `as` attribute matches the resource type (e.g., `as="font"` for fonts), add `crossorigin` for CORS-fetched resources, and verify the `type` attribute matches the resource's MIME type. **Server push still enabled**: the origin is configured to push resources on HTTP/2, but the browser discards them. Correction: disable HTTP/2 server push at the origin; modern browsers ignore it and the bandwidth is wasted. **Preload of an inline resource**: the developer preloads a script that is also inlined; the preload fetches a separate copy. Correction: remove the preload for inlined resources. **Preload blocks a more important fetch**: the preload tag is so aggressive that it preempts the document's own fetch. Correction: use `<link rel="preload">` for resources that are loaded after the document, not for the document itself, and verify the order with a waterfall capture. **Wrong MIME type on preload**: the `type` attribute does not match the resource, and the browser does not honour the preload as a high-priority fetch. Correction: set the correct MIME type on the preload and verify it matches the resource's Content-Type header.

## Limitations
The article assumes the resource is hosted on the same origin as the document. Cross-origin preloads require CORS and a matching `crossorigin` attribute; the article covers the most common cases but not all of them. The article does not cover HTTP/103 Early Hints, which is a server-driven preload mechanism that operates at the HTTP layer rather than the HTML layer; Early Hints is the modern replacement for HTTP/2 server push and is mentioned only briefly. The article does not cover the preload scanner's behaviour in detail; the scanner is what makes `<script>` tags in the body of an HTML document start downloading before the parser reaches them, and the interaction between scanner discovery and explicit preloads is nuanced. The article assumes modern browsers (Chrome 50+, Firefox 44+, Safari 11+); older browsers may ignore preloads entirely.
