# Ab Test Velocity Distortion Web Vitals

## Scope
This article addresses how A/B testing platforms distort client-side Web Vitals measurements when variants are served asynchronously, and how to attribute a metric to the correct user-assigned bucket. The scope covers the Interaction to Next Paint (INP), Largest Contentful Paint (LCP), and Cumulative Layout Shift (CLS) indicators, the moment a hydration-script-driven variant swap occurs, and the timing relationship between the user's first paint and the experiment framework's mutation of the DOM. It also covers the velocity at which an experiment reaches statistical significance in production traffic and the way that velocity—together with the per-user randomization unit—can compress or stretch the apparent performance of each variant into a metric that no longer reflects the user-visible experience. The article is concerned with measurement, attribution, and experiment-design guardrails; it does not cover the underlying statistics of hypothesis testing or the operational rollout mechanics of feature flags.

## Workflow or implementation guidance
Begin by establishing a measurement window per variant that begins at the earliest possible user-visible event, not at the moment the experiment SDK reads its bucket. Most production A/B systems store the assigned variant on the client and apply it only after hydration; if INP is measured from `navigationStart` but the variant is applied 600 ms later, every recorded INP for variant B is contaminated with control behaviour on the first interaction. The correct window is from the first input the user actually performs after the variant takes effect, or—if the test changes layout—strictly after the variant's first paint. Build a per-variant `performance.mark` at the moment the variant renders, and subtract any pre-variant input latency from the INP calculation.

Second, separate the variant-assignment request from the variant-application request. Many A/B SDKs block on a synchronous `XMLHttpRequest` to a configuration endpoint during page load; that request lengthens the long-task tail and is itself a treatment. Move the assignment to a fetch in the document head, stream the configuration as a script, and apply variants via class toggles on `documentElement` rather than waiting for the full DOM. This removes the assignment round-trip from the critical rendering path and decouples the user's timing data from the experiment infrastructure.

Third, align the experiment's randomization unit with the measurement unit. If users are bucketed by `anonymous_id` but page views are the metric, you will undercount because one user's three page views share one bucket. Conversely, if you bucket by `page_view_id` but measure per-user, the same user lands in different variants across visits and the metric becomes meaningless. Decide whether the experiment is per-session, per-user, or per-event, and propagate that decision into the analytics pipeline.

Fourth, design the test for statistical power before launch. A 2% LCP improvement is detectable only with a sample size large enough that the variant receives roughly 100,000 sessions at p95 INP under 200 ms; running the test until a significance threshold is crossed without a pre-registered duration leads to peeking, which inflates the false-positive rate. Use a power calculator, fix the experiment duration in advance, and only inspect results at the pre-set checkpoint.

Fifth, isolate the variant's effect on Web Vitals from the variant's effect on rendering path. A test that moves a button from the right rail to a header slot will change CLS because of the layout shift during hydration; the metric change is caused by the variant itself, not by performance work. To distinguish "the variant is slow" from "the variant is expensive to render," measure CLS from `domInteractive` rather than `loadEventStart`, and track the layout-shift score before and after the variant's first paint in separate metrics.

## Controls
Define three categories of control. The first is a **measurement control**: a small fraction of users (typically 1–5%) receive a no-op variant that exercises the full experiment pipeline without changing the UI. The difference between the control and the production control reveals the overhead the A/B SDK itself introduces; this delta must be subtracted from every active variant before drawing conclusions. The second is a **timing control**: a guardrail metric that bounds the maximum acceptable INP or LCP regression per variant, typically 50 ms or 5%—whichever is stricter. The third is a **flicker guard**: ensure the variant's first paint matches the assigned variant within one frame; visible flicker inflates CLS and biases user-perceived speed independently of true render time.

Configure the A/B platform to emit the assigned variant with each performance beacon, and reject beacons where the variant tag is missing or arrives after the metric's first event. This prevents the "unassigned" bucket from absorbing late-arriving data and dominating the metric when the assignment endpoint is slow. Use server-side rendering of the variant tag for the first contentful paint and client-side enrichment for everything after; this minimizes the window in which variant attribution is ambiguous.

## Validation evidence
The recommended validation evidence is a side-by-side comparison of Web Vitals distributions per variant at fixed traffic splits, captured through a Performance Observer in the browser and tagged with the variant at observation time. Compare the p50, p75, p95, and p99 of LCP and INP across variants, with a Kruskal–Wallis or Mann–Whitney U test on the per-user distributions rather than means. Confirm the no-op control matches the production control within the 95% confidence interval; if not, the A/B SDK is itself a performance treatment and the test must be redesigned. Document the per-variant sample size, the assignment round-trip latency, the time-to-first-paint for the variant, and the prerendered variant tag presence in the HTML source.

## Failure modes and correction
**Variant-tagging delay**: the A/B SDK writes the assigned variant to `localStorage` only after the first interaction, so the LCP event has no variant attribution. Correction: read the variant at `document_start` from a server-injected `<meta>` tag or a streamed `data-variant` attribute on `<html>`, and write it to a global before any user input is observed. **Hydration-induced layout shift**: variant A renders without a sidebar, variant B adds a 300-px sidebar; the shift inflates CLS for variant B by hundreds of milliseconds. Correction: reserve the sidebar space in the HTML shell regardless of variant, then populate it once the variant is known. **Significant-inflated tail latency**: a variant that uses a heavier chart library extends the long-task tail past the 200-ms threshold. Correction: pre-fetch the heavy module only on idle, or move the chart into a worker; in either case, instrument the input-to-render path to confirm the regression is fixed before re-running the test. **Sample-ratio mismatch**: the analytics pipeline sees 50/50 traffic but the experiment SDK reports 45/55. Correction: investigate the assignment endpoint for timeouts or throttling that drop users into the default bucket; users with slow networks disproportionately land in default, which biases the metric toward slow-user experience.

## Limitations
The technique assumes Web Vitals are the correct success metric for the experiment; if the variant's purpose is to change a downstream conversion event, LCP and INP are guardrails rather than outcomes, and the distortion mechanism is different. The article does not cover server-side experiments, multi-armed bandits, or holdout groups. The mitigation strategies assume a modern browser with the Performance Observer API; older browsers must fall back to a polyfill or be excluded from the experiment. Statistical analysis is described only at a high level; consult a statistician for power calculations and sequential testing corrections if you plan to peek at results during the run.
