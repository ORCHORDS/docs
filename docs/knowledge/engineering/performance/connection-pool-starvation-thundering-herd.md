# Connection Pool Starvation Thundering Herd

## Scope
This article addresses connection pool starvation under load, the canonical failure mode where a downstream resource (database, RPC service, HTTP API) refuses new connections because the pool is exhausted, and the synchronous retries from upstream amplify the condition into a thundering herd. The scope covers pool sizing theory (HikariCP, PgBouncer, database vendor guidance), the interaction between pool size, request concurrency, and per-request latency, and the engineering patterns that prevent starvation from cascading into an outage. It does not cover application-level retry storms in depth, queueing theory, or the operational mechanics of any specific database. The article is concerned with the steady-state pool size that absorbs peak load, the failure modes that arise when steady state is exceeded, and the design decisions that keep the system available when those failure modes occur.

## Workflow or implementation guidance
Begin by measuring the steady-state connection count under production load. A connection pool that is sized for average load will starve under peak; a pool sized for peak will waste resources during troughs. The right approach is to size for a percentile: the p95 or p99 of concurrent in-flight queries, plus a small headroom. HikariCP's documentation recommends a pool size based on the formula `(core_count * 2) + effective_spindle_count` for the database's perspective; the application perspective is the inverse: how many concurrent queries does each application instance issue, multiplied by the number of application instances, must not exceed the database's connection capacity. Both must be checked.

Configure the pool with an explicit maximum wait time. When the pool is exhausted, new requests must either queue or fail fast. Queueing beyond a short bound (typically 50–100 ms) hides the starvation from upstream and converts it into a latency spike; failing fast converts it into a 5xx response that upstream retry logic can handle predictably. HikariCP's `connectionTimeout` should be set to a value that aligns with the upstream's own deadline; longer than the upstream's deadline wastes a request that is about to be aborted anyway; shorter than the upstream's deadline wastes the slot.

Use a connection lifetime cap. Most databases and load balancers benefit from recycling connections periodically: a connection held for an hour may have stale state, an aborted TCP session, or a server-side cursor that has grown unbounded. Configure `maxLifetime` on the order of 30 minutes, with `keepaliveTime` of a few minutes to keep idle connections alive through NAT timeouts. Stagger the lifetime across the pool so connections do not all expire simultaneously; HikariCP's default jitter handles this if `maxLifetime` is configured.

For databases specifically, prefer PgBouncer in transaction-pooling mode over per-application pooling. PgBouncer multiplexes many application connections onto a smaller number of database connections, so the database's connection capacity is not exceeded even if the application pool is large. The trade-off is that session-state features (prepared statements, advisory locks, `SET` statements) must be moved out of the connection and into the transaction, since each transaction may use a different backend connection. With careful schema design, transaction pooling is a major capacity win.

For HTTP dependencies, use a bounded connection pool per upstream. The `undici` library (Node.js), `requests` Session (Python), and `http.Client` (Go) all support a per-host connection cap. Set the cap based on the upstream's published limits: some APIs cap at 50 concurrent connections per API key, others at 10. Exceeding the limit triggers 429 responses that, if retried synchronously, recreate the stampede.

When a downstream is slow but not yet failing, the connection pool fills with slow connections. Detect this condition by monitoring `pool_pending` (the number of requests waiting for a connection). A rising `pool_pending` is the leading indicator of an impending stampede: the application is sending requests faster than the pool can serve them, and as soon as the pool fills, every new request waits for an existing one to release. Mitigate by shedding load upstream: a circuit breaker that returns a 503 when `pool_pending` exceeds a threshold prevents the herd from forming.

Finally, observe the connection acquisition latency. A histogram of `pool_acquire_time` reveals whether the pool is sized correctly. A bimodal distribution (fast for most requests, slow for the tail) indicates that the pool is too small for peak load; a flat distribution indicates the pool is sized correctly. The acquisition latency should be measured and alerted, not derived from a single test.

## Controls
Define three categories of control. The first is a **circuit breaker**: when the downstream's error rate exceeds a threshold or the pool's wait time exceeds the deadline, the application stops sending requests to that downstream for a cooldown period. The circuit breaker prevents a slow downstream from accumulating a queue of waiting requests, each of which would have added load if it had been served. The second is a **bulkhead**: each downstream has its own dedicated pool, so a slow downstream cannot starve the connections intended for a fast one. The third is a **load shedder**: when the application's request rate exceeds a calibrated threshold, the application rejects new requests with a 503 rather than queue them indefinitely.

A useful guardrail metric is the **pool utilisation percentage**: the average number of in-use connections divided by the pool's maximum. A pool that runs at 90% utilisation is one slow query away from starvation; a pool at 50% is over-sized. The target is whatever keeps the acquisition latency flat; the percentage is a proxy, not a target in itself.

## Validation evidence
The validation evidence is a load test that ramps concurrent requests against the pool until the pool saturates, measures the saturation point, and verifies the configured circuit breaker trips at the expected threshold. Run the load test with realistic per-request latency distributions (a mix of fast and slow queries), not just a constant request rate. Confirm the pool recovers quickly when load drops, that no leaked connections remain after the test, and that the database's `pg_stat_activity` (or equivalent) shows the expected number of connections from the application. Document the pool size, the saturation point, the acquisition latency distribution, and the circuit breaker trip threshold.

## Failure modes and correction
**Pool exhausts under burst load**: a sudden spike of requests fills the pool, and subsequent requests time out waiting for a connection. Correction: increase the pool size within the downstream's tolerance, or add a queue with a bounded wait time and shed load beyond the bound. **Connection leak**: an application forgets to release a connection, the pool size shrinks over time, and eventually the pool is exhausted by leaks. Correction: enable `leakDetectionThreshold` (HikariCP) or the equivalent in the client library, and audit the code path that uses the connection for unclosed resources. **Prepared statement cache fills**: a database pool with a per-connection prepared statement cache fills up over time, and new statements evict older ones. Correction: pin prepared statements at the application level rather than relying on the connection's cache, or switch to PgBouncer in transaction-pooling mode where per-connection caches are less useful. **Slow query fills the pool with long-held connections**: one slow query holds a connection for several seconds, and the pool empties as the remaining connections serve the rest of the load. Correction: set a `queryTimeout` so a slow query is killed and its connection released, and identify the slow query for optimisation. **Circuit breaker does not trip**: the downstream is failing but the error rate has not crossed the threshold because errors are spread across many slow requests. Correction: track both error rate *and* latency in the breaker decision, and trip when either exceeds its bound.

## Limitations
The article focuses on application-side pools; database-side pool tuning is mentioned only in the context of PgBouncer. The article assumes a synchronous request-response model; asynchronous systems with backpressure have different failure modes. The recommended pool sizes are starting points, not universal rules; the actual right size depends on the specific workload. The article does not cover connection encryption overhead, TCP keepalive tuning, or DNS resolution latency for the connection endpoint. The article does not address multi-region deployments where connection pools span data centres.
