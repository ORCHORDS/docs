# Analytics Engine Query Latency Budget

## Scope
This article addresses query latency budgeting for Cloudflare Analytics Engine, the time-series analytics product backed by ClickHouse that is available to Workers. The scope is restricted to the SQL API and its query execution path: how long a query takes to return, how the platform parallelises work across shards, how concurrent queries interact with the per-database rate limits, and how to design a Worker that issues analytics queries inside a user-facing latency budget. It does not cover ingestion throughput, the Workers Analytics Engine Dashboard, or the Workers Logs product. The article is concerned with the read path, the SLO a Worker can rely on, and the engineering patterns that keep query latency inside that budget under load.

## Workflow or implementation guidance
Begin by establishing the latency budget you need. The Analytics Engine SQL API is not designed for synchronous, sub-100 ms responses; it is intended for asynchronous analytics queries where a Worker can use `ctx.waitUntil` to amortise the cost, or for end-user queries that tolerate 200–800 ms p95. If you need real-time metrics on the request path, the SQL API is the wrong tool—use Workers Analytics Engine's `writeDataPoint` followed by a rollup read pattern, or precompute aggregates into KV and read them. The SQL API is the right tool when the question is "what was the p99 INP for users in region X over the last 24 hours," not "what was the LCP for this specific user right now."

Once the use case is scoped, design the query so that the database can answer it from a single shard's worth of data within the budget. Analytics Engine partitions data by the first index, so queries that filter on the index column hit one shard and return in tens of milliseconds; queries that scan all shards take proportionally longer. Index columns you will filter on, and place the most selective filter first. Use `WHERE blob1 = ? AND blob2 = ? AND timestamp > ?` with `blob1` as the index, not `WHERE timestamp > ?` alone, because the latter scans every shard in the time window.

For queries that need to span shards, design them as background work. The Worker returns a placeholder response (a 202 Accepted with a request ID) immediately, then issues the cross-shard query in `ctx.waitUntil`, stores the result in KV or R2, and serves subsequent reads from the cache. This pattern amortises a 5-second analytics query over many user requests and matches the platform's strengths: the SQL API is excellent at answering broad questions once and caching the answer, not at answering them on every request.

When issuing a query from a Worker, use the Analytics Engine binding and set a hard timeout on the `fetch` call. The SQL API supports a query timeout via the URL parameter; set it explicitly so a slow query does not block the Worker indefinitely. Use `AbortController` to cancel the fetch when the Worker's own deadline approaches; an aborted query does not return a partial result, but it does free the Worker to fail fast and serve a fallback.

For dashboards that require fresh data every few seconds, consider whether the underlying write pattern supports it. Analytics Engine is a write-optimised store; reads are eventually consistent within a few seconds of the write. If the dashboard needs second-level freshness, the Worker should subscribe to a real-time channel (Durable Objects' WebSocket hibernation, or a third-party stream) rather than polling Analytics Engine.

Finally, profile the query. The SQL API returns query execution statistics in the response headers; capture them, log them to Workers Logs, and review them regularly. A query whose execution time grows linearly with the time window is a candidate for a rollup table or a narrower WHERE clause; a query whose bytes scanned grows linearly with the number of unique blobs is a candidate for a higher-cardinality index.

## Controls
Define three categories of control. The first is a **per-Worker concurrency limit**: cap the number of in-flight Analytics Engine queries a single Worker instance can issue at any time, using a small in-process semaphore. Cloudflare's edge schedules many requests onto one isolate; without a cap, one slow query can starve every other request the isolate serves. The second is a **circuit breaker**: if the p95 query latency exceeds the budget for N consecutive queries, the Worker stops issuing Analytics Engine queries for a cooldown period and serves a cached or default response. The third is a **budgeted cache**: every query result has an explicit TTL based on the data's acceptable staleness, and the Worker reads from the cache before issuing a query. The cache key should include the query parameters and a version stamp so a schema change invalidates the cache.

A useful guardrail metric is the **query-byte budget**: the total bytes scanned across all queries issued by a Worker in a window, divided by the number of requests served. If this metric grows faster than traffic, the Worker is over-scanning; investigate whether the WHERE clauses have become less selective or whether the index choice is still optimal.

## Validation evidence
The validation evidence is a controlled query latency benchmark: issue the production query set against the production Analytics Engine dataset at a representative time window, measure the median, p95, and p99 latency, and compare against the budget. Run the benchmark at three traffic levels (low, medium, peak) and three time windows (one hour, one day, one week) to characterise the latency surface. Capture the query execution statistics from the response headers: bytes scanned, partitions read, rows returned. Confirm that the bytes scanned does not grow proportionally with the time window for queries that filter on an index column. Document the per-query p99 against the SLA, the cache hit rate, and the number of queries aborted due to timeout.

## Failure modes and correction
**Query times out at p99**: the dataset has grown past the budgeted size and the query now scans too many partitions. Correction: add an index on the most selective filter, narrow the time window, or precompute the aggregate into a rollup dataset and query the rollup instead. **Worker isolate CPU exhaustion**: a single Worker handles many parallel queries and the isolate's CPU budget is exhausted before the queries complete. Correction: lower the per-Worker concurrency limit, offload long-running queries to a Durable Object, or move them entirely to `ctx.waitUntil` so they do not count against the isolate's response-time budget. **Cache stampede on a popular query**: a query whose result is cached but expires triggers a thundering herd of cache misses as soon as the TTL elapses. Correction: stagger the cache TTL with jitter, serve stale results while a single background query refreshes, or use probabilistic early expiration. **Stale data served as fresh**: the cache TTL is longer than the data's acceptable staleness, so users see outdated metrics. Correction: shorten the TTL to match the data's freshness requirement, and add a version stamp to the cache key so a backend recompute invalidates the cache proactively. **SQL API quota exceeded**: the Worker issues more queries per minute than the per-database quota allows, and subsequent queries return 429. Correction: aggregate queries at a coarser granularity (one query per minute per Worker instead of one per request), back off on 429 with exponential delay, and add a per-Worker rate limiter that respects the platform quota.

## Limitations
The article is specific to Cloudflare Analytics Engine; the latency characteristics do not transfer to other time-series databases. The benchmarks assume the Workers paid plan; the free tier has stricter rate limits that change the achievable p99. The article does not cover the cost model: queries are billed by bytes scanned, not by execution time, and a slow query may be cheap while a fast query over a large dataset may be expensive. The article also does not cover the Workers Analytics Engine Dashboard, which has its own query execution path independent of the SQL API.
