# TypeScript Declaration Merging for Cloudflare Workers `Env` Interface

Date: 2026-08-24 / Author: example.com / Status: production

---

## Symptom / Use-case

A monorepo has twelve Worker packages that each bind a different subset of KV namespaces, D1 databases, and service bindings. Maintaining a separate hand-written `Env` interface per package causes drift — bindings are added to `wrangler.toml` but not to the TypeScript type, leading to runtime `undefined` surprises that TypeScript should have caught.

## Context

The TypeScript compiler's *declaration merging* feature allows multiple `interface` declarations with the same name to be merged into one. Combined with `declare module` augmentation and `wrangler types` auto-generation, you can layer binding types: a generated base interface lives in the package root, shared bindings live in a workspace-level `env.d.ts`, and package-specific additions augment via module declaration — all without a single copy-paste.

## Auto-generating the Base `Env` from `wrangler types`

```bash
# Run once per wrangler.toml change (or in a postinstall / codegen script)
npx wrangler types --env-interface Env --output-path src/generated/env.d.ts
```

Generated output (example):

```typescript
// src/generated/env.d.ts  — DO NOT EDIT — generated by wrangler types
export {};
declare global {
  interface Env {
    MY_KV: KVNamespace;
    DB: D1Database;
    ASSET_BUCKET: R2Bucket;
    API_SECRET: string;
  }
}
```

Commit this file and regenerate whenever `wrangler.toml` bindings change.

## Shared `env.d.ts` and Per-Package Augmentation

```typescript
// packages/shared-types/src/env.d.ts
// Base interface — shared bindings all Workers have
export interface Env {
  LOG_LEVEL: string;
  ENVIRONMENT: 'development' | 'staging' | 'production';
}
```

```typescript
// packages/api-worker/src/env.d.ts
// Augment the shared Env with bindings specific to this Worker
import type { Env as BaseEnv } from '@example-org/example-repo/src/env';

declare module '@example-org/example-repo/src/env' {
  interface Env {
    USER_KV: KVNamespace;          // only this Worker needs user storage
    AUTH_SERVICE: Fetcher;         // service binding to auth-worker
    RATE_LIMIT: RateLimit;         // Workers Rate Limiting binding
  }
}

// Re-export so consumers import from a single place
export type { Env };
```

```typescript
// packages/api-worker/src/index.ts
import type { Env } from './env';

export default {
  async fetch(request: Request, env: Env): Promise<Response> {
    // env.USER_KV, env.AUTH_SERVICE, env.LOG_LEVEL — all typed
    const level = env.LOG_LEVEL;              // string — from shared
    const kv = env.USER_KV;                  // KVNamespace — from augmentation
    const auth = env.AUTH_SERVICE;           // Fetcher — from augmentation
    return new Response('ok');
  },
};
```

## `IntersectionEnv<A, B>` for Service Binding Composition

When a Worker composes multiple binding groups (e.g., analytics bindings + storage bindings), intersection types provide a clean alternative to declaration merging:

```typescript
// packages/shared-types/src/composition.ts
import type { Env as StorageEnv } from './storage-env';
import type { Env as AnalyticsEnv } from './analytics-env';
import type { Env as BaseEnv } from './env';

// Utility: compose N binding groups
export type IntersectionEnv<A, B> = A & B;
export type ComposedEnv = IntersectionEnv<BaseEnv, IntersectionEnv<StorageEnv, AnalyticsEnv>>;

// packages/reporting-worker/src/index.ts
import type { ComposedEnv } from '@example-org/example-repo/src/composition';

export default {
  async fetch(request: Request, env: ComposedEnv): Promise<Response> {
    // env has all bindings from all three groups
    await env.ANALYTICS_KV.put('event', JSON.stringify({ ts: Date.now() }));
    return new Response('logged');
  },
};
```

Prefer `IntersectionEnv` when groups are stable and independently versioned; prefer declaration merging when you want additive contributions from unrelated packages.

## Wiring Up `tsconfig.json` to Pick Up the Generated File

```jsonc
// packages/api-worker/tsconfig.json
{
  "extends": "../../tsconfig.base.json",
  "compilerOptions": {
    "types": [],            // prevent auto-including @types/*
    "typeRoots": ["./node_modules/@types"],
    "paths": {
      "@example-org/example-repo/*": ["../../packages/shared-types/src/*"]
    }
  },
  "include": [
    "src/**/*.ts",
    "src/generated/env.d.ts"   // explicitly include generated types
  ]
}
```

## Why Declaration Merging Beats Manual Copy-paste

| Approach | Binding added to `wrangler.toml` | Type safety | Maintenance |
|---|---|---|---|
| Manual copy-paste | Developer must update each package's `Env` | Drifts silently | High |
| Declaration merging + `wrangler types` | Regenerate → base updates automatically | Immediate TS error | Low |
| Intersection types | Same as above for composed groups | Immediate TS error | Low |

## Anti-patterns

- **Augmenting `global` directly** — `wrangler types --env-interface Env` uses `global` augmentation, but project-level augmentation should use `declare module` to avoid polluting every file in the repo.
- **Duplicate binding declarations** — if the generated `env.d.ts` and a hand-written file both declare `MY_KV: KVNamespace`, TypeScript merges them without error but the duplication causes confusion. Regenerate the file and delete manual copies.
- **Using `type` instead of `interface`** — `type` aliases cannot be merged; always use `interface Env` for declaration merging targets.
- **Committing `src/generated/` to `.gitignore`** — generated types must be committed so that CI without a codegen step still has them.

## Gotchas

- `wrangler types` requires `@cloudflare/workers-types` to be installed; the generated file imports from it.
- When augmenting a module, the path string in `declare module '…'` must exactly match the import path the consuming file uses, including whether it is relative or a package name.
- TypeScript merges interface members but does not check for conflicts: if two augmentations both declare `MY_KV` with different types, the compiler picks the last declaration silently. Use unique binding names across packages.
- `declare module` augmentation only works when the base module actually exports the interface. A `declare global { interface Env }` cannot be augmented via `declare module`.

# Regenerate types and check for TypeScript errors
