# MISP Threat Intelligence Sharing Playbook

## Purpose
This playbook describes how to stand up and operate a MISP instance for internal threat intelligence collection, automated ingestion from external feeds, STIX 2.x exchange with partner platforms, and integration with EDR, SIEM, and the Zeek intel framework. It covers initial deployment, daily operations, and incident handling so that analysts have a single source of truth for configuration, ingestion, and downstream exchange.

## Audience
Threat intelligence engineers, SOC analysts, detection engineers, and platform engineers responsible for deploying, operating, and consuming the MISP platform. Secondary readers include incident responders and red team operators who rely on MISP-sourced indicators during active investigations and purple team exercises.

## Pre-conditions
- MISP 2.4.x installed on a hardened Linux host with time synchronisation and host-based firewall rules
- Redis cache and MySQL back-end configured, tuned, and protected by TLS where supported
- Sync user account provisioned with a dedicated API key stored in a managed secret store
- MISP taxonomies and galaxies installed from the official repositories and pinned to a known version
- Ingestion feeds preconfigured, for example the CIRCL OSINT feed, with GPG signature validation enabled
- OpenCTI available optionally for STIX 2.x exchange and graph-based correlation
- Zeek intel framework reachable on the sensor network with the MISP intel file format supported
- EDR solution deployed with a documented MISP event ingest endpoint and supported attribute types

## Procedure
1. Initialise the MISP database schema, create the admin user, and set a strong passphrase generated by the managed secret store. Rotate on a documented cadence and revoke any temporary bootstrap credentials.
2. Install taxonomies, galaxies, warninglists, and noticelists from the official MISP repositories and pin their versions in the configuration to avoid silent drift.
3. Configure user roles and sharing groups so that only authorised analysts can publish events or push indicators of compromise to downstream systems.
4. Connect upstream feeds via the feed management UI or via a scheduled `misp-feed` cron job, validating fetch cadence, content hash, and GPG signature on every pull.
5. Configure server-to-server sync with trusted partners by exchanging hostnames, certificate fingerprints, sharing group identifiers, and pull-only versus push-only modes.
6. Set up the STIX 2.x export pipeline for OpenCTI and downstream consumers, confirming that bundle UUIDs match the source MISP event UUIDs and that custom objects are mapped correctly.
7. Wire MISP to EDR via the push API for indicators of compromise, enforcing tag and TLP filtering at the export rule and excluding sensitive infrastructure attributes that should not leave the trust boundary.
8. Publish MISP events to TheHive for case creation through the modular alerting pipeline, mapping event attributes to observables, tasks, and TTPs so that responders have immediate context.
9. Configure correlation thresholds and warninglist behaviour so that known-clean indicators do not generate spurious alerts, and review the false positive queue weekly with detection engineers.
10. Schedule a daily backup of the MySQL database and signed zip archives of attachments, writing checksums to immutable storage with a thirty-day retention window and quarterly restore drills.
11. Schedule a weekly review of stale events, broken feeds, and warninglist drift, with tickets routed to the intel queue and assigned to the on-call engineer.
12. Document and hand over to the threat intel on-call, including runbooks at `docs/runbooks/misp-oncall.md:1` and key rotation cadence at `docs/runbooks/misp-key-rotation.md:1`.

## Rollback
Disable all server-to-server sync and feed pulls, isolate the MISP host at the network layer with an emergency firewall rule, retain indicators of compromise in an offline archive with detached signatures, and notify sharing partners of the outage and expected restoration window before any reconnection. Preserve MySQL backups and configuration snapshots for post-incident review and forensic analysis.
