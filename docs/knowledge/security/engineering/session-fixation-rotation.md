# session-fixation-rotation

**Issue:** Session fixation (CWE-384) is an attack in which the adversary establishes a known session identifier inside the victim's browser, then waits for the victim to authenticate, at which point the application continues using the attacker-known ID and the attacker hijacks the now-authenticated session. The vulnerability exists whenever an application accepts a session ID that was not generated by the server at the moment of privilege change: identifiers propagated through URLs, subdomains, untrusted flows, or pre-login cookies that survive authentication. The complementary discipline is rotation: even without fixation, failing to refresh identifiers at privilege transitions allows stolen pre-auth tokens, network-captured IDs, and XSS-exfiltrated cookies to remain valid after login, reauthentication, or privilege escalation. Correct session lifecycle management is therefore a two-part requirement: only the server issues IDs, and every privilege change issues a new one.

## How fixation happens

1. **URL-propagated identifiers.** When the app accepts session IDs from query strings or path segments, an attacker crafts a link containing a known ID, the victim logs in through it, and the ID is now authenticated; this also leaks IDs through links, logs, and the Referer header.
2. **Cookie injection from sibling subdomains.** If the session cookie is scoped to the parent domain, a compromised or attacker-controlled subdomain can set a known session cookie that the main application later honors after login.
3. **Pre-login cookies reused post-login.** Anonymous session cookies created on first visit that are simply upgraded to authenticated state on login keep whichever value was in place before the user proved identity, preserving any attacker-planted value.
4. **Middleware and framework defaults.** Some frameworks only create a session lazily or keep the same ID across authentication events unless regeneration is called explicitly, so the default behavior is fixation-prone until configured.

## Rotation requirements

1. **Regenerate on every privilege change.** Issue a fresh, cryptographically random session ID at login, reauthentication, password change, MFA enrollment, and any admin-role elevation; the old ID must be invalidated server-side, not merely replaced in the cookie.
2. **Server-only issuance.** Accept session IDs exclusively from the secure cookie the server set; ignore IDs arriving in URLs, form fields, or headers, and generate a new one whenever an unrecognized or expired ID is presented.
3. **High-entropy identifiers.** Use at least 64 bits, preferably 128 bits, from a cryptographically secure random generator with no predictable structure, making brute force and prediction infeasible even at scale.
4. **Invalidate the old session atomically.** Store server-side session state keyed by ID so rotation can delete or tombstone the old record; without server-side invalidation, a replaced cookie leaves the old ID usable until natural expiry.
5. **Concurrent session awareness.** On password change or security-event rotation, invalidate all other sessions for the account, not just the current one, since an attacker may hold a parallel session.

## Cookie and transport hardening

1. **Scoped, flagged cookies.** Set HttpOnly, Secure, SameSite=Lax or Strict, and a host-only Domain attribute so scripts, plaintext networks, cross-site flows, and sibling subdomains cannot read or plant the session cookie.
2. **Session ID never leaves the cookie.** Never echo session IDs in page HTML, JSON responses, redirects, or logs; every additional surface is both a leak and a fixation vector.
3. **Absolute and idle timeouts.** Enforce a hard absolute lifetime requiring reauthentication and an idle timeout that terminates dormant sessions; short ceilings bound the value of any fixed or stolen ID.
4. **Binding signals for high-risk accounts.** For privileged roles, consider binding sessions to a fingerprint of stable request properties and forcing reauthentication on significant change, raising the cost of replaying a rotated-away token.

## Implementation and testing

1. **Framework-native rotation APIs.** Use the platform's session regeneration primitive rather than overwriting the cookie value manually, so the session store and identifier stay consistent under concurrency.
2. **Fixation regression tests.** Automated tests should pre-plant a known session ID via cookie and URL, authenticate, and assert the server issued a different ID and refuses the planted one afterward.
3. **Rotation audit in CI.** Grep-level checks and integration probes should fail builds where authentication routes do not call the regeneration API, catching silent regressions when auth code is refactored.
4. **Monitoring for anomalous lifecycle events.** Alert on authentication events that reuse an existing session ID, on the same ID suddenly changing IP or user agent, and on one account presenting multiple simultaneously valid IDs after a rotation trigger.
