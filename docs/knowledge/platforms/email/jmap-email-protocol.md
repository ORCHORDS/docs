# jmap-email-protocol

**Issue:** IMAP is a 1980s-descended protocol whose quirks — half-duplex command tagging, multiple concurrent connections to parallelize fetches, 57 flags, UTF-7 mailbox names, and the disconnected-operation sync model bolted on by clients — make automated email clients slow, fragile, and expensive to run. JMAP (JSON Meta Application Protocol, RFC 8620 core + RFC 8621 mail, standardized 2019 out of Fastmail's work) replaces it with a modern JSON-over-HTTPS API: batched method calls in one request, state-synced data objects, efficient delta fetching, and native push. Adoption as of 2025 remains niche — Fastmail is the reference implementation, Stalwart (open-source Rust server) fully supports it including JMAP-over-WebSocket (RFC 8887), Cyrus implements it, but Gmail/Outlook expose no JMAP endpoint and mainstream clients (Thunderbird, Apple Mail) have not adopted it. For agent and automation workloads where you control both client and server, it is dramatically saner than IMAP.

## Core protocol model

1. **Everything is a JMAP resource with a session document.** Clients start at a well-known URL (/.well-known/jmap) and get a Session object: accounts, the capabilities each supports (urn:ietf:params:jmap:mail, :core, :submission, :websocket), and per-object API/download/upload endpoints. Capabilities are versioned and negotiated per account, so feature-detection is built into the hello handshake instead of probing CAPABILITY strings.
2. **Method calls are batched into a single HTTP POST.** A request carries an array of invocations (method + arguments + client-generated call id) executed in order, and one call can back-reference results of a previous call in the same batch — e.g., Email/query for ids, then Email/get with the result as the ids argument, in one round trip. This batching is the core performance win: where IMAP needs dozens of sequential commands (and often multiple connections), JMAP does it in one request.
3. **Data is object-store synced by state string, not flag-diffed.** Every account has a state token that changes when any object of a type changes; clients store per-object state and request only deltas (created/updated/destroyed since their state). This replaces IMAP's CHANGEDSINCE/CONDSTORE-and-hope model and is exactly the primitive an idempotent agent checkpoint wants: persist the state string, resume later, receive only what changed.
4. **Blob handling is separate from structure.** Attachments and raw messages are blobs with their own download endpoints (resumable, ranged); Email objects reference blob ids for raw bodies. Fetching the parsed structure and fetching the bytes are independent, so metadata syncs stay cheap while heavy attachments are fetched on demand.

## Mail data model

1. **Mailbox, Thread, and Email are first-class objects with stable ids.** Threads are server-computed (Gmail-style conversation grouping without client heuristics); Mailboxes carry role properties (inbox, archive, trash) so folder-name localization stops breaking automation; Email objects carry mailboxIds, keywords (per-user flags like $seen, $flagged), and server-assigned immutable ids. No more matching on mailbox name strings across locales.
2. **bodyValues solves the HTML-body problem.** Instead of clients downloading the full MIME tree and re-implementing parsing to render text, Email/get can return bodyValues: server-extracted text/plain and text/html values, optionally only the body parts (isEncodingProblem, isTruncated flags included). For agents that need to read mail, this deletes an entire IMAP-era subsystem — no more BODYSTRUCTURE parsing and quoted-printable decoding by hand.
3. **Identity and submission are explicit.** RFC 8621's Identity object separates who you send as from the account, and the submission capability (MailSubmission) tracks envelope, submission status, and per-recipient delivery status (with DSN/MDN reasoning exposed as structured data). Sending mail through JMAP uses the same object model as reading it — no separate SMTP client with its own auth stack.
4. **Vacation responses, search, and sieve are capability-optional.** Extensions exist for vacations (autoreplies) and Sieve script management as JMAP objects, and Email/query implements server-side search filters (from, subject, keyword, mailbox scope, date ranges) as structured filter objects rather than IMAP SEARCH string mini-languages.

## Push and realtime

1. **Push subscriptions deliver change notifications without long-poll IMAP.** Clients register a push callback (webhook-style) with verification handshake; the server pushes a state-change event (which types changed, not the data) and the client then pulls deltas. For server-side agents this is the cleanest integration: your webhook receives "mail changed," you sync one account state, done.
2. **EventSource streaming is the interactive-client push.** The JMAP EventSource capability streams typed change events over an HTTP event stream; RFC 8887 defines JMAP over WebSocket for lower-overhead bidirectional use, which Stalwart implements. Interactive clients get sub-second updates without the multi-connection IDLE hack.
3. **Backoff and loss are designed in.** Because the state string is the sync anchor, a missed push costs nothing — the next sync returns the full delta. Push delivery failures degrade to polling without protocol-level divergence, unlike IMAP where a dropped IDLE connection is silently stale until a NOOP reveals new mail.

## Adoption status and when to choose it

1. **Server side: Fastmail (reference), Stalwart (full, including WebSocket), Cyrus.** Self-hosting Stalwart gives a complete JMAP mail platform (SMTP + JMAP + IMAP fallback) — the most practical path to JMAP for a private automation stack today. Exchange, Gmail, and most hosting providers remain IMAP/JMAP-absent, so JMAP-only tooling cannot reach mainstream mailboxes.
2. **Client side: still thin, plan to write your own.** Fastmail's apps, a handful of third-party clients, and CLI/library tooling exist (jmap-client libraries in TypeScript/Python/Rust), but Thunderbird, Apple Mail, and Outlook show no adoption — Nextcloud Mail's JMAP support is still an open feature request. The realistic 2025-2026 pattern: JMAP where you control both ends (agent mailbox, product-owned receiving domain), IMAP as the compatibility fallback elsewhere.
3. **Hybrid architecture is the pragmatic answer for agents.** Point the JMAP path at a JMAP-capable mailbox you own for high-volume ingestion (fast delta sync, structured bodies, push), and gateway legacy providers through IMAP-to-JMAP bridges or an ingestion relay into the same object model. Normalize both into your internal Email/Thread representation so downstream code is protocol-agnostic.
4. **Evaluate against your actual bottleneck.** JMAP's wins are largest for: high-mailbox-count automation (batch + delta), unreliable networks (one request, idempotent resync), and body-parsing-averse clients (bodyValues). If your workload is "poll one inbox once a minute," IMAP IDLE is adequate and JMAP is a nicety; at thousands of mailboxes or sub-second reaction requirements, the protocol choice becomes architectural.
