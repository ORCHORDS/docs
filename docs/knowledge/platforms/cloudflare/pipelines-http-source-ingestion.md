# Cloudflare Pipelines HTTP Source Ingestion

Date: 2026-08-23
Author: example.com
Status: production

## Symptom / Use-case

You want to ingest event streams, webhook payloads, or log records from external services
directly into a Cloudflare Pipeline — without writing a Worker to receive and forward the
data. Cloudflare Pipelines support an HTTP source endpoint that accepts JSON payloads and
writes them to R2 (or D1) without any intermediate Worker code.

## Context

Cloudflare Pipelines (GA 2025) is a managed data ingestion service. A Pipeline has:

- **Source**: where data enters (HTTP endpoint or a Workers binding).
- **Transform** (optional): a Worker that mutates or filters records mid-flight.
- **Sink**: where data lands (R2 bucket in NDJSON/Parquet, or D1 table).

The HTTP source gives each Pipeline a unique HTTPS URL that accepts `POST` requests with
`Content-Type: application/json` or `application/x-ndjson`. External services — Stripe
webhooks, GitHub webhooks, IoT sensors — can POST directly to this URL without any
intermediary Worker.

Authentication to the HTTP source uses an API token or a shared secret header that you
configure on the Pipeline. The endpoint is rate-limited at 10 MB/s per Pipeline by default.

## 1. Creating a Pipeline with an HTTP Source via Wrangler

```toml
# wrangler.toml (pipelines are defined here for wrangler pipelines commands,
# not as a Workers binding in this flow)
# Pipeline config is typically managed via wrangler CLI or Terraform
```

```bash
# Create a pipeline with HTTP source and R2 sink
wrangler pipelines create my-events-pipeline \
  --source http \
  --r2-bucket my-events-bucket \
  --batch-max-mb 10 \
  --batch-max-seconds 30

# Outputs:
# Pipeline ID: <pipeline-id>
# HTTP Source URL: https://pipelines.cloudflare.com/v1/<account-id>/my-events-pipeline
# HTTP Source Token: <auto-generated-bearer-token>
```

Save the HTTP Source URL and token — they are shown only once at creation. Rotate the
token with `wrangler pipelines rotate-token my-events-pipeline`.

## 2. Posting Events to the HTTP Source

Any HTTPS client can now send events to the pipeline URL. The body must be a single JSON
object or a newline-delimited JSON (NDJSON) stream.

```typescript
// Example: a Node.js/Bun webhook relay forwarding GitHub events
const PIPELINE_URL = process.env.CF_PIPELINE_URL!;
const PIPELINE_TOKEN = process.env.CF_PIPELINE_TOKEN!;

async function forwardWebhook(payload: unknown): Promise<void> {
  const res = await fetch(PIPELINE_URL, {
    method: 'POST',
    headers: {
      'Content-Type': 'application/json',
      Authorization: `Bearer ${PIPELINE_TOKEN}`,
    },
    body: JSON.stringify({
      ...payload as object,
      _ingestedAt: Date.now(),
    }),
  });

  if (!res.ok) {
    const text = await res.text();
    throw new Error(`Pipeline rejected event: ${res.status} ${text}`);
  }
}
```

## 3. Batched NDJSON Ingestion

For high-volume sources, POST NDJSON (one JSON object per line) to maximise throughput
and reduce per-request overhead.

```typescript
async function sendBatch(events: unknown[]): Promise<void> {
  const ndjson = events.map(e => JSON.stringify(e)).join('\n');

  const res = await fetch(PIPELINE_URL, {
    method: 'POST',
    headers: {
      'Content-Type': 'application/x-ndjson',
      Authorization: `Bearer ${PIPELINE_TOKEN}`,
    },
    body: ndjson,
  });

  if (!res.ok) {
    throw new Error(`Batch rejected: ${res.status} ${await res.text()}`);
  }
}

// Accumulate events and flush every 5 seconds or 500 records
class EventBuffer {
  private buf: unknown[] = [];
  private timer: ReturnType<typeof setInterval>;

  constructor(private flushFn: (events: unknown[]) => Promise<void>, intervalMs = 5000) {
    this.timer = setInterval(() => this.flush(), intervalMs);
  }

  push(event: unknown) {
    this.buf.push(event);
    if (this.buf.length >= 500) this.flush();
  }

  async flush() {
    if (!this.buf.length) return;
    const batch = this.buf.splice(0);
    await this.flushFn(batch);
  }

  destroy() { clearInterval(this.timer); }
}
```

## 4. Validating and Enriching Events via a Transform Worker

Attach a transform Worker to the Pipeline to validate schema, drop PII, or enrich records
before they land in R2. The transform Worker receives a batch of records and returns the
modified batch.

```typescript
// transform-worker/src/index.ts
export interface PipelineRecord {
  _ingestedAt: number;
  event: string;
  userId?: string;

}

export default {
  async transform(
    records: PipelineRecord[],
    controller: TransformStreamDefaultController
  ): Promise<void> {
    for (const record of records) {
      // Drop records missing required fields
      if (!record.event) continue;

      // Mask PII before writing to R2
      if (record.userId) {
        record.userId = await sha256Truncate(String(record.userId));
      }

      // Enrich with geo tag from a header injected by Cloudflare
      record._source = 'http';
      record._processedAt = Date.now();

      controller.enqueue(record);
    }
  },
};

async function sha256Truncate(input: string): Promise<string> {
  const buf = await crypto.subtle.digest('SHA-256', new TextEncoder().encode(input));
  return [...new Uint8Array(buf)].slice(0, 8).map(b => b.toString(16).padStart(2, '0')).join('');
}
```

Reference the transform Worker in `wrangler.toml`:

```toml
[[pipelines]]
name = "my-events-pipeline"
source = [{ type = "http" }]
transforms = [{ script = "transform-worker" }]

[[pipelines.destination]]
type = "r2"
format = "ndjson"
bucket = "my-events-bucket"
prefix = "events/${year}/${month}/${day}/"
```

## 5. Querying Ingested Data via R2 Data Catalog

Once events land in R2, use the R2 Data Catalog (integrated with Cloudflare D1 or
external query engines via S3 API) to run SQL over the NDJSON files.

```bash
# List what the pipeline has written
wrangler r2 object list my-events-bucket --prefix "events/2026/08/23/"

# Download a day's NDJSON file for local analysis
wrangler r2 object get my-events-bucket "events/2026/08/23/part-000001.ndjson" \
  --file /tmp/events.ndjson

# Quick line count and sample
wc -l /tmp/events.ndjson
head -5 /tmp/events.ndjson | jq .
```

For real-time querying without downloading, enable the R2 Data Catalog on the bucket and
use Cloudflare Analytics Engine or connect via the S3-compatible API to DuckDB:

```bash
duckdb -c "
  INSTALL httpfs;
  LOAD httpfs;
  SET s3_endpoint='<account-id>.r2.cloudflarestorage.com';
  SET s3_access_key_id='<r2-access-key>';
  SET s3_secret_access_key='<r2-secret-key>';
  SELECT event, count(*) FROM read_ndjson('s3://my-events-bucket/events/2026/08/23/*.ndjson')
  GROUP BY event ORDER BY 2 DESC LIMIT 20;
"
```

## 6. Securing the HTTP Source with a Shared Secret Header

If your upstream service cannot send a Bearer token but supports a custom header (e.g.,
Stripe's `Stripe-Signature`), you can validate the signature in a thin Worker placed in
front of the Pipeline URL, then forward to the Pipeline with the Bearer token injected.

```typescript
// Stripe webhook → this Worker → Pipeline HTTP source
interface Env {
  STRIPE_WEBHOOK_SECRET: string;
  PIPELINE_URL: string;
  PIPELINE_TOKEN: string;
}

export default {
  async fetch(request: Request, env: Env): Promise<Response> {
    const sig = request.headers.get('stripe-signature') ?? '';
    const body = await request.text();

    const valid = await verifyStripeSignature(body, sig, env.STRIPE_WEBHOOK_SECRET);
    if (!valid) return new Response('Forbidden', { status: 403 });

    const payload = JSON.parse(body);
    const res = await fetch(env.PIPELINE_URL, {
      method: 'POST',
      headers: {
        'Content-Type': 'application/json',
        Authorization: `Bearer ${env.PIPELINE_TOKEN}`,
      },
      body: JSON.stringify({ ...payload, _source: 'stripe', _receivedAt: Date.now() }),
    });

    return new Response(null, { status: res.ok ? 200 : 502 });
  },
};

async function verifyStripeSignature(body: string, sig: string, secret: string): Promise<boolean> {
  const [, timestamp] = sig.match(/t=(\d+)/) ?? [];
  const [, v1] = sig.match(/v1=([a-f0-9]+)/) ?? [];
  if (!timestamp || !v1) return false;
  const key = await crypto.subtle.importKey(
    'raw', new TextEncoder().encode(secret), { name: 'HMAC', hash: 'SHA-256' }, false, ['sign']
  );
  const mac = await crypto.subtle.sign('HMAC', key, new TextEncoder().encode(`${timestamp}.${body}`));
  const computed = [...new Uint8Array(mac)].map(b => b.toString(16).padStart(2, '0')).join('');
  return computed === v1;
}
```

## Anti-Patterns

- **Posting individual records one by one at high frequency.** Each POST is a separate HTTPS
  handshake. Batch records into NDJSON arrays and POST at most once per second for high-
  volume streams.
- **Embedding the Pipeline token in client-side JavaScript.** The HTTP source token is a
  write credential; expose it only to backend services or Workers, never to browsers.
- **Ignoring transform Worker errors.** If the transform throws, the batch is retried from
  the Pipeline's internal buffer. Ensure the transform is idempotent and does not mutate
  external state.
- **Using the HTTP source for real-time push to subscribers.** Pipelines are write-to-R2
  pipelines, not a pub/sub bus. Use Queues or Durable Objects for fan-out.

---

## Gotchas

- The HTTP source URL changes if you delete and recreate the Pipeline. Update upstream
  services immediately after any Pipeline recreation.
- NDJSON files written to R2 are closed and flushed either when `batch-max-mb` is reached
  or `batch-max-seconds` elapses — whichever comes first. Very low frequency sources may
  produce many small files; tune batch settings accordingly.
- Transform Workers are invoked synchronously within the Pipeline; a slow transform blocks
  ingestion. Keep transform logic fast (< 50 ms per batch).
- The Pipeline does not deduplicate records. If your upstream retries a failed POST, the
  same record can appear twice in R2. Handle deduplication at query time using a unique
  event ID field.
- Pipelines are account-level resources, not zone-level. The HTTP source URL is always
  under `pipelines.cloudflare.com`, not your custom domain.
