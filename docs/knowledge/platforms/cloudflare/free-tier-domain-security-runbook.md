# free-tier-domain-security-runbook

**Issue:** Owner of a domain on the Cloudflare $0 (Free) plan wants every security layer Cloudflare makes available at no cost enabled properly, in the right order, with a verification step for each. This runbook enumerates the complete free stack — account hardening, DNSSEC, TLS, DDoS, WAF custom rules, the free managed ruleset, one rate-limiting rule, Bot Fight Mode, edge hygiene tools (Browser Integrity Check, IP Access Rules, Scrape Shield), Turnstile, Zero Trust Access (50 users), Cloudflare Tunnel, and email security (SPF/DKIM/DMARC + Email Routing) — with 2025–2026 verified plan limits and per-feature setup/verification. Paid-only features are explicitly marked "(paid)" so the runbook stays honest.

**Repo:** example-org/example-repo

## Enablement order at a glance

The order matters because later layers depend on earlier ones being stable. Enabling HSTS before HTTPS is proven end-to-end can lock visitors out for the max-age duration; enabling Full (Strict) before the origin has a valid certificate throws 526 errors; DNSSEC must come after nameservers are stable. The order documented here:

1. **Account hardening** (2FA, scoped API tokens) — an account takeover undoes every layer below it.
2. **DNS layer** (orange-cloud proxy on, then DNSSEC) — nothing else works through Cloudflare until traffic is proxied.
3. **TLS** (Full (Strict) with an Origin CA cert, min TLS 1.2, TLS 1.3, HSTS last) — encrypt and authenticate visitor↔edge↔origin before adding blocking layers.
4. **DDoS + edge hygiene** (unmetered DDoS is automatic; Under Attack Mode procedure; Browser Integrity Check; IP Access Rules; Security Level).
5. **WAF** (Cloudflare Free Managed Ruleset, 5 custom rules, 1 rate-limiting rule).
6. **Bots** (Bot Fight Mode + Block AI Bots, Turnstile on forms).
7. **Hide the origin** (Cloudflare Tunnel, then Zero Trust Access for admin surfaces, 50 users free).
8. **Email security** (SPF/DKIM/DMARC DNS records, Email Routing).
9. **Final verification sweep** (curl/dig/browser checks per layer).

Verified limits cited per section below. Cloudflare changes free-plan limits periodically; each section links the canonical docs page to re-check before running this runbook.

## Phase 0 — Account hardening (do this first)

1. **Enable 2FA on every account member.** Dashboard: top-right **Profile → Authentication → Two-Factor Authentication → Set up**. All accounts (including Free) get app-based TOTP, hardware security keys (phishing-resistant), and — since October 2025 — email as a 2FA factor; users without 2FA are now prompted to enroll at login. Download backup codes (**Profile → Security & Authentication → Backup codes**) so a lost device does not mean a support ticket. Verify: log out and back in — a second factor must be required. Source: https://developers.cloudflare.com/fundamentals/user-profiles/2fa/ and https://developers.cloudflare.com/changelog/post/2025-10-30-email-2FA/
2. **Replace the Global API Key with scoped API tokens.** The Global API Key is all-or-nothing for the whole account. Dashboard: **My Profile → API Tokens → Create Token** — pick a template (e.g., "Edit zone DNS") or build a custom token with per-permission (Account/User/Zone × Read/Edit), per-resource scope (e.g., DNS edit on one zone only), optional Client IP filtering, and a TTL so tokens expire. The secret is shown once; new tokens use a `cfut_`-prefix format detectable by secret scanners. Verify: `curl -H "Authorization: Bearer $TOKEN" https://api.cloudflare.com/client/v4/user/tokens/verify` returns `"status":"active"`, and a deliberately out-of-scope call returns an error. Source: https://developers.cloudflare.com/fundamentals/api/get-started/create-token/ (see also `api-token-least-privilege-and-rotation-governance.md` in this folder for rotation policy)
3. **Check member list and audit.** Dashboard: **Manage Account → Members** — remove stale invitations; keep at least two administrators. Free accounts get the audit log under **Manage Account → Audit Log**; review it for unfamiliar API token creation or login events. Verify: member list contains only known humans.

## Phase 1 — DNS layer: proxy + DNSSEC

1. **Proxy every public hostname (orange cloud).** In **DNS → Records**, set records that should be protected to **Proxied**. Only proxied traffic passes through the WAF, DDoS, Bot Fight Mode, and rate limiting; grey-cloud (DNS only) records bypass all of it. Keep grey-cloud only for records that cannot be proxied (e.g., some mail MX, origin-validation TXT). Verify: `nslookup yourdomain.com` returns Cloudflare edge IPs (104.x/172.64–71.x ranges), not your origin IP.
2. **Enable DNSSEC.** Free on all plans. Dashboard: **DNS → Settings → Enable DNSSEC**. Cloudflare signs the zone and shows a **DS record** (Algorithm 13, ECDSA Curve P-256 with SHA-256 — Cloudflare's preferred algorithm). Copy the DS record into your registrar's DNSSEC management. With Cloudflare Registrar, DS records are submitted automatically via CDS/CDNSKEY scanning (takes one to two days). Warning: only enable DNSSEC *after* nameserver changes have fully propagated — enabling on a freshly migrated zone can cause SERVFAIL for validating resolvers. Verify: check https://dnsviz.net/ or https://dnssec-debugger.verisignlabs.com/ for a green chain of trust, and `dig DS yourdomain.com +dnssec` returns the record. Source: https://developers.cloudflare.com/dns/dnssec/
3. **Do not expose origin IPs in DNS or history.** If the origin IP was ever published (pre-Cloudflare DNS history, SPF `ip4:` mechanisms, MX on the same host), it can be attacked directly, bypassing every layer here. Mitigate with Tunnel in Phase 6; meanwhile remove origin IPs from SPF includes. Verify: search SecurityTrails/crt.sh history for the origin IP and confirm current DNS shows only Cloudflare IPs.

## Phase 2 — TLS: Full (Strict), min TLS 1.2, TLS 1.3, HSTS (in that order)

1. **Install a Cloudflare Origin CA certificate on the origin.** Free, 15-year validity, trusted by Cloudflare's edge (not by browsers — it is only for origin pulls). Dashboard: **SSL/TLS → Origin Server → Create Certificate**. This is the certificate Full (Strict) will validate. Verify: `openssl s_client -connect origin-host:443 -servername yourdomain.com` shows the Origin CA cert.
2. **Set SSL/TLS mode to Full (Strict).** Dashboard: **SSL/TLS → Overview → Full (strict)**. This encrypts visitor→edge and edge→origin, and — unlike plain Full — rejects expired, self-signed, or hostname-mismatched origin certificates (visitors get a 526 error instead of silently-encrypted-but-unauthenticated traffic). API equivalent: `PATCH .../zones/$ZONE/settings/ssl` with `"value":"strict"`. Never use Flexible — it encrypts visitor→edge only and sends plain HTTP to the origin. Verify: `curl -sv https://yourdomain.com` succeeds with no 525/526; confirm the origin port 443 is serving your Origin CA cert. Source: https://developers.cloudflare.com/ssl/origin-configuration/ssl-modes/full-strict/
3. **Raise Minimum TLS Version to 1.2.** Available on Free (zone-level; per-hostname minimums require Advanced Certificate Manager, paid). Dashboard: **SSL/TLS → Edge Certificates → Minimum TLS Version → TLS 1.2**. This rejects TLS 1.0/1.1 clients, which have known vulnerabilities. Verify: `curl --tlsv1.1 --tls-max 1.1 https://yourdomain.com` fails with a handshake/protocol error, and the same call with `--tlsv1.2` succeeds. Source: https://developers.cloudflare.com/ssl/edge-certificates/additional-options/minimum-tls/
4. **Enable TLS 1.3.** Available on Free. Dashboard: **SSL/TLS → Edge Certificates → TLS 1.3 → On**. Improves handshake latency and security; supported by all current major browsers. Verify: `curl -sv https://yourdomain.com 2>&1 | grep "SSL connection"` (or openssl with `-tls1_3`) shows TLSv1.3 on a capable client. Source: https://developers.cloudflare.com/ssl/edge-certificates/additional-options/tls-13/
5. **Enable HSTS — last, deliberately.** Available on Free. Dashboard: **SSL/TLS → Edge Certificates → HTTP Strict Transport Security (HSTS) → Enable HSTS**; set Max Age to 1 month initially (range is 1–12 months), enable No-Sniff; leave **Apply to subdomains** OFF until every subdomain serves HTTPS, and leave **Preload** OFF until you are sure (preload submission requires max-age ≥ 12 months and removal from browser preload lists is slow and manual). Lockout risk: if HTTPS is later removed (grey-clouding records, pausing Cloudflare, cert expiry) before max-age expires, browsers refuse plain-HTTP access for the remaining duration. Verify: `curl -sI https://yourdomain.com | grep -i strict` shows `strict-transport-security: max-age=2592000`. Source: https://developers.cloudflare.com/ssl/edge-certificates/additional-options/http-strict-transport-security/

## Phase 3 — DDoS protection, Under Attack Mode, and edge hygiene tools

1. **Confirm unmetered DDoS protection is on (it always is).** Standard unmetered L3/4 (network) and L7 (HTTP) DDoS protection is automatic on every plan including Free — detection and mitigation run autonomously, no dashboard switch exists. Nothing to enable; just don't opt out. Verify: **Security → Events** shows mitigated attack traffic labeled with DDoS services during an incident. Source: https://developers.cloudflare.com/ddos-protection/
2. **Know the Under Attack Mode procedure before you need it.** In the current dashboard, Security Level is the switch for Under Attack Mode: **Security → Settings → Security Level → Under Attack** (API/Terraform: the `security_level` setting set to `under_attack`). It presents a managed-challenge interstitial to all visitors and is meant for active layer-7 attacks only — it can break APIs and mobile apps, so scope it to a path via a Configuration Rule if only one endpoint is under attack, and turn it off when the attack subsides. Note: the legacy threat-score (cf.threat_score) is now always `0` — do not build rules on it. Verify during an attack: browser shows the Cloudflare interstitial once, then passes. Source: https://developers.cloudflare.com/waf/tools/security-level/
3. **Keep Browser Integrity Check on.** Enabled by default on all plans; screens requests for headers commonly abused by spammers and challenges missing/non-standard user agents. Dashboard: **Security → Settings → filter "DDoS attacks" → Browser integrity check → On**. If it breaks a legitimate API client, scope an exception with a Configuration Rule rather than disabling zone-wide. Verify: `curl -H "User-Agent:" -H "Accept:" https://yourdomain.com` (stripped headers) gets challenged or blocked while a normal browser request passes. Source: https://developers.cloudflare.com/waf/tools/browser-integrity-check/
4. **Create IP Access Rules for known-bad and known-good.** Available on all plans; each account can hold up to 50,000 rules on every tier. Dashboard: **Security → WAF → Tools (IP Access Rules)** — match on IP, IP range, country, or ASN with actions Allow / Block / Challenge / JS Challenge. Caveats: the *country* match with Block is Enterprise-only — for geoblocking on Free use a WAF custom rule with `ip.geoip.country` instead; and **Allow** bypasses custom rules, rate limiting, and managed rules, so prefer narrow, deliberate allows (e.g., your monitoring IP) over broad ones. Verify: add your own IP with Challenge → your next request hits a challenge; remove it after testing. Source: https://developers.cloudflare.com/waf/tools/ip-access-rules/
5. **Turn on Scrape Shield items: Email Obfuscation and Hotlink Protection.** Under **Security → Settings → filter "Client-side abuse"** (Scrape Shield). Email Obfuscation is enabled automatically at signup — it rewrites mailto: addresses to block scraping (exclusions via `<!--email_off-->...<!--/email_off-->`; skipped inside script/noscript/textarea/head and on `Cache-Control: no-transform` responses). Hotlink Protection blocks other sites from embedding your images. Verify: view your contact page source — the literal email text is replaced with encoded script; hotlink-test by embedding an image URL from another domain. Sources: https://developers.cloudflare.com/waf/tools/scrape-shield/ and https://developers.cloudflare.com/waf/tools/scrape-shield/email-address-obfuscation/
6. **Privacy Pass: supported, nothing to configure.** Modern Privacy Pass (IETF tokens) works with Cloudflare's CAPTCHA-free, Turnstile-based managed challenges for visitors on VPNs/Tor/shared IPs who install the "Silk — Privacy Pass Client" browser extension. The old zone-level Privacy Pass toggle is no longer meaningful and Privacy Pass v1 stopped being accepted in September 2023 — there is no server-side enable step today. Verify: nothing to verify server-side; the challenge page works for extension users automatically. Source: https://developers.cloudflare.com/waf/tools/privacy-pass/

## Phase 4 — WAF: what Free actually gets

1. **Enable the Cloudflare Free Managed Ruleset.** The only managed ruleset on Free — deployed for you on all plans, covering high-impact widely exploited vulnerabilities (e.g., Shellshock, log4j-style rules). Managed rules appear under **Security → WAF → Managed rules**; on Free the Free Managed Ruleset is the one present. Verify: **Security → Events** with the "Service" filter set to the managed ruleset shows rule tags firing on synthetic exploits (e.g., a log4j `${jndi:ldap://...}` probe in a query parameter). Source: https://developers.cloudflare.com/waf/managed-rules/
2. **Know what is NOT on Free: Cloudflare Managed Ruleset (SQLi/XSS signatures) and the OWASP Core Ruleset are (paid)** — Pro and above. Do not promise signature-based SQLi/XSS blocking on a $0 zone; approximate it with custom rules (next item) and Turnstile on input forms. Sources: https://developers.cloudflare.com/waf/managed-rules/ and https://developers.cloudflare.com/waf/managed-rules/reference/owasp-core-ruleset/
3. **Spend your 5 custom firewall rules deliberately.** Free = 5 custom rules (Pro 20, Business 100, Enterprise 1,000), counting active and inactive rules. Dashboard: **Security → WAF → Custom rules → Create rule**. A battle-tested free-tier allocation: (1) challenge or block dangerous paths (`http.request.uri.path contains "/wp-login" or "/.env" or "/.git"`) → Managed Challenge; (2) block abusive countries with `(ip.geoip.country in {"XX" "YY"})` → Block; (3) block known-bad ASNs; (4) allow-list a partner/monitoring IP with the Skip action; (5) keep one spare for incident response. Verify: `curl "https://yourdomain.com/.env"` gets the configured action, and the rule shows hits in **Security → Events**. Rule-writing depth: see `waf-best-practices.md` in this folder. Source for the 5-rule limit: https://developers.cloudflare.com/waf/custom-rules/
4. **Configure your single rate-limiting rule.** Free = 1 rate-limiting rule (Pro 2, Business 5, Enterprise 100+). Dashboard: **Security → WAF → Rate limiting rules → Create rule**. Free-rule parameters: fixed counting only (no sliding/adaptive windows), counting characteristics limited to basic fields like IP, HTTP headers, cookies, ASN — no JA3/JA4 fingerprints, bot score, or headers-from-expression counting; periods limited to 10 seconds / 1 minute / 1 hour; mitigation timeout capped at 10 minutes; challenge actions take a fixed duration. Point it at your most abused endpoint (e.g., `(http.request.uri.path contains "/api/login")` → requests > 30 per 1 minute → Managed Challenge for 10 minutes). Verify: fire 40 rapid requests with a loop (`for i in $(seq 1 40); do curl -o /dev/null -sw "%{http_code}\n" https://yourdomain.com/api/login; done`) and observe 429/challenge responses. Deep dive: `waf-rate-limiting-deep-dive.md`. Sources: https://developers.cloudflare.com/waf/rate-limiting-rules/compatibility-matrix/ and https://developers.cloudflare.com/waf/rate-limiting-rules/parameters/

## Phase 5 — Bots: Bot Fight Mode + Turnstile on forms

1. **Enable Bot Fight Mode.** Included with Free; uses the same underlying detection as the paid products. Dashboard: **Security → Settings → filter "Bot traffic" → Bot fight mode → On**. It issues computationally expensive challenges to known bot patterns across the entire domain. Critical limitations: it cannot be customized, scoped, or bypassed — Skip/Allow custom rules have no effect on it (it runs outside the Ruleset Engine) — and it can challenge legitimate API/mobile clients and even verified bots. If it breaks a payment webhook or monitoring agent, your only free-tier options are turning it off or moving that endpoint to a subdomain where Bot Fight Mode stays off. Verify: **Security → Events** shows requests labeled "Bot Fight Mode" in the Service field; watch for false positives on your own automation for the first 48 hours. Sources: https://developers.cloudflare.com/bots/get-started/bot-fight-mode/ and https://developers.cloudflare.com/bots/plans/free/
2. **Turn on Block AI Bots.** Free. Same **Security → Settings** area (Bot traffic section) — blocks AI crawlers from scraping content. Verify: **Security → Analytics → Events** shows blocked AI-bot user agents (GPTBot etc.). Source: https://developers.cloudflare.com/bots/additional-configurations/block-ai-bots/
3. **Super Bot Fight Mode is (paid)** — Pro/Business/Enterprise; adds per-score actions (definitely/likely automated), verified-bot allowlisting, and static-resource protection. Free zones get the one-click Bot Fight Mode above, not granular control. Source: https://developers.cloudflare.com/use-cases/solutions/stop-malicious-bots/
4. **Add Turnstile to forms and sensitive actions.** Free: up to 20 widgets per account, unlimited challenges, 10 hostnames per widget, 7-day analytics lookback. Dashboard: **Turnstile → Add widget** (managed / non-interactive / invisible types) → embed the site key + `challenges.cloudflare.com/turnstile/v0/api.js` in the form → validate the token server-side against the siteverify API with your secret key. This is the free-tier answer to credential stuffing and form spam on endpoints Bot Fight Mode can't distinguish. Verify: submit the form without solving (e.g., via curl) — siteverify returns a failure; the browser flow passes and returns a token. Widget-selection and fallback guidance: `turnstile-best-practices.md`. Source: https://developers.cloudflare.com/turnstile/plans/

## Phase 6 — Hide the origin: Cloudflare Tunnel + Zero Trust Access

1. **Run the origin behind Cloudflare Tunnel (free).** `cloudflared` makes outbound-only connections from your origin to Cloudflare — no open inbound ports, no public origin IP, so attackers cannot bypass the edge and hit the origin directly. Setup: create a tunnel in **Zero Trust dashboard → Networks → Connectors** (or the main dashboard at **Networking → Tunnels**, available since Feb 2026), install `cloudflared` on the origin with the tunnel token, map public hostnames to local services (e.g., `app.yourdomain.com → http://localhost:8080`). Then firewall the origin to allow outbound only. Note: Authenticated Origin Pulls does not apply to tunneled hostnames — the tunnel's connector credentials already authenticate origin traffic. Verify: from an external host, `curl http://origin-ip:8080` times out (inbound blocked) while `https://app.yourdomain.com` works through the tunnel. Source: https://developers.cloudflare.com/cloudflare-one/networks/connectors/cloudflare-tunnel/
2. **Put admin surfaces behind Cloudflare Access (Zero Trust free tier: up to 50 users).** The Zero Trust free plan covers 50 users at no cost (beyond that is paid, ~$7/user/month). In the Zero Trust dashboard: **Access → Applications → Add an application (self-hosted)** → set the domain (e.g., `admin.yourdomain.com`) → policy: Action Allow, Include `emails ending in @yourdomain.com` (or a specific list) → choose an identity provider (one-time PIN works with zero infrastructure). Every request to that hostname now requires email verification before reaching the origin — effectively free 2FA-in-front for dashboards, Grafana, CI, anything. Verify: open the app URL in a private window — you get a Cloudflare Access login; only after the emailed code does the app load. Architecture and JWT validation depth: `zero-trust-access.md` and `cloudflare-access-jwt-validation.md` in this folder. Sources: https://developers.cloudflare.com/cloudflare-one/account-limits/ and https://www.cloudflare.com/plans/zero-trust-services/

## Phase 7 — Email security: SPF, DKIM, DMARC + Email Routing

1. **Publish SPF.** A TXT record on the apex: `v=spf1 include:_spf.<your-provider>.com -all` (start with `~all` softfail while validating). Only one SPF record per domain — multiple records invalidate all of them. Verify: `dig txt yourdomain.com +short` returns exactly one `v=spf1` string; send to a Gmail address and inspect "show original" for `spf=pass`. Full record syntax and provider includes: `../email/spf-record-setup.md`.
2. **Publish DKIM.** Get the public key from your sending provider (or generate a selector keypair), publish `selector._domainkey.yourdomain.com TXT "v=DKIM1; k=rsa; p=<key>"`, and enable signing in the provider. Verify: `dig txt selector1._domainkey.yourdomain.com +short` returns the key; a sent email's headers show `DKIM-Signature` and the receiver reports `dkim=pass`. Details: `../email/dkim-record-setup.md`.
3. **Publish DMARC.** Start with monitoring: `_dmarc.yourdomain.com TXT "v=DMARC1; p=none; rua=mailto:dmarc-reports@yourdomain.com"`. Watch the weekly aggregate reports for legitimate senders you forgot, then tighten `p=quarantine` and finally `p=reject`, adding `aspf=r; adkim=r` alignment as needed. Verify: `dig txt _dmarc.yourdomain.com +short`; reports arrive at the rua address; mail-tester.com scores align. Details: `../email/dmarc-policy-setup.md` and `../email/dmarc-rua-reporting.md`.
4. **Turn on Email Routing (free on Free and paid plans).** Dashboard: **Email → Email Routing** for the zone — Cloudflare adds the required MX records and asks you to add its SPF include. Verify destination addresses by clicking emailed links, then create custom address rules (e.g., `hi@yourdomain.com → you@gmail.com`) or a catch-all. Platform limits: 200 routing rules per domain, 200 destination addresses per account, 25 MiB maximum inbound message size. This removes the need for any inbound mail server while keeping the domain's mail on your domain. Verify: send mail from an external account to `hi@yourdomain.com` — it lands in the verified destination within seconds. Sources: https://developers.cloudflare.com/email-routing/ and https://developers.cloudflare.com/email-service/platform/limits/ (also see `cloudflare-email-routing.md` and `workers-email-routing.md` in this folder for Worker-handler patterns)

## Final verification sweep (run top to bottom)

1. **DNS/proxy:** `nslookup yourdomain.com` returns only Cloudflare IPs; DNSViz shows a valid DNSSEC chain.
2. **TLS:** `curl -sI https://yourdomain.com` returns 200 with HSTS header; `curl --tlsv1.1 --tls-max 1.1 https://yourdomain.com` fails; TLS 1.3 negotiates; no 525/526 in **Security → Events**.
3. **Edge tools:** header-stripped curl gets challenged (BIC); test IP rule triggers its action.
4. **WAF:** `curl https://yourdomain.com/.env` hits your custom rule; 40 rapid requests to the protected endpoint trip the rate-limit rule; a log4j-style probe shows the Free Managed Ruleset firing in Security Events.
5. **Bots/forms:** Bot Fight Mode entries appear in Security → Events with no false positives on your automation; Turnstile-protected form rejects tokenless submissions server-side.
6. **Origin hidden:** direct-to-origin-IP requests time out; tunneled hostname resolves through Cloudflare; Access-gated admin URL demands login.
7. **Email:** `dig txt yourdomain.com`, `_dmarc`, and `_domainkey` records all present; SPF/DKIM/DMARC pass on a real send; Email Routing forwards inbound mail.
8. **Re-check limits quarterly:** Cloudflare moves free-tier boundaries (e.g., custom-rule counts and rate-limit parameters changed with the 2024 firewall-rules → custom-rules merge). Re-verify each cited docs page before relying on a number in a new quarter.
