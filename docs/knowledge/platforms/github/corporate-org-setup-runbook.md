# corporate-org-setup-runbook

**Issue:** A company is standing up GitHub "for real" — organization account, corporate SSO, team/access architecture, repository defaults, security scanning, CI/supply-chain policy, and audit/compliance — and needs the single ordered checklist that sequences all of it correctly. Doing these out of order is expensive: enforcing SSO before SCIM strands members, enabling GHAS before counting committers surprises finance, and setting base permissions after repos exist breaks automations. This is the ordered runbook that ties the deep-dive KB articles together; each phase ends with what to verify and cross-references the deep articles for the pieces it touches. Researched against 2025–2026 GitHub mechanics (post April-2025 GHAS unbundling into Secret Protection / Code Security).

## Phase 1: Account structure & plan selection

1. **Decide the account topology.** A standalone organization is one org with its own billing; an enterprise account is a container that can hold multiple orgs with unified billing, policy, and audit. Rule of thumb: one company identity, even if you only have one org today → create the enterprise account now and put the org in it, because retrofitting (transferring orgs into an enterprise) later is disruptive to SSO and billing. Verify: `gh api /enterprises/<enterprise>` returns your org under `organizations_url`, and `gh api /orgs/<org>` shows the enterprise billing relationship.
2. **Run the plan decision matrix.** As of 2025–2026 the options are: **Free** ($0, unlimited members, 2,000 Actions min/mo — SAML SSO and 2FA enforcement work, but rulesets on private repos, required reviews enforcement, and audit retention are crippled), **Team** (~$4/user/mo, 3,000 Actions min/mo — rulesets on private repos, and since April 2025 you can buy Secret Protection and Code Security à la carte), **Enterprise Cloud / GHEC** (~$21/user/mo billed annually, 50,000 Actions min/mo, GHAS included, audit log streaming, enterprise-level SAML/SCIM, 180-day audit retention vs 90 for standalone orgs), **EMU** (Enterprise Cloud with users provisioned and controlled by your IdP), **Enterprise Server** (~$21/seat/mo, self-hosted, for air-gapped). Pick Team only if you are cost-sensitive and have no compliance mandate; pick GHEC the moment you need audit log streaming, unified SSO, or full GHAS. Verify: decision recorded; the chosen plan shows under org Billing & Licensing.
3. **Decide EMU vs standalone org.** EMU means members are `user_corp@tenant` accounts created/manged by your IdP — they cannot interact with public GitHub outside the enterprise, cannot be individually invited, and leave when deprovisioned. Choose EMU when: compliance requires that you own all accounts and block outside activity, or you want guaranteed no "personal account in corporate org" entanglement. Choose standalone org + SAML when: your people need their existing public GitHub identities (open-source work, personal repos), or you hire heavy OSS contributors who would revolt at managed accounts. This choice is nearly irreversible — EMU orgs cannot be converted back to standalone. Verify: read `github-enterprise-managed-users.md` and get an explicit sign-off; the EMU support restriction (no public activity) is accepted by engineering leadership.
4. **Model the seat/licensing model before purchase.** Org plans bill per *billable user*: owners, members, and outside collaborators with access to private repos; pending invitations reserve seats on Team; GitHub Apps and bots do not count. Enterprise accounts bill per *unique person across all orgs in the enterprise* — someone in three orgs consumes one seat, which is the main reason to consolidate orgs under an enterprise. Budget Actions minutes and storage separately (overage is per-minute/GB). Verify: export the seat math (headcount + expected collaborators + contractor churn) and compare `gh api /orgs/<org>/settings/billing/shared-storage` and `.../actions` against the budget before the first invoice lands.
5. **Set up billing controls.** Add payment method, set a billing manager (non-owner role that can see invoices without org admin), configure spending limits for Actions Packages/Large Storage, and enable budget alerts to a finance email/distribution list. Verify: a deliberate `$1` overage test or a dry-run via the pricing calculator; finance confirms they receive the alert email.

**Related:** `github-organization-settings.md`, `github-enterprise-managed-users.md`, `github-audit-log-api.md`

## Phase 2: Domain & identity bootstrap

6. **Verify the corporate domain.** Org Settings → Verified & approved domains → add `corp.com`, publish the DNS TXT record GitHub gives you (`_github-challenge-<org>.corp.com`), wait for verification. *Verified* domains prove ownership and light up the "Verified" badge when profile website/email match; *approved* domains additionally restrict notification emails to that domain. For EMU/GHEC, do this at the enterprise level too — verified domains are what tie your IdP to the enterprise. Verify: badge shows on the org profile; `dig TXT _github-challenge-<org>.corp.com` returns the token.
7. **Enforce 2FA org-wide — with warning.** Announce a deadline (≥1 week), then `gh api -X PATCH orgs/<org> -f two_factor_requirement_enabled=true`. Members without 2FA are removed from the org on enforcement; the audit log records removals. Verify: `gh api /orgs/<org> --jq .two_factor_requirement_enabled` → `true`; audit log shows zero surprise `org.remove_member` events after the deadline.
8. **Configure SAML SSO (or OIDC for EMU) without enforcing yet.** Standalone org: upload IdP metadata (Okta/Entra/Ping), set SSO URL, issuer, public cert, test with the "Test" button while SSO is *not* enforced so nobody is locked out. EMU/GHEC: configure SAML or OIDC at the enterprise level — note that OIDC federation is only available for EMU, not standalone orgs, as of 2025–2026. Verify: your own admin account round-trips the IdP login; the SAML response in an SP-initiated test has NameID format and attributes you expect.
9. **Wire SCIM provisioning and group→team sync.** Configure the SCIM app in the IdP (Okta "GitHub" app with org credentials, or Entra enterprise app), grant it org admin, then map IdP groups to GitHub teams so membership is driven from the directory. For EMU this is mandatory — users do not exist until provisioned. Verify: move a test user into an IdP group → within minutes they appear in the mapped team (`gh api /orgs/<org>/teams/<team>/members`) and receive repo access; remove them from the group → access disappears without manual offboarding.
10. **Enforce SSO, then sweep credentials.** Flip SAML enforcement on. Authorize (or revoke) each member's PATs, SSH keys, and GitHub Apps against SSO; un-authorized tokens silently fail with 401s that look like "mysterious CI breakage." Publish the re-auth runbook for CLI users (`gh auth refresh -h github.com`). Verify: API access with a stale token fails; a fresh `gh auth login` via SSO works; audit log shows `saml_user_authorization` events for every active member.

**Related:** `github-saml-sso-enforcement.md`, `github-enterprise-managed-users.md`, `github-organization-settings.md`

## Phase 3: Access architecture

11. **Set base permissions to Read (or None).** Org Settings → Member privileges → Base permissions: **Read** as default (None only if every repo is explicitly assigned via teams — cleaner but more upkeep). This is the single highest-leverage least-privilege setting; do it *before* repos migrate in so nothing grows up depending on implicit write. Verify: `gh api /orgs/<org> --jq .default_repo_permission` → `read`; a plain member `gh api /repos/<org>/<repo>` shows `permissions.push: false`.
12. **Design the team hierarchy around the directory, not the org chart of the week.** Top-level teams mirror IdP groups (SCIM-synced): `eng`, `security`, `sre`; child teams inherit parent repo access for containment (`eng/backend`, `eng/frontend`). Give repo access to teams only, never individuals — individual grants are unreviewable and survive team cleanups. Verify: `gh api /orgs/<org>/teams` lists every team with an SCIM-linked group; spot-check that `gh api /repos/<org>/<repo>/collaborators` contains zero direct user grants outside break-glass.
13. **Create custom repository roles for scoped write.** Org Settings → Repository roles → new role, e.g. "deploy-only" = write + Actions:write + Workflows:none, or "triage" without merge. Use these instead of blanket Write for automation-facing humans and support staff. Verify: assign the role to a test user on a sandbox repo; confirm `gh api /repos/<org>/<repo>` for that user shows exactly the intended permission bits, and that they *cannot* push to a protected path.
14. **Make CODEOWNERS the enforcement layer.** Every active repo gets `.github/CODEOWNERS` (or root) covering all meaningful paths; combine with the Phase 4 ruleset requiring "review from Code Owners" so ownership is a merge gate, not documentation. Verify: open a PR touching an owned path from a non-owner → merge blocked with "missing required review from code owners"; audit the file quarterly via a script that diffs CODEOWNERS against the directory.
15. **Standardize service identities: GitHub Apps over PATs, ever.** Policy: org-owned GitHub App per automation (scoped repos, minimal permissions, installation tokens are short-lived and SSO-exempt); fine-grained PATs for humans where an App doesn't fit (org policy can restrict to allow-listed FG PATs only, max 1-year expiry, repository/resource-scoped); classic PATs banned. Keep one sealed break-glass credential in the vault, never in CI. Verify: `gh api /orgs/<org>/installation` (or Settings → Integrations) lists Apps with narrow scopes; scheduled audit-log query for `pat.create`/`oauth_app` events flags anything outside policy.

## Phase 4: Repository defaults

16. **Lock down repo creation defaults.** Org Settings → Repository defaults: new repo visibility **Private**; default branch name `main`; disable member public-repo creation (or route it through an approvals repo template). Verify: a member creating a repo gets Private+`main` with no option to publish public without owner action (`gh api /orgs/<org> --jq .members_can_create_public_repositories` → `false`).
17. **Build org-level rulesets, not per-repo branch protection.** Org Settings → Rules → rulesets targeting `repository: all` / `branch: default`: require PR before merge, require approvals (1–2), dismiss stale reviews, require CODEOWNERS review, require conversation resolution, block force-pushes and deletions. Org-level rulesets apply to every repo including ones created mid-second — this is the whole point of doing it before repo onboarding. Migrate any inherited classic branch protection to rulesets (evaluated any-rule-matches). Verify: direct push to `main` as a member is rejected: `! [remote rejected] (protected by org ruleset)`; the ruleset Insights tab shows evaluations; zero repos have classic protection remaining.
18. **Require status checks and a merge queue.** Add required checks (`ci`, `lint`, `test`) to the ruleset — ensure they're reported by required contexts and sharded consistently — and enable **merge queue** on the default branch so a green PR cannot break `main` through races; set a merge method policy (squash-only recommended) and auto-delete head branches. Verify: PR merged via queue shows "Merged into queue → merged" lifecycle; temporarily break a check → merge button disabled; `git push origin :refs/heads/feature-x` after merge returns "branch not found" (auto-deleted).
19. **Require signed commits and verification.** Ruleset: "Require signed commits" on the default branch; ask admins to enable vigilant mode in their personal settings (unsigned commits flagged even if not enforced). Decide the org signing standard (SSH signing is lowest-friction; GPG or 1Password/sigstore for stricter shops) and document it. Verify: an unsigned push to `main` is rejected with `GH009: branch protection violation`; merged commits show **Verified** badge; audit-log spot-check for `git.push` events with unsigned payloads on protected refs.
20. **Add tag protection rules.** Org-level tag protection restricting `v*` creation/updates to release bots or the release team (or a ruleset targeting `refs/tags/*` with restrictions on tag create/update/delete). Verify: `git tag v1.2.3 && git push origin v1.2.3` as a regular member is rejected; the release bot's tag lands and subsequent deletion attempts fail.

**Related:** `github-rulesets-migration-from-branch-protection.md`, `branch-protection-and-codeowners.md`, `github-required-status-checks.md`, `github-auto-merge.md`

## Phase 5: Security suite

21. **Count committers before enabling anything GHAS-shaped.** Since April 2025 the products are unbundled: **Secret Protection** (~$19/committer/mo: secret scanning, push protection, AI generic-secret detection) and **Code Security** (~$30/committer/mo: code scanning, dependency review), both purchasable à la carte on Team; full GHAS is included in Enterprise Cloud. Licensing is per *unique active committer* in the billing period — anyone who pushes a commit to an enabled repo consumes a license, including bot-shaped identities pushing under a person's name. Get the committer census (Billing → Licensing → committer data, or `gh api /repos/<org>/<repo>/committers` across candidate repos) and buy to that number. Verify: license usage page matches your census within ~10%; finance has pre-approved the ceiling.
22. **Enable Secret Protection org-wide.** Org Settings → Codespaces, security & features (Security & analysis): enable secret scanning + push protection for all repositories and for new repos by default (API: `gh api -X PATCH /orgs/<org> -f secret_scanning_enabled_for_new_repositories=true ...`); add org-level custom patterns for internal token formats. Verify: push a fake AWS key (`AKIA...` test string) → push blocked at `git push` time; Security → Coverage shows 100% of repos enabled; closed alerts appear in the org Security Overview.
23. **Set the Dependabot org policy.** Enable Dependabot alerts + security updates for all repos (org-level default), then roll `.github/dependabot.yml` via repo template (version updates weekly, grouped updates to cut PR noise, custom branch names aligning with the Phase 4 rulesets). Verify: alert on a repo with a known-vulnerable dependency (e.g. an old `lodash`) appears within a day; the auto-PR passes required checks and is mergeable by triage role.
24. **Turn on CodeQL default setup org-wide.** Security → Code scanning → enable CodeQL default setup at the org level (auto-enabled for new repos, analysis of default + supported languages, no workflow file to maintain). For non-default analysis matrices, advanced setup with a reusable workflow. Verify: `gh api /repos/<org>/<repo>/code-scanning/analyses` returns a recent analysis for every non-archived repo in each supported language; Security Overview code-scanning tab shows no gaps.
25. **Enable private vulnerability reporting and security advisories.** Org/repo Settings → Advanced Security → Private vulnerability reporting ON for all repos (so researchers have a channel that doesn't require a public issue); maintain a SECURITY.md via the repo template; publish internal-only advisories for incidents, GHSA + CVE publication for shipped OSS. Verify: "Report a vulnerability" button visible on a private repo to a non-member researcher; a test report lands in the repo's Security tab advisories queue.

**Related:** `github-advanced-security-setup.md`, `github-secret-scanning.md`, `github-code-scanning-codeql.md`, `dependabot-config.md`, `github-security-advisories.md`

## Phase 6: Automation & supply chain

26. **Set the allowed actions policy.** Org Settings → Actions → General → Allow: select actions — permit `actions/*`, `github/*`, verified-creator patterns, and your own org namespace; everything else is blocked at workflow-parse time. Prefer referencing pinned SHAs (`uses: actions/checkout@<sha> # v5`) for the allow-listed set. Verify: a workflow referencing a random marketplace action fails immediately with "not in the allow list"; an allow-listed action runs.
27. **Default the workflow token to read-only.** Org Settings → Actions → General → Workflow permissions: **Read repository contents and packages permission**, and leave "Allow GitHub Actions to create and approve pull requests" unchecked unless a specific bot needs it. Individual jobs opt up with `permissions: write...` explicitly, which is reviewable in the PR diff. Verify: a workflow that pushes a commit without an explicit `permissions:` block fails with 403; the same workflow with an explicit, minimal `permissions:` succeeds.
28. **Kill static cloud credentials — use OIDC federation.** For every deploy pipeline, replace long-lived AWS keys/GCP service-account JSON/Azure secrets with the actions OpenID Connect flow (`aws-actions/configure-aws-credentials` with `role-to-assume`, the GCP/Azure equivalents) where the cloud trust policy pins `repo: <org>/<repo>:ref:refs/heads/main`. Secrets stay only for third-party services without OIDC support, stored as environment secrets, never org-wide. Verify: revoke the old static key and the deploy still runs; the cloud provider's audit trail shows assumed-role sessions with the workflow's `sub` claim; `gh api /repos/<org>/<repo>/actions/secrets` returns near-empty.
29. **Gate deployments with environments and protection rules.** Create `production`/`staging` environments on deploy repos; protection rules: required reviewers (change-approvers, not the PR approvers), wait timer, branch restriction to `main` + tags; deployment branches policy "selected branches". Secrets scoped per environment. Verify: a deploy to `production` from a feature branch is refused; a manual `workflow_dispatch` against `main` opens an approval request to the listed reviewers; approving completes the deployment and logs `deployment.status` in the audit log.
30. **Decide runner posture.** Default GitHub-hosted for CI; self-hosted or larger hosted runners only where needed (GPU, private network, egress-locked builds) — and never attach self-hosted runners to public repos (fork PR RCE). For supply-chain audit, add artifact attestations (`actions/attest-build-provenance`) on release artifacts. Verify: `gh api /orgs/<org>/actions/permissions/runners` reflects the allowed runner types; a release artifact shows provenance via `gh attestation verify`.

## Phase 7: Audit & compliance

31. **Stream the audit log to the SIEM.** On GHEC: enterprise Settings → Audit log → Log streaming → add destination (Amazon S3, Azure Blob Storage, Azure Event Hubs, Datadog, Google Cloud Storage, Splunk, or partner endpoints); stream at the enterprise level so it covers every org. On standalone Team orgs there is no streaming — schedule a puller against the audit log REST API instead, since retention is only 90 days. Verify: perform a known action (add a member), then confirm the corresponding event (`org.add_member`) arrives in the SIEM within minutes, with actor/IP/UA fields intact; alert on stream pausing.
32. **Apply IP allow lists with exceptions enumerated.** Org/enterprise Settings → Network access → IP allow list: add office/VPN/CI egress CIDRs, and explicitly decide the toggles for installed GitHub Apps and SSO-exempt scenarios. Coordinate with Phase 6 — runner egress and any allow-listed integrations must be in the list or CI breaks the moment the list is enforced. Verify: from a non-listed network the web/API/git access fails with the allow-list message; from VPN everything works; `gh api` from the CI runner succeeds.
33. **Lock OAuth App and PAT policy.** Org Settings → Third-party access: restrict OAuth Apps and personal access tokens to an approved allow-list; unapproved apps lose org-scoped token grants. Reserve GitHub App installations for vetted vendors (their token scopes were reviewed in Phase 3). Verify: attempt to authorize a random OAuth App with org access → request routed to owners for approval or denied; audit-log query for `oauth_app_access.*` events over the last 90 days shows only allow-listed app ids.
34. **Run an inactive-member and access review cadence.** Monthly: export members and outside collaborators (`gh api /orgs/<org>/outside_collaborators`), diff against the IdP's active-employee list from SCIM, and suspend accounts that have no IdP counterpart or 90+ days of inactivity (GHEC dormant-user suspension helps here). Quarterly: review custom repo roles, admin grants, deploy keys, and the break-glass credential (rotate on use). Verify: an access-review report exists with dated sign-off; a deliberately suspended test account gets 404s on private repo access within one SCIM cycle.
35. **Instrument org insights and close the loop.** Point the compliance dashboard at Security Overview (open alerts, coverage %) and org insights (PR throughput, commit activity) — the point is that Phase 5 coverage stays at 100% and Phase 3 drift gets caught. Wire SIEM detections for the high-signal audit events: `repo.add_access`, `org.update_member`, ruleset changes (`repository_rulesuites`/`repo_rule` events), `secret_scanning_alert.*`, streaming failures, and IP-allow-list edits. Verify: tabletop one incident — "a leaked PAT was used from an unknown IP" — and show that the query finds the `git.push` event, actor, and repo inside the detection SLA.

## Sequencing summary

The order matters because each phase assumes the previous one's constraints: plan choice (1) fixes what identity model (2) can even do; identity (2) drives team sync (3); base permissions (3) must precede repo defaults (4) or automations depend on implicit write; GHAS enablement (5) is a financial act gated on committer counts; automation policy (6) builds on rulesets (4) and service identities (3); and audit streaming (7) only captures events from day one if it is stood up before — not after — the org fills up. If you are mid-way through a brownfield setup, run this runbook top-to-bottom anyway and expect steps 11–16 to surface existing dependencies as failures; fix them rather than loosening the defaults.
