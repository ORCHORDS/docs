# R2 CORS Preflight Misconfiguration Production Incident

- **Date**: 2026-08-23
- **Author**: example.com
- **Status**: production

## Symptom / Use-case

Browser-based file uploads to our R2 bucket stopped working for all users on a Saturday morning following a routine infrastructure configuration push. The browser console reported `Access to fetch at '...' from origin '...' has been blocked by CORS policy: Response to preflight request doesn't pass access control check: No 'Access-Control-Allow-Origin' header is present on the requested resource.` Upload success rate dropped from 99.7% to 0% within two minutes of the push.

## Context

The platform serves user-generated media uploads directly to R2 via presigned PUT URLs generated by a Worker. The browser sends an `OPTIONS` preflight before the PUT, and R2 must respond with the correct CORS headers. CORS configuration on R2 buckets is set via the Cloudflare dashboard or API as a JSON array of rules. The configuration push on Saturday rotated a Hyperdrive connection string and inadvertently included a partial R2 CORS config export from a staging bucket—which had a stricter origin whitelist and was missing the `PUT` method—as part of a Terraform plan that managed multiple resources.

## Timeline

- **08:02 UTC** — Infrastructure engineer runs `terraform apply` for Hyperdrive connection string rotation. Plan includes 3 resource changes; R2 bucket CORS config is one of them (unintended).
- **08:04 UTC** — Apply completes; R2 CORS config replaced with staging config.
- **08:06 UTC** — First upload failure reports appear in Sentry; CORS errors in browser console.
- **08:09 UTC** — Upload success rate in Analytics Engine drops to 0%.
- **08:14 UTC** — On-call paged via PagerDuty; begins triage assuming Worker error.
- **08:26 UTC** — Sentry error text contains `Access-Control-Allow-Origin`; on-call shifts focus to CORS.

- **08:38 UTC** — Correct CORS config re-applied via Cloudflare API; preflight responses verified with `curl`.

- **10:00 UTC** — Postmortem opened; Terraform R2 CORS config separated into its own isolated module with state locking.

## Root Cause

The Terraform configuration for R2 CORS was co-located with Hyperdrive and KV resources in a single `cloudflare-infra` module. A copy-paste from the staging workspace left the R2 bucket CORS rule referencing the wrong `cloudflare_r2_bucket` resource—the staging bucket—instead of production. Because Terraform plan output showed `~ cors_rules` as an update (not a destroy/create), it was read as an innocuous config drift correction rather than a breaking change:

```hcl
# terraform/cloudflare-infra/r2.tf — pre-incident (truncated)

resource "cloudflare_r2_bucket" "media_prod" {
  account_id = var.account_id
  name       = "media-prod"

  cors_rules = [
    # BUG: copied from staging, wrong allowed_origins and missing PUT method
    {
      allowed_origins = ["https://staging.example.com"]
      allowed_methods = ["GET", "HEAD"]
      allowed_headers = ["*"]
      max_age_seconds = 3000
    }
  ]
}
```

The correct production CORS config that was overwritten:

```json
[
  {
    "AllowedOrigins": ["https://example.com", "https://www.example.com"],
    "AllowedMethods": ["GET", "PUT", "HEAD", "DELETE"],
    "AllowedHeaders": ["*"],
    "ExposeHeaders": ["ETag"],
    "MaxAgeSeconds": 86400
  }
]
```

There was no pre-apply diff review step that called out CORS config changes as high-risk, and no automated test that exercised an OPTIONS preflight against the bucket post-deploy.

## Fix Applied

**Immediate fix** (08:38 UTC): re-apply correct CORS config via Cloudflare API:

```bash
curl -X PUT "https://api.cloudflare.com/client/v4/accounts/${ACCOUNT_ID}/r2/buckets/media-prod/cors" \
  -H "Authorization: Bearer ${CF_API_TOKEN}" \
  -H "Content-Type: application/json" \
  -d '[
    {
      "AllowedOrigins": ["https://example.com", "https://www.example.com"],
      "AllowedMethods": ["GET", "PUT", "HEAD", "DELETE"],
      "AllowedHeaders": ["*"],
      "ExposeHeaders": ["ETag"],
      "MaxAgeSeconds": 86400
    }
  ]'
```

**Verification script** added to CI post-deploy checks:

```bash
#!/usr/bin/env bash
# scripts/verify-r2-cors.sh
set -euo pipefail

BUCKET_URL="https://media-prod.${CF_ACCOUNT_ID}.r2.cloudflarestorage.com"
ORIGIN="https://example.com"

STATUS=$(curl -s -o /dev/null -w "%{http_code}" \
  -X OPTIONS "${BUCKET_URL}/healthcheck" \
  -H "Origin: ${ORIGIN}" \
  -H "Access-Control-Request-Method: PUT" \
  -H "Access-Control-Request-Headers: Content-Type")

if [[ "$STATUS" != "200" ]]; then
  echo "CORS preflight failed: HTTP $STATUS"
  exit 1
fi

ALLOW_ORIGIN=$(curl -s -I \
  -X OPTIONS "${BUCKET_URL}/healthcheck" \
  -H "Origin: ${ORIGIN}" \
  -H "Access-Control-Request-Method: PUT" \
  | grep -i "access-control-allow-origin" | tr -d '\r')

echo "Preflight OK — $ALLOW_ORIGIN"
```

**Architectural fix**: moved R2 CORS config into its own isolated Terraform module with a `prevent_destroy` lifecycle rule:

```hcl
# terraform/r2-cors/main.tf
resource "cloudflare_r2_bucket_cors" "media_prod" {
  account_id  = var.account_id
  bucket_name = "media-prod"

  lifecycle {
    prevent_destroy = true
  }

  rules = [
    {
      allowed_origins = var.allowed_origins   # pulled from tfvars, not inline
      allowed_methods = ["GET", "PUT", "HEAD", "DELETE"]
      allowed_headers = ["*"]
      expose_headers  = ["ETag"]
      max_age_seconds = 86400
    }
  ]
}
```

## What We Learned

1. **CORS misconfiguration is a silent, instant total outage for browser clients.** Unlike latency degradation, a wrong CORS config drops 100% of preflight-gated requests immediately with no retry path.
2. **Terraform plan diffs that show `~ cors_rules` must be treated as high-risk**, equivalent to a firewall rule change. The diff is easy to miss in a multi-resource apply.
3. **Post-deploy smoke tests must include an OPTIONS preflight**, not just a GET health check. A Worker returning 200 does not prove uploads work.
4. **CORS config for production buckets should live in its own isolated Terraform module** to prevent accidental co-application with unrelated changes.
5. **Staging and production Terraform workspaces must never share resource references.** Using a workspace-aware variable for `bucket_name` and `allowed_origins` removes the copy-paste risk.

## Prevention

- **CI preflight check**: run `verify-r2-cors.sh` as a post-deploy step in every deployment pipeline that touches the `cloudflare-infra` module.
- **Terraform plan gate**: add a CI step that greps the Terraform plan output for `cors_rules` changes and blocks auto-apply, requiring manual approval:

```bash
terraform plan -out=tfplan.binary
terraform show -json tfplan.binary | jq '.resource_changes[] | select(.change.actions[] | contains("update")) | select(.address | contains("r2"))' | grep cors_rules && echo "CORS CHANGE DETECTED — manual approval required" && exit 1 || true
```

- **Alerting**: create an Analytics Engine alert that fires when upload success rate drops below 95% for two consecutive minutes.
- **CORS config in version control**: store the canonical R2 CORS JSON in the repo and validate it matches the live config on every deploy.
- **Module isolation**: enforce via `tflint` that R2 bucket CORS resources must not share a module with Hyperdrive or KV resources.

## Anti-patterns

- Co-locating CORS configuration with unrelated infrastructure resources in the same Terraform module.
- Using inline CORS rule values (hardcoded strings) rather than workspace-scoped variables.
- Smoke tests that only check HTTP 200 on a GET endpoint, ignoring OPTIONS preflight behaviour.
- Treating `~ cors_rules` in a Terraform plan diff as a low-risk change equivalent to a tag update.
- Not keeping the canonical CORS config in version control as the source of truth.

## Gotchas

- R2 CORS configuration is applied at the **bucket level**, not per-object or per-prefix. One misconfigured rule blocks all uploads to that bucket from all origins.
- Cloudflare's R2 CORS implementation requires `AllowedMethods` to explicitly include `PUT` for upload flows—`GET` and `HEAD` alone will pass preflight for reads but not writes.
- Presigned URL uploads still require CORS to be configured on the bucket; the presigned URL only handles auth, not CORS headers.
- When testing CORS with `curl`, you must send both `-H "Origin: ..."` and `-H "Access-Control-Request-Method: PUT"` to trigger a true preflight response—omitting either returns a non-preflight response that may look like a false pass.
- Cloudflare may cache CORS preflight responses for `MaxAgeSeconds`; after a config fix, browsers may need a hard refresh or may continue using the stale preflight cache for up to the old `max_age_seconds` value.

## Verification

1. Run `verify-r2-cors.sh` against the production bucket for each allowed origin and confirm HTTP 200 with correct `Access-Control-Allow-Origin`, `Access-Control-Allow-Methods`, and `Access-Control-Allow-Headers` headers.
2. Perform a manual end-to-end upload from a browser using the production origin and confirm no CORS error in the browser console.
3. Check Analytics Engine `upload_success_rate` metric for five minutes post-fix and confirm it returns to baseline (≥99%).
4. Verify Terraform state file reflects the correct CORS config and that the new isolated module shows no pending changes.
