# R2 Presigned URL Race Condition and Upload Integrity Incident

- **Date:** 2026-08-23
- **Author:** example.com
- **Status:** production

## Symptom / Use-case
Users uploading profile images via client-side presigned R2 URLs intermittently received a `403 Forbidden`
on PUT and, in a smaller subset of cases, successfully uploaded a file that was immediately overwritten
by a stale retry — resulting in corrupted or replaced profile images appearing hours after the user had
already changed them to something else.

## Context
The upload flow used short-lived presigned URLs generated by a Cloudflare Worker acting as an API
gateway. The frontend requested a presigned URL, uploaded the file directly to R2, then called a
second API endpoint to confirm the upload and update the user's profile record in D1. Two races
existed: (1) the presigned URL's 15-minute expiry was calculated at Worker request time but the
user might not begin uploading for several minutes, particularly on slow mobile connections; (2) the
client's retry logic on network errors re-used the original presigned URL without checking whether the
prior attempt had partially succeeded, leading to duplicate PUT requests landing out of order.

## Presigned URL Generation and the Clock Skew Problem

Workers generate presigned URLs using `Date.now()` at request time, but the 15-minute window erodes
before the user even starts uploading on a slow connection. The fix was to defer expiry calculation
to actual upload start using a two-stage approach:

```typescript
// Stage 1: Worker generates a short-lived "intent token" stored in KV
// Stage 2: Client exchanges the token for a fresh presigned URL just before uploading

interface UploadIntent {
  userId: string;
  filename: string;
  contentType: string;
  issuedAt: number;
}

export async function issueUploadIntent(
  env: Env,
  userId: string,
  filename: string,
  contentType: string
): Promise<{ intentToken: string }> {
  const intentToken = crypto.randomUUID();
  const intent: UploadIntent = { userId, filename, contentType, issuedAt: Date.now() };
  // Intent is valid for 30 minutes; presigned URL is generated only when exchanged
  await env.UPLOAD_INTENTS_KV.put(
    `intent:${intentToken}`,
    JSON.stringify(intent),
    { expirationTtl: 1800 }
  );
  return { intentToken };
}

export async function exchangeIntentForPresignedUrl(
  env: Env,
  intentToken: string
): Promise<{ url: string; key: string }> {
  const raw = await env.UPLOAD_INTENTS_KV.get(`intent:${intentToken}`);
  if (!raw) throw new Error("Intent token expired or invalid");

  const intent: UploadIntent = JSON.parse(raw);
  // Delete intent immediately to prevent replay
  await env.UPLOAD_INTENTS_KV.delete(`intent:${intentToken}`);

  const key = `uploads/${intent.userId}/${crypto.randomUUID()}-${intent.filename}`;
  const url = await env.R2_BUCKET.createPresignedUrl("PUT", key, {
    expiresIn: 300, // 5-minute window — tight because we just issued it
    httpMetadata: { contentType: intent.contentType },
  });
  return { url, key };
}
```

## Preventing Stale Retry Overwrites

The second race — retry storms overwriting the committed file — was caused by the client's exponential
backoff retrying a PUT that had actually succeeded, but whose 200 response was lost due to a network
timeout. On retry, the same presigned URL was still valid and the client sent the same file content to
the same key, but because the presigned URL was generated with a content-addressed key (UUID), the
overwrite was harmless in isolation. The problem was the profile update confirmation endpoint was
called twice: once by the original request (which timed out on the client side) and once by the retry.

The fix required an idempotency key on the confirmation endpoint:

```typescript
interface ConfirmUploadBody {
  key: string;
  idempotencyKey: string; // Client-generated UUID, same across retries
}

export async function confirmUpload(
  env: Env,
  userId: string,
  body: ConfirmUploadBody
): Promise<void> {
  const idempotencyRecord = await env.UPLOAD_INTENTS_KV.get(
    `confirm:${body.idempotencyKey}`
  );
  if (idempotencyRecord) {
    // Already confirmed — return success without re-applying
    return;
  }

  // Verify the object exists in R2 before updating the profile
  const object = await env.R2_BUCKET.head(body.key);
  if (!object) {
    throw new Error(`R2 object not found: ${body.key}`);
  }

  await env.DB.prepare(
    "UPDATE users SET avatar_key = ?1, avatar_updated_at = ?2 WHERE id = ?3"
  ).bind(body.key, Date.now(), userId).run();

  // Record confirmation for 24 hours to absorb retries
  await env.UPLOAD_INTENTS_KV.put(
    `confirm:${body.idempotencyKey}`,
    JSON.stringify({ key: body.key, confirmedAt: Date.now() }),
    { expirationTtl: 86400 }
  );
}
```

## Validating R2 Object Integrity Post-Upload

R2 does not currently support server-side checksum verification on PUT (unlike S3's `x-amz-checksum-*`
headers). The team added client-side checksum verification by requiring the client to send the SHA-256
of the file content in the confirmation request, then re-reading the first 64 KB of the uploaded object
to compare:

```typescript
async function verifyUploadIntegrity(
  bucket: R2Bucket,
  key: string,
  expectedSha256: string
): Promise<void> {
  const object = await bucket.get(key, { range: { offset: 0, length: 65_536 } });
  if (!object) throw new Error("Object not found after upload");

  const bodyBytes = new Uint8Array(await object.arrayBuffer());
  const digest = await crypto.subtle.digest("SHA-256", bodyBytes);
  const actual = Array.from(new Uint8Array(digest))
    .map((b) => b.toString(16).padStart(2, "0"))
    .join("");

  // For files > 64 KB this is a partial check — sufficient for profile images (< 5 MB limit)
  if (!actual.startsWith(expectedSha256.slice(0, actual.length))) {
    await bucket.delete(key); // Remove corrupt upload
    throw new Error("Upload integrity check failed");
  }
}
```

## Anti-patterns
- Generating presigned URLs with a long expiry at request time when the user may not start
  uploading immediately
- Reusing the same presigned URL across client retries without checking if the first attempt succeeded
- Confirming an upload to the application database without first verifying the object exists in R2
- Using a fixed key (e.g., `avatars/<userId>.jpg`) for user uploads — concurrent uploads from
  multiple sessions overwrite each other; always use a UUID-prefixed key and update the reference

## Gotchas
- R2 presigned URL expiry is calculated from the moment the URL is signed, not from when the client
  receives it; account for network round-trip time in your expiry window
- `R2Bucket.createPresignedUrl` requires the `workers_r2_temp_url` feature to be enabled in `wrangler.toml`
  and is not available in all Cloudflare plans
- Presigned URLs bypass R2 bucket access policies — any client with the URL can PUT regardless of
  Worker authentication; always scope keys to a user-controlled path prefix and keep expiry short
- `R2Bucket.head()` counts against R2 Class B operation limits; batch confirmation requests can
  cause unexpected cost spikes

## Verification
1. Write an integration test using Miniflare that simulates a network timeout after a successful PUT
   and asserts the retry with the same idempotency key returns 200 without duplicating the DB record.
2. In staging, upload a deliberately corrupt file (truncate last 100 bytes) and assert the integrity
   check deletes the object and returns an error to the client.
3. Verify the presigned URL exchange endpoint returns a 404 on a second call with the same intent
   token (confirms single-use enforcement).
