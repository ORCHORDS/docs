# Vite Workers Build Plugin Custom

Date: 2026-08-23
Author: example.com
Status: production

## Symptom / Use-case

The standard `@cloudflare/vite-plugin` covers most Cloudflare Workers build scenarios, but example project has specialised needs: inlining WASM modules, virtualising feature-flag files at build time, or injecting per-environment metadata into the bundle without a runtime fetch. Writing a custom Vite plugin that targets the Workers build pipeline solves these without forking the upstream plugin.

## Context

Cloudflare Workers uses `workerd` as its runtime and `wrangler` as the build/deploy CLI. When Vite is used as the asset pipeline (`@cloudflare/vite-plugin`), the Worker entry point is built via Vite's SSR pipeline with `platform: "neutral"` (or `"browser"` for modules targeting the edge). Custom Vite plugins integrate at the same points as any SSR plugin but must respect Workers constraints: no Node.js built-ins, no dynamic `require`, no `import.meta.url` that resolves to the file system.

## Plugin Skeleton

A minimal custom Vite plugin targeting Workers follows the same interface as any Vite plugin but must set `enforce: "pre"` when it needs to run before `@cloudflare/vite-plugin` transforms input.

```typescript
// tools/vite-plugin-workers-feature-flags.ts
import type { Plugin } from "vite";

export interface WorkersFeatureFlagsOptions {
  /** Map of flag name to boolean, resolved at build time */
  flags: Record<string, boolean>;
  /** Virtual module id that the Worker imports */
  moduleId?: string;
}

const VIRTUAL_MODULE_ID = "virtual:feature-flags";
const RESOLVED_ID = `\0${VIRTUAL_MODULE_ID}`;

export function workersFeatureFlagsPlugin(
  options: WorkersFeatureFlagsOptions,
): Plugin {
  const moduleId = options.moduleId ?? VIRTUAL_MODULE_ID;
  const resolvedId = `\0${moduleId}`;

  return {
    name: "workers-feature-flags",
    enforce: "pre",

    resolveId(id) {
      if (id === moduleId) return resolvedId;
      return null;
    },

    load(id) {
      if (id !== resolvedId) return null;

      // Emit as a typed ES module — tree-shaken at build time
      const entries = Object.entries(options.flags)
        .map(([k, v]) => `export const ${k}: boolean = ${v};`)
        .join("\n");

      return `// auto-generated by workers-feature-flags plugin\n${entries}\n`;
    },
  };
}
```

Usage in `vite.config.ts`:

```typescript
import { cloudflare } from "@cloudflare/vite-plugin";
import { defineConfig } from "vite";
import { workersFeatureFlagsPlugin } from "./tools/vite-plugin-workers-feature-flags";

export default defineConfig({
  plugins: [
    workersFeatureFlagsPlugin({
      flags: {
        ENABLE_DM_REACTIONS: process.env.ENABLE_DM_REACTIONS === "true",
        ANONYMOUS_FEED_V2: true,
      },
    }),
    cloudflare(),
  ],
});
```

The Worker then imports flags with full type inference and zero runtime overhead:

```typescript
// src/features/feed.ts
import { ANONYMOUS_FEED_V2 } from "virtual:feature-flags";

export function buildFeedQuery(): string {
  return ANONYMOUS_FEED_V2 ? buildV2Query() : buildV1Query();
}
```

## WASM Inline Plugin

Workers supports WASM via `import` with the `?raw` suffix or via explicit `WebAssembly.instantiate`. A custom plugin can automate the inline base64 dance for small WASM blobs.

```typescript
// tools/vite-plugin-workers-wasm-inline.ts
import type { Plugin } from "vite";
import { readFileSync } from "node:fs";
import { resolve } from "node:path";

const WASM_SUFFIX = "?workers-wasm";

export function workersWasmInlinePlugin(): Plugin {
  return {
    name: "workers-wasm-inline",
    enforce: "pre",

    resolveId(id, importer) {
      if (!id.endsWith(WASM_SUFFIX)) return null;
      const cleanId = id.slice(0, -WASM_SUFFIX.length);
      const resolved = resolve(importer ? resolve(importer, "..") : process.cwd(), cleanId);
      return `\0wasm-inline:${resolved}`;
    },

    load(id) {
      if (!id.startsWith("\0wasm-inline:")) return null;
      const filePath = id.slice("\0wasm-inline:".length);
      const bytes = readFileSync(filePath);
      const base64 = bytes.toString("base64");
      // Emit a module that decodes and instantiates synchronously
      return `
const bytes = Uint8Array.from(atob(${JSON.stringify(base64)}), c => c.charCodeAt(0));
const module = new WebAssembly.Module(bytes);
export default module;
      `.trim();
    },
  };
}
```

## Build-time Metadata Injection

Inject git commit hash and build timestamp into the Worker bundle without a runtime env var lookup.

```typescript
// tools/vite-plugin-workers-build-meta.ts
import type { Plugin } from "vite";
import { execSync } from "node:child_process";

const MODULE_ID = "virtual:build-meta";
const RESOLVED_ID = `\0${MODULE_ID}`;

export function workersBuildMetaPlugin(): Plugin {
  const commitHash = (() => {
    try {
      return execSync("git rev-parse --short HEAD").toString().trim();
    } catch {
      return "unknown";
    }
  })();

  const buildTime = new Date().toISOString();

  return {
    name: "workers-build-meta",

    resolveId(id) {
      if (id === MODULE_ID) return RESOLVED_ID;
      return null;
    },

    load(id) {
      if (id !== RESOLVED_ID) return null;
      return `
export const COMMIT_HASH: string = ${JSON.stringify(commitHash)};
export const BUILD_TIME: string = ${JSON.stringify(buildTime)};
      `.trim();
    },
  };
}
```

## Anti-patterns

- Using `fs` or `path` inside the `transform` hook's returned code — that code runs in the Worker runtime where Node.js built-ins don't exist; use them only in plugin hooks (which run in Node.js at build time)
- Returning large base64 blobs for WASM files > 1 MB — Workers has a 25 MB compressed bundle limit; prefer `wasm_modules` binding in `wrangler.toml` for larger assets
- Registering a plugin without `enforce: "pre"` when it virtualises modules — `@cloudflare/vite-plugin` may intercept the module id first
- Mutating `options.flags` after the plugin is created — flags are captured at plugin instantiation; restart Vite to pick up changes

## Gotchas

- Virtual module IDs must be prefixed with `\0` in `resolveId` return values and `load` id comparisons; omitting `\0` causes Vite to treat them as file paths
- `wrangler dev` uses its own bundler (esbuild) when invoked directly; the Vite plugin only applies when you invoke `vite dev` via `@cloudflare/vite-plugin`'s dev mode
- HMR does not work with virtual modules that change based on env vars; a full Vite restart (`r` in the terminal) is required
- TypeScript `/// <reference types="..." />` declarations for virtual modules must live in a `.d.ts` file in the project root or in `src/`

## Verification

```bash
# Build and inspect the bundle for the injected constants
vite build --mode production
# Check dist/ for the Worker bundle, then grep for the constant:
strings dist/worker.js | grep "ANONYMOUS_FEED_V2"
# Expected: the string "true" or "false" hardcoded, no runtime reference

# For WASM inline plugin:
vite build && grep "WebAssembly.Module" dist/worker.js
```
