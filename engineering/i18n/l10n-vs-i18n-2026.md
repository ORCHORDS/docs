# l10n-vs-i18n-2026

**Issue:** A team says they're "doing i18n" but has hardcoded English strings in JSX. Another team says "l10n is done" but the app crashes on non-Latin input. The terms are used interchangeably; the practices are different.
**Date:** 2026-08-10
**Repo:** example-org/example-repo
**Author:** ORCHORDS
**Status:** published

## Symptom

Teams confuse internationalization (i18n) and localization (l10n). The two are sequential, not interchangeable. i18n is engineering work done once; l10n is per-locale content work done continuously. A team that does l10n without i18n ships broken translations. A team that does i18n without l10n ships empty UI.

## Root cause

- **Internationalization (i18n):** Designing and engineering the product so it can be adapted to different languages and regions without engineering changes. Engineering work, done once. Includes: string extraction, locale-aware APIs, character encoding, RTL support, locale data, time zones, number/currency formatting.
- **Localization (l10n):** Adapting the product for a specific locale, including translating text, adapting images, formatting dates/numbers/currencies, complying with local regulations. Content work, done per locale. Includes: translation, glossary, terminology, locale-specific imagery, regulatory compliance.

The numerals reflect the practice: i18n has 18 letters between i and n; l10n has 10 letters between l and n.

## The i18n checklist (engineering, done once)

- [ ] All user-facing strings extracted to a translation file (no hardcoded English in JSX/HTML)
- [ ] ICU MessageFormat or i18next for plural/gender
- [ ] Locale-aware APIs (Intl.NumberFormat, Intl.DateTimeFormat, Intl.PluralRules)
- [ ] Time zone handling (Temporal API or Date with IANA zone)
- [ ] Character encoding: UTF-8 declared everywhere; utf8mb4 in MySQL
- [ ] RTL support: `dir="rtl"`, CSS logical properties, mixed-direction `<bdi>` for inline content
- [ ] Font fallbacks: Latin, CJK, Arabic, Hebrew, emoji
- [ ] Locale negotiation: URL segment, cookie, Accept-Language
- [ ] Date/time/calendar formats: Gregorian default; other calendars where required
- [ ] Address/phone/postal code patterns: locale-specific

A team that completes this checklist has i18n done. The product can be adapted to any locale; the remaining work is content.

## The l10n checklist (per locale, done continuously)

- [ ] Translation: 100% of user-facing strings translated
- [ ] Glossary: key terms documented and used consistently
- [ ] Translation memory: leverage previous translations
- [ ] Pseudo-localization tested before real translations
- [ ] Native speaker review (not just machine translation)
- [ ] Locale-specific imagery (icons, illustrations, photos)
- [ ] Regulatory compliance (cookie consent, age verification, accessibility)
- [ ] Currency, date, number formats per locale
- [ ] Cultural conventions (formality, color, gestures)
- [ ] Continuous updates as product evolves

A team that completes this checklist per locale has l10n done. The product is fully adapted to that locale.

## The sequence

i18n must come first. The engineering work:

1. Extract strings
2. Add locale-aware APIs
3. Test with pseudo-localization
4. Add RTL/encoding/timezone support
5. Validate with a non-Latin test locale (Arabic, Chinese, Russian)

After i18n is done, l10n begins:

1. Choose target locales
2. Set up translation workflow (in-house, vendor, or platform)
3. Translate strings
4. Native speaker review
5. Continuous updates with the product

A team that starts l10n before i18n is done wastes effort — the engineering changes break the translations, and the translators re-do work.

## The common failures

| Failure | Symptom | Fix |
|---|---|---|
| l10n without i18n | Translators translate hardcoded English; refactor breaks everything | i18n first |
| i18n without l10n | Product supports locale switching but strings are English | l10n next |
| i18n for English, French, German only | Russian, Arabic, Chinese break in production | Add non-Latin test locales early |
| "We'll add i18n later" | Refactoring cost grows 10x as product matures | Add i18n from day 1 |
| Pseudo-locale in dev only | Translations break in production where the pseudo-locale isn't used | Pseudo-locale in production smoke tests |

## The relationship to translation platforms

- **i18next, FormatJS, react-intl, vue-i18n** — engineering libraries for i18n
- **Phrase, Lokalise, Crowdin, Transifex, Smartling** — content platforms for l10n
- **gettext + POEditor** — classic open-source i18n + l10n
- **ICU MessageFormat + Locale-specific translators** — for complex i18n

The i18n library extracts strings and provides runtime formatting. The l10n platform manages translations, glossaries, and translator workflows. The two integrate but serve different roles.

## The continuous loop

i18n and l10n are not one-time projects. They are continuous:

- New features → new strings → i18n extraction → translation
- New locales → locale-aware config → translation → review
- Bug fixes → regression in pseudo-locale → i18n fix
- Regulatory changes → compliance review → code/config changes

A team that treats i18n+l10n as a one-time project ships a product that drifts out of compliance. The discipline is continuous: every PR that adds a string also adds the translation files for active locales.

## The team structure

For a 2026 product:

- **Engineering** owns i18n: string extraction, locale APIs, RTL support
- **Localization PM** owns l10n: locale selection, translation vendors, glossary
- **Translators** (in-house or vendor) produce the actual content
- **Native reviewers** validate translations and flag cultural issues
- **Legal** reviews regulatory compliance per locale (especially for EU, China, Russia)

## The verification

The tell that i18n is done:

- A developer can add a new string and ship to all active locales without code changes for other locales
- Pseudo-localization in CI catches layout and encoding bugs
- The codebase has no hardcoded English in user-facing paths

The tell that l10n is done per locale:

- 100% of strings are translated and reviewed
- The locale's regulatory requirements are met
- A native speaker confirms the product is usable and culturally appropriate
