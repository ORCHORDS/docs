# mobile-crash-symbolication

**Issue:** Converting obfuscated crash stack traces back to readable source locations for iOS and Android
**Date:** 2026-08-11
**Status:** documented

## Symptom / Context
Production crashes show method addresses or obfuscated names; symbolication maps them back to file names and line numbers.

## Pattern / Solution
**iOS — dSYM files:**
```sh
# Upload dSYMs to Firebase Crashlytics
./Pods/FirebaseCrashlytics/upload-symbols -gsp GoogleService-Info.plist -p ios MyApp.app.dSYM

# Manually symbolicate a crash log
xcrun atos -o MyApp.app/MyApp -arch arm64 -l 0x100000000 0x0000000100012345
```

Archive builds automatically in Xcode generate dSYMs; enable in Build Settings: `Debug Information Format = DWARF with dSYM File`.

**Android — ProGuard/R8 mapping files:**
```sh
# retrace a crash log
java -jar retrace.jar mapping.txt crash.txt

# Firebase automatically symbolicates if mapping is uploaded via Gradle plugin
# gradle.properties
crashlytics.mappingFileUploadEnabled=true
```

Fastlane integration:
```ruby
lane :upload_symbols do
  upload_symbols_to_crashlytics(dsym_path: './MyApp.app.dSYM')
end
```

**React Native JS crashes:**
- Source maps are uploaded via `@sentry/react-native`:
```sh
npx sentry-cli sourcemaps upload --release 1.0.0 --dist 1 ios/main.jsbundle.map
```

## Gotchas
- dSYMs must match the exact build UUID — archiving again produces a new UUID that won't match old crashes
- Bitcode-enabled builds have dSYMs generated by Apple's servers; download them from App Store Connect
- R8 mapping files are per-build; store them alongside the AAB in your artifact storage
- React Native JS stack traces require both the JS source map and the native dSYM/mapping to fully symbolicate
