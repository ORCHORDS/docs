# Outbox Pattern for Reliable Event Publishing with D1

- **Date**: 2026-08-22
- **Author**: example.com
- **Status**: production

---

## Symptom / Use-case

You update a row in D1 (`orders` table, status → `PAID`) and immediately try to
publish an event to Cloudflare Queues or an external webhook so downstream
services can react. Sometimes the queue `send()` fails after the DB write
succeeds, or the Worker crashes after the commit but before the send. Consumers
never learn the order was paid.

This is the **dual-write problem**: two side-effects that must either both
succeed or both be rolled back, but they live in different systems that share no
transaction boundary.

---

## Context

The **Transactional Outbox** pattern resolves the dual-write problem by
collapsing it into a single transaction. Instead of writing to the DB and
*separately* sending to the queue, you:

1. Write the domain change **and** an outbox row in one D1 transaction.
2. A separate relay process reads unprocessed outbox rows and publishes them to
   the queue.
3. Once the queue confirms delivery, the relay marks the rows as sent.

Because step 1 is atomic, either both the domain row and the outbox row are
committed, or neither is. The relay guarantees at-least-once delivery; consumers
must be idempotent (see the companion Inbox pattern).

In Cloudflare Workers the relay is a **Cron Trigger** Worker that polls D1 every
minute (or a Durable Object alarm for sub-minute precision). The event
destination is typically Cloudflare Queues, an HTTP webhook, or another Worker
via service binding.

## Schema Design

```sql
-- migrations/001_create_outbox.sql

CREATE TABLE IF NOT EXISTS outbox (
  id           TEXT    PRIMARY KEY,   -- UUID v4 generated by the app
  aggregate_id TEXT    NOT NULL,      -- e.g. order_id
  event_type   TEXT    NOT NULL,      -- e.g. "order.paid"
  payload      TEXT    NOT NULL,      -- JSON blob
  created_at   INTEGER NOT NULL,      -- Unix ms
  sent_at      INTEGER,               -- NULL until relayed
  failed_at    INTEGER,               -- NULL until relay gives up
  attempts     INTEGER NOT NULL DEFAULT 0,
  last_error   TEXT
);

CREATE INDEX IF NOT EXISTS idx_outbox_unsent
  ON outbox (created_at)
  WHERE sent_at IS NULL AND failed_at IS NULL;
```

Keep the `payload` column as a JSON string — D1 does not have a native JSON
column type, but `JSON()` / `json_extract()` still work for queries.

## Writing to the Outbox (Transactional Write)

```typescript
// src/handlers/pay-order.ts
import { Env } from '../types';
import { randomUUID } from 'crypto';

export async function payOrder(
  orderId: string,
  env: Env,
): Promise<Response> {
  const eventId = randomUUID();
  const now = Date.now();

  // Single transaction: domain write + outbox write
  await env.DB.batch([
    env.DB.prepare(
      `UPDATE orders SET status = 'PAID', paid_at = ? WHERE id = ? AND status = 'PENDING'`
    ).bind(now, orderId),

    env.DB.prepare(
      `INSERT INTO outbox (id, aggregate_id, event_type, payload, created_at)
       VALUES (?, ?, ?, ?, ?)`
    ).bind(
      eventId,
      orderId,
      'order.paid',
      JSON.stringify({ orderId, paidAt: now }),
      now,
    ),
  ]);

  // DB.batch() is atomic — both statements succeed or both are rolled back.
  // Do NOT call env.QUEUE.send() here.

  return new Response(JSON.stringify({ ok: true }), {
    headers: { 'Content-Type': 'application/json' },
  });
}
```

`DB.batch()` wraps all statements in a single implicit transaction on D1's SQLite
layer. If the second `INSERT` violates a constraint, the `UPDATE` is also
rolled back.

## The Relay Worker (Cron Trigger)

```typescript
// src/relay/outbox-relay.ts
import { Env } from '../types';

const BATCH_SIZE = 50;
const MAX_ATTEMPTS = 5;

export async function relayOutbox(env: Env): Promise<void> {
  // Fetch a batch of unsent, non-failed events ordered oldest-first
  const { results } = await env.DB.prepare(
    `SELECT id, aggregate_id, event_type, payload, attempts
     FROM outbox
     WHERE sent_at IS NULL
       AND failed_at IS NULL
       AND attempts < ?
     ORDER BY created_at ASC
     LIMIT ?`
  ).bind(MAX_ATTEMPTS, BATCH_SIZE).all<OutboxRow>();

  if (results.length === 0) return;

  for (const row of results) {
    try {
      // Publish to Cloudflare Queues
      await env.EVENTS_QUEUE.send({
        id: row.id,
        type: row.event_type,
        aggregateId: row.aggregate_id,
        payload: JSON.parse(row.payload),
      });

      // Mark as sent
      await env.DB.prepare(
        `UPDATE outbox SET sent_at = ?, attempts = attempts + 1 WHERE id = ?`
      ).bind(Date.now(), row.id).run();

    } catch (err) {
      const attempts = row.attempts + 1;
      const isExhausted = attempts >= MAX_ATTEMPTS;

      await env.DB.prepare(
        `UPDATE outbox
         SET attempts = ?,
             last_error = ?,
             failed_at = CASE WHEN ? THEN ? ELSE NULL END
         WHERE id = ?`
      ).bind(
        attempts,
        String(err),
        isExhausted ? 1 : 0,
        isExhausted ? Date.now() : null,
        row.id,
      ).run();
    }
  }
}

// Wrangler handler
export default {
  async scheduled(_event: ScheduledEvent, env: Env): Promise<void> {
    await relayOutbox(env);
  },
};
```

```toml
# wrangler.toml (excerpt)

crons = ["* * * * *"]   # Every minute

[[queues.producers]]
queue = "events"
binding = "EVENTS_QUEUE"
```

## Outbox Pruning

Sent outbox rows are safe to delete after a retention window. Add a second cron
or extend the relay to prune:

```typescript
async function pruneOutbox(env: Env): Promise<void> {
  const cutoff = Date.now() - 7 * 24 * 60 * 60 * 1000; // 7 days
  await env.DB.prepare(
    `DELETE FROM outbox WHERE sent_at IS NOT NULL AND sent_at < ?`
  ).bind(cutoff).run();
}
```

Do not prune `failed_at` rows automatically — they represent events that were
never delivered and need human review or a requeue workflow.

## Anti-patterns

**Sending to the queue inside the same request handler (no outbox)**
The queue send is not part of the D1 transaction. A Worker crash, timeout, or
queue backpressure error drops the event silently.

**Using KV as the outbox store**
KV is eventually consistent and offers no atomic multi-key transactions. A D1
relational table with SQL constraints is the right primitive here.

**Polling too frequently without an index**
A full table scan every second on a large `outbox` table will exhaust D1 row
read limits. The partial index `WHERE sent_at IS NULL AND failed_at IS NULL`
dramatically reduces the scan range.

**Not capping `MAX_ATTEMPTS`**
Without a cap, poison-pill events (malformed payload that always fails
deserialization) loop forever, consuming relay CPU and queue quota.

## Gotchas

- **D1 `batch()` vs explicit transactions**: `batch()` is atomic but does not
  expose `BEGIN`/`COMMIT`. For more complex multi-table writes use
  `DB.prepare("BEGIN").run()` / `DB.prepare("COMMIT").run()` in sequence, keeping
  in mind D1 has no support for `SAVEPOINT` as of mid-2026.

- **Clock skew on `created_at`**: Workers run across many PoPs. Use
  `Date.now()` consistently (always server-side, never client-supplied) to avoid
  ordering anomalies in the relay batch.

- **Queue send is not idempotent by default**: If the relay publishes to the
  queue and then fails to mark `sent_at` before the Cron is killed, the same
  event will be relayed again on the next tick. Consumers **must** implement the
  Inbox pattern to absorb duplicates.

- **D1 `batch()` statement limit**: A single batch is limited to 100 statements.
  Do not attempt to relay more than ~49 events (1 SELECT + 49 × 2 UPDATE/INSERT
  pairs) in a single batch call.

## Verification

```bash
# 1. Trigger a domain write that should produce an outbox row
curl -X POST https://api.example.com/orders/ord_123/pay

# 2. Inspect the outbox immediately (before relay runs)
wrangler d1 execute MY_DB --command \
  "SELECT id, event_type, sent_at, attempts FROM outbox WHERE aggregate_id = 'ord_123'"

# 3. Wait for the cron relay (or trigger it manually)
wrangler dev --local  # run: scheduled event

# 4. Confirm sent_at is populated
wrangler d1 execute MY_DB --command \
  "SELECT sent_at, attempts FROM outbox WHERE aggregate_id = 'ord_123'"

# 5. Confirm message landed in the queue consumer
# tail the consumer Worker logs
wrangler tail my-queue-consumer
```
