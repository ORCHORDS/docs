# sbom-slsa-2026

**Issue:** A team ships a container image. A CVE drops in a dependency. The team doesn't know which image versions are affected. The team doesn't know which build produced the image. The team has no SBOM, no provenance, no signed artifact. The supply chain is opaque.

**Date:** 2026-08-10
**Repo:** example-org/example-repo
**Author:** ORCHORDS
**Status:** published

## Symptom

Supply chain attacks (SolarWinds 2020, Log4Shell 2021, xz-utils 2024) exploit the gap between source code and shipped artifact. The 2026 defense stack is SBOM (bill of materials) + SLSA provenance + signed artifacts.

## Root cause

Three concerns get conflated:

1. **What is in the artifact?** — answered by SBOM (CycloneDX or SPDX)
2. **How was the artifact built?** — answered by SLSA provenance
3. **Is the artifact authentic?** — answered by cryptographic signing (cosign, sigstore)

Adopt all 3. Each answers a different question.

## The 3 SBOM formats

| Format | Maintainer | Strength | Use case |
|---|---|---|---|
| CycloneDX | OWASP | lightweight, security-focused, supports VEX | 2026 default for security tooling |
| SPDX | Linux Foundation | license-focused, legal compliance | license audits, legal review |
| Syft JSON | Anchore | tool-specific output | Syft-generated SBOMs |

The 2026 default is CycloneDX for security use cases; SPDX for license use cases. Most tools (Syft, Trivy, Grype) emit both.

## The SLSA build levels

SLSA v1.0 (pronounced "salsa") defines 3 build levels.

| Level | Guarantee | Threat stopped |
|---|---|---|
| L1 | provenance exists | almost nothing (documentation) |
| L2 | provenance is signed by hosted build service | tampering during distribution |
| L3 | provenance generated by tamper-resistant build platform | everything short of builder compromise |

L2 is the 2026 baseline. L3 is achievable with one workflow addition (slsa-github-generator). L4 (two-party review + hermetic builds) is aspirational.

## The GitHub Actions L2 pattern

```yaml
# .github/workflows/release.yml
name: Release
on:
  push:
    tags: ['v*']

jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      - name: Build binary
        run: make build

      - name: Generate SBOM
        uses: anchore/sbom-action@v0
        with:
          format: cyclonedx-json
          output-file: sbom.cdx.json

      - name: Attest build provenance (SLSA L2)
        uses: actions/attest-build-provenance@v3
        with:
          subject-path: ./dist/myapp

      - name: Attest SBOM
        uses: actions/attest-sbom@v3
        with:
          subject-path: ./dist/myapp
          sbom-path: sbom.cdx.json
```

`actions/attest-build-provenance` is GA since late 2024. It produces SLSA L2 provenance signed by GitHub's OIDC issuer. One workflow step.

## The L3 pattern with slsa-github-generator

For higher assurance, use `slsa-framework/slsa-github-generator`:

```yaml
# In the build job, after building the artifact
- name: Generate SLSA L3 provenance
  uses: slsa-framework/slsa-github-generator/.github/workflows/generator_container_slsa3.yml@v2
  with:
    image: myapp
    registry: ghcr.io/myorg
```

L3 adds build environment isolation: ephemeral, no shared state, hermetic. The provenance is non-forgeable by the repo owner.

## The cosign + sigstore layer

SLSA answers "how was it built?" Cosign answers "is this the artifact?"

```bash
# Sign a container image (keyless, uses OIDC)
cosign sign --yes ghcr.io/myorg/myapp@sha256:abc123...

# Verify
cosign verify --certificate-identity-regexp 'https://github.com/myorg/myapp' \
  --certificate-oidc-issuer 'https://token.actions.githubusercontent.com' \
  ghcr.io/myorg/myapp@sha256:abc123...

# Attest an SBOM (signed, recorded in Rekor transparency log)
cosign attest --yes --predicate sbom.cdx.json --type cyclonedx \
  ghcr.io/myorg/myapp@sha256:abc123...
```

Keyless signing uses OIDC tokens (e.g., GitHub Actions workflow identity). No key to manage; the workflow's identity is the signer.

## The 5-stage pipeline

The 2026 production supply chain pipeline.

1. **Source commit** triggers CI build
2. **CI build** produces a container image + 2 attestations: SLSA provenance + CycloneDX SBOM
3. **Cosign keyless signing** signs the image and both attestations, recording signatures in Rekor
4. **Registry stores** image + attestations as OCI referrer artifacts (same digest, never drift)
5. **Admission controller** (e.g., Kyverno, Connaisseur) verifies signatures before Kubernetes deploy

The full chain closes: source commit -> CI build -> signed attestations -> registry -> admission enforcement.

## The 5 anti-patterns

1. **SBOM without provenance.** An SBOM alone says "what's in the artifact" but not "is this the artifact you think it is." Combine with SLSA + cosign.
2. **Provenance at L1 only.** L1 is documentation. Push to L2 (signed by hosted build) minimum.
3. **Key-based cosign signing without key management.** Keyless signing via OIDC removes the key management problem. Use it.
4. **No admission enforcement.** Attestations are useless if the cluster doesn't verify them. Wire up Kyverno or Connaisseur.
5. **SBOM generated once and forgotten.** New CVEs drop daily. Regenerate SBOMs on every build; track SBOM diffs over time.

## The cost / benefit

- **L2 provenance**: one workflow step, free, no infrastructure. Adopt today.
- **L3 provenance**: switch to slsa-github-generator; ~1 day of work, free.
- **Cosign signing**: install cosign, one workflow step, free.
- **SBOM generation**: install Syft or use anchore/sbom-action, free.
- **Admission enforcement**: deploy Kyverno (Kubernetes) or use a managed admission controller; ~1 week of work, free (OSS) or paid (managed).

L2 + cosign + SBOM is achievable in 1-2 days. No budget blocker.

## Verification

The tell that the supply chain stack is real:

- `actions/attest-build-provenance` is in the release workflow
- SBOM is generated and attested (CycloneDX or SPDX)
- Container images are signed with cosign (keyless or keyed)
- A registry stores the attestations as OCI referrers
- An admission controller verifies signatures before deploy
- `gh attestation verify` returns valid for the latest release

The tell it isn't:

- "We have a Dockerfile" is the only supply chain artifact
- No SBOM, no provenance, no signing
- An SBOM was generated once, attached to a wiki page
- A CVE drops and the team can't answer "which images are affected"

## Gotchas

- **CycloneDX vs SPDX**: pick one per use case. SPDX is better for license audits; CycloneDX is better for security. Don't try to standardize on one.
- **L2 vs L3**: L2 is signed provenance; L3 is signed by an isolated build platform. The difference is whether a compromised developer can forge provenance. L2 cannot; L3 also cannot.
- **Keyless signing requires OIDC.** The build platform must issue OIDC tokens (GitHub Actions does, GitLab CI does). Self-hosted runners without OIDC need key-based signing.
- **Rekor transparency log** is the public record of signatures. Verify against Rekor, not just the local cosign state.
- **The 30-day grace period** for new attestations on a tag. After 30 days, the attestations are immutable.
